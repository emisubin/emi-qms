# 모델·위임·실행 방식

일상 작업은 현재 대화에서 끝낸다. 적용 원칙과 승인 경계는 [Root AGENTS](../../AGENTS.md)가 소유한다.

## 모델 선택

| 실제 작업 영향 | 기본 선택 | 검토 |
| --- | --- | --- |
| 설명·좁은 문서/스타일 수정 | 현재 parent 직접 처리 | 직접 확인 |
| 범위가 명확한 일반 구현 | GPT-6 Medium 직접 구현 | 영향 테스트·diff 확인 |
| 기존 패턴의 반복·독립된 제한 구현 | 실익이 있을 때 Sol Medium/High 한 명 | parent가 계약·실제 diff·반례 확인 |
| 권한·3-DB·migration·동시성·운영/CI·큰 공통 기능 | GPT-6 High가 방향을 정하고 직접 구현 또는 좁게 위임 | 작성/구현과 분리된 GPT-6 High 검토 |
| 원인 불명 반복 실패·복잡한 판단 | 원인을 좁힌 뒤 해당 부분에만 xhigh 고려 | 가설·근거와 해결 여부 확인 |

파일명이나 파일 수가 아니라 실제 동작 영향으로 선택한다. 인증 파일의 오타가 인증 정책 변경은 아니며 한 줄 권한 변경도 높은 위험일 수 있다. 이 기본값은 PMS의 비용·속도 실측 최적값이라는 주장이 아니다.

[프로젝트 설정](../../.codex/config.toml)은 새 실행의 기본값이다. 채팅의 명시 선택·상위 정책·프로젝트 trust가 우선할 수 있고, 파일 변경만으로 현재 모델이나 실행 중 agent가 바뀌지 않는다. 사용자는 보통 **GPT-6 / Medium**, 권한·DB·배포 판단은 **High**로 시작하면 된다. 특정 모델만 요청했다면 그 선택을 따른다.

## 위임이 유용할 때

독립 구현 또는 필요한 독립 검토에만 agent를 사용한다. 일상적인 수정은 0명으로 끝날 수 있으며 동시 실행 한도는 사용 목표가 아니다.

위임 전에 다음을 하나의 짧은 계약으로 전달한다.

1. 목표, 사용자 요청·유효한 승인과 현재 사실.
2. 담당 파일, interface·데이터·권한·업무 불변조건과 제외 범위.
3. 권장 접근과 이유. 세부 구현을 전부 미리 작성하지 않는다.
4. 사용자에게 보이는 완료 조건, 실패 반례·필요 테스트와 반환 증거.
5. 완료/차단/판단 불충분의 반환 조건. 범위·운영·게시 권한을 넓히거나 재위임하지 않는다.

같은 Task·승인·업무 계약·검증을 공유하는 작은 반복 수정은 한 구현자에게 묶을 수 있다. 다른 권한·DB·배포 경계는 비용 때문에 합치지 않는다. 보정은 가능하면 같은 구현자에게 Finding과 영향 테스트를 돌려준다.

도구가 지원할 때 Sol 위임은 `model=gpt-5.6-sol`, `reasoning_effort=medium` 또는 `high`를 명시한다. 독립 검토는 `gpt-6-astra/high`로 요청한다. 모델 override와 전체 맥락 상속의 호환성 등 **현재 도구 schema**를 확인한다. 요청 모델과 도구가 실제 반환한 모델을 구분하고, 반환하지 않으면 `NOT_REPORTED`로 기록한다. 설정값을 관측값으로 쓰지 않는다.

## 검토와 세션

검토자는 실제 계약·diff·테스트를 읽는다. 한 검토에서 **요구사항 충족**과 **코드/운영 품질** 두 판단을 함께 내린다. parent가 직접 구현했으면 필요한 독립 reviewer 한 번으로 책임을 나누고, parent 확인을 추가 전체 review 회차로 늘리지 않는다.

첫 검토는 Task의 누적 변경과 allowlist WIP를 포함한다. 이후는 수정분·영향받는 호출 경계를 확인하며 새로운 위험이 생기면 범위를 넓힌다. 이전 전체 승인/지적과 최신 수정이 어떻게 연결되는지 기록한다. 기준선·Finding·완료 요건은 [완료 정책](../12-task-completion-policy.md)을 따른다.

새 reviewer 맥락을 기본으로 한다. 생성 한도 때문에 작성과 분리된 기존 reviewer 맥락을 재사용하면 그 사실을 밝히고 이번 기준선부터 다시 검토한다. 작성자/구현자 자신을 독립 검토자라고 부르지 않는다. 독립 수단이 없으면 해당 검토는 미완료이며 직접 구현으로 대체하지 않는다.

## 도구·속도·재시도

- 독립 조회를 묶고 결과를 필요한 범위로 좁힌다. 의존하는 변경·승인·배포는 순서대로 처리한다.
- 실행 중인 명령은 반환된 session으로 이어간다. timeout이나 출력 잘림만으로 서버·전체 테스트·배포를 중복 시작하지 않는다.
- 같은 로그를 반복 조회·중계하지 않고 의미 있는 진행·실패·결정을 알린다.
- 일시적 읽기/멱등 실패는 제한적으로 재시도한다. 같은 실패라면 바뀐 입력·가설을 확인하고 원인 조사로 전환한다.
- 버그는 재현 입력·최근 변경과 정상 경로를 비교해 가장 작은 원인 가설부터 검증한다. 승인 오류는 세션·readiness·Directory 소속·사업부 profile 중 실패 경계를 좁힌다.
- migration·배포·외부 전송의 응답이 불명확하면 실제 적용 상태·식별자·멱등성을 먼저 확인한다.
- 정책 거부는 사용자 승인 부재, 저장소 규칙, 실행환경 제한 중 확인된 사실만 설명한다. 정확한 판정 규칙을 못 봤다면 특정 모델/하네스 탓이라고 단정하지 않는다. 거부 동작을 변형해서 우회하지 않는다.
- 모델/도구가 없으면 사용자 지정 모델을 조용히 대체하거나 외부 CLI를 agent처럼 실행하지 않는다. 가능한 독립 작업과 미완료 범위를 구분한다.

## 맥락과 스킬

재개에는 기존 Task의 `목표 / 승인 범위 / branch·기준선 / 완료한 일 / session·자원 / 증거·실패 / 다음 행동`을 사용한다. 실제 diff와 대조하고 관련 없는 과거 보고·다른 프로젝트 기억을 모두 불러오지 않는다. 압축은 새 Task·새 승인·완료 기능 재구현의 이유가 아니다.

Repository 공통 반복 작업은 기존 script와 SOP를 먼저 사용한다. 문서·이미지·도구 등 전문 작업은 관련 스킬을 필요한 때만 읽는다. 개인 스킬을 한꺼번에 호출하거나 매 수정 뒤 skill→review→재설계 연쇄를 만들지 않는다. 전역 `~/.agents`, 공유 plugin·skill은 이번 PMS 규칙으로 수정하거나 비활성화하지 않는다. 별도 프로젝트 스킬 묶음이나 hooks는 반복 필요가 입증될 때만 만든다.

OmO의 목적별 작업 분리, CodexClaw의 재개 기록, Superpowers의 독립 기대값·작은 검증 단위·원인 조사·증거 기반 완료를 이 흐름에 통합했다. 외부 프로젝트는 설치하지 않았다. 선정 근거와 고정 출처는 [승인 설계 §9](pms-harness-redesign.md#9-스킬-정리)를 참고한다.

## 설정·명령 정책의 한계

repo config/rules는 신뢰된 프로젝트의 새 실행에서 로드된다. rules는 명령 prefix를 평가하며 임의 SQL·모든 옵션 순서·사용자 승인 이력을 이해하지 않는다. 일반 PR 조회와 shell wrapper에 별도 광범위 prompt를 두지 않지만 모든 명령을 allow로 열지도 않는다. 직접 SQL은 prefix로 읽기 전용을 보장할 수 없어 `psql` prompt를 유지한다. 일반 작업에 이 추가 제한이 불필요한지와 허용 수단은 해당 실행환경에서 판단한다.

명확한 게시/파괴 보호와 server 권한·DB guard·required CI를 유지한다. 이 설정은 상위 승인 정책을 낮추지 않으며 `never`는 모든 실행 허용이 아니다. 이번 정책 변경으로 이전에 거부된 명령을 재시도하지 않는다.

지원 항목과 적용 방식은 [OpenAI config reference](https://learn.chatgpt.com/docs/config-file/config-reference), [실행 규칙](https://learn.chatgpt.com/docs/agent-configuration/rules)에서 확인했다. 실제 비용·속도는 요청부터 검증된 완료까지의 전체 시간·사용량·재작업으로 비교하고 API 가격과 Codex 사용량을 혼용하지 않는다.
