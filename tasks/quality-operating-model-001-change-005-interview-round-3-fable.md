# TASK-QUALITY-OPERATING-MODEL-001 Change 005 — Deep Interview Round 3 (Fable 5)

- taskType: `NEW_FEATURE`

## Round 3 기준선 확인

Round 2 답변을 누적 interview 문서와 실제 코드·양식 관리 구현과 대조해 확인한 사실은 다음과 같다.

- 양식 관리에는 TASK-ADMIN-002로 이미 확정·구현된 **부서장 지정** 개념이 있다. 시스템 관리자가 품질·생산계획·제조 domain별로 "부서 양식 관리자(부서장)"를 지정·해제하고, 지정된 활성 사용자가 자기 부서 소속을 유지하는 동안에만 해당 domain 양식을 편집할 수 있다. 지정·해제는 append-only audit에 기록된다.
- 반면 현재 구매품 구분 관리(`IQC 필요` 토글 포함)는 부서장 지정과 무관하게 **품질부서 활성 사용자 전원**과 시스템 관리자가 변경할 수 있다. 즉 같은 양식 관리 영역 안에 "지정 부서장 전용"과 "품질부서 전원" 두 계약이 공존한다.
- 현재 모든 양식·구분 API는 시스템 관리자를 무조건 허용한다. 답변 5의 "관리자는 현장 업무에 관여하면 안 됨"은 현행 코드 동작과 다르므로 서버 강제 여부를 확정해야 한다.
- 답변 1·2로 확정된 방향: 구분마다 부서장이 양식 관리에서 스캔형/상세형을 선택하고 구매품(구분)별 검사 항목을 만들 수 있다. 스캔형을 외함 전용으로 고정하지 않는다.
- 답변 3으로 확정된 방향: 이번 작업은 기능 제공까지다. 판금류·부스바·명판을 실제로 켜는 것은 이후 품질팀이 화면에서 수행하며, 초기 상태는 현재 동작(외함=스캔형 검사, 나머지=검사 없음)을 보존한다.
- 답변 4로 확정된 방향: 이미 저장된 구매품에는 새 설정이 적용되지 않고, 구매품 입력 시점에 해당 구분의 검사 양식이 있고 검사 스위치가 켜져 있는 경우에만 IQC를 생성한다. 다만 스캔형은 체크리스트 항목이 없는 방식이므로 "양식이 있다"의 정확한 조건과, 상세형 스위치가 켜졌는데 항목이 0개인 경계 상황의 처리를 확정해야 한다.

다음은 이번 round에서 다시 질문하지 않는 확정 항목이다: 구분별 스캔형/상세형 선택 자유, 초기 상태 비변경, 기존 상세 IQC 엔진(항목·사진·판정·PDF·부적합 Pending·재검사) 재사용, 전역 `MATERIAL_IQC`의 legacy 프로젝트 전용 보존, 이미 저장된 구매품 비소급.

아래 4개 질문은 모두 답변 4·5를 실제 시스템 계약으로 옮길 때 구현 범위를 직접 바꾸는 blocking 결정이다.

### 질문 1 — "품질부서 부서장"을 시스템에서 어떻게 식별하는가

**필요한 이유**: 답변 5의 "품질부서 부서장이 모두 변경 가능"을 서버가 강제하려면 부서장을 식별하는 기준이 필요하다. 시스템에는 사용자 record 자체에 부서장 표시가 없는 대신, TASK-ADMIN-002의 "부서 양식 관리자 지정"이 부서장 개념으로 이미 운영되고 있다. 한편 현행 구매품 구분 관리는 지정 여부와 무관하게 품질부서 전원에게 열려 있어 어느 기준을 따를지 확정해야 한다.

**답변이 바꾸는 범위**: 구분별 검사 스위치·방식·검사 항목 변경 API의 권한 검사, 화면의 편집 활성 조건, 감사 기록 주체, 부서장 미지정 상태의 운영 안내.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A (권장) | 기존 품질 domain **부서 양식 관리자 지정**을 그대로 사용: 지정된 활성 품질 부서장만 검사 스위치·방식·항목을 변경 | 사용자가 말한 "부서장"과 정확히 일치하는 기존 개념·지정 화면·audit를 재사용하고, 검사 생략 같은 고위험 결정이 지정된 사람에게만 허용됨 | 품질 부서장이 지정돼 있지 않으면 관리자가 먼저 지정해야 설정을 시작할 수 있음 |
| B | 현행 구분 관리 계약과 동일하게 **품질부서 활성 사용자 전원** 허용 | 현행 권한과 동일해 운영 변화 없음 | 부서장이 아닌 품질부서원도 검사 생략·방식 전환이 가능해 답변 5의 "부서장" 통제 의도와 어긋남 |

권장안은 A다. 새 권한 개념을 만들지 않고 답변 5를 가장 충실하게 구현한다.

### 질문 2 — 시스템 관리자의 변경을 서버에서 차단하는가

**필요한 이유**: 답변 5는 "관리자는 현장 업무에 관여하면 안 되고 시스템만 관리한다"고 확정했지만, 현재 코드는 모든 양식·구분 API에서 시스템 관리자를 무조건 허용한다. 또한 기존 구분 관리 화면의 `IQC 필요` 토글이 새 검사 스위치와 같은 값을 다루므로, 두 편집 경로의 권한이 다르면 부서장 통제를 우회하는 구멍이 생긴다.

**답변이 바꾸는 범위**: Backend 권한 검사에서 관리자 예외 처리, 관리자 화면의 편집 비활성 표시, 기존 구분 관리 화면의 `IQC 필요` 토글 정리 범위, 운영 안내.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A (권장) | 검사 스위치·방식·항목 변경은 지정 품질 부서장 전용으로 서버가 강제하고 **시스템 관리자의 쓰기는 차단**(조회와 부서장 지정·해제는 관리자 유지). 기존 구분 관리 화면의 `IQC 필요` 토글은 새 설정으로 대체하거나 같은 권한 규칙으로 정리해 우회 경로를 없앰 | 답변 5의 원칙이 관행이 아니라 서버 계약으로 보장되고, 같은 값의 편집 경로가 하나의 권한 규칙으로 통일됨 | 부서장 부재·이석 시 관리자가 대신 설정을 바꿔줄 수 없어 반드시 부서장 지정을 거쳐야 함 |
| B | 관리자 쓰기 허용을 현행대로 유지하고 "관리자는 관여하지 않는다"는 운영 관행으로만 지킴 | 비상시 관리자가 대신 처리 가능하고 코드 변경이 가장 작음 | 답변 5의 원칙이 시스템으로 보장되지 않아 관리자 실수로 현장 설정이 바뀔 수 있음 |

권장안은 A다. 참고로 Change 004에서 확정된 Item별 LQC 운영 상태의 "시스템 관리자 전용" 계약은 이번 작업의 제외 범위(Change 004 재작업 제외)에 따라 이번에는 변경하지 않는다. 답변 5의 원칙을 LQC에도 적용하길 원하면 별도 Change로 지시가 필요하다.

### 질문 3 — 상세형 스위치와 빈 양식의 관계를 어떻게 처리하는가

**필요한 이유**: 답변 4는 "구매품 입력 시점에 검사 양식이 있고 검사 스위치가 켜져 있는 경우에만 IQC를 띄운다"고 확정했다. 스캔형은 체크리스트가 없는 방식이므로 스위치만으로 유효한 반면, 상세형은 검사 항목이 0개인 상태가 존재할 수 있다. 이 경계 상황의 규칙에 따라 양식 저장 validation과 구매품 저장 snapshot 설계가 달라진다.

**답변이 바꾸는 범위**: 구분별 양식 저장·스위치 전환 validation, 구매품 저장 시 snapshot 판정 조건, 구매 화면의 안내·경고 표시, 검증 시나리오.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A (권장) | 상세형은 검사 항목이 1개 이상 저장된 뒤에만 스위치를 켤 수 있고, 상세형이 켜져 있는 동안 항목 0개 저장을 차단. 스캔형은 항목 없이 스위치만으로 유효. 구매품 저장 시점에는 "스위치 on + 방식"만 확인하면 됨 | "검사하기로 한 구분인데 양식이 비어 있어 소리 없이 무검사로 입고"되는 상황이 구조적으로 불가능하고 구매 시점 판정이 단순해짐 | 검사 항목을 준비하기 전에는 스위치를 미리 켜 둘 수 없음 |
| B | 스위치와 양식을 독립으로 두고, 구매품 저장 시점에 상세형인데 항목이 0개면 그 구매품을 검사 없음으로 snapshot하고 화면에 경고만 표시 | 답변 4의 문구를 문자 그대로 구현하고 스위치를 먼저 켜 두는 운영이 가능 | 부서장이 스위치를 켰다고 믿는 동안 양식 미완성 구분의 구매품이 계속 검사 없이 저장될 수 있음 |

권장안은 A다. 두 선택지 모두 이미 저장된 구매품 비소급과 스위치 off = 검사 없음 규칙은 동일하다.

### 질문 4 — 상세형 검사 항목 내용은 어느 시점의 양식으로 고정하는가

**필요한 이유**: 답변 4로 검사 여부·방식이 구매품 저장 시점에 고정되는 것은 확정됐다. 그런데 "이미 저장된 구매품에는 새 설정이 적용되지 않는다"가 검사 항목 내용까지 포함하는지는 두 해석이 가능하다. 구매품 저장 후 도착 전에 부서장이 항목을 보완하면 그 도착분 검사에 반영되는지에 따라 snapshot 구조가 달라진다.

**답변이 바꾸는 범위**: 구매품·검사 회차의 양식 version snapshot 설계, "양식을 고치면 언제부터 반영되는가" 운영 안내, 재검사·회귀 검증 시나리오.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A (권장) | 검사 여부·방식은 구매품 저장 시점 고정, **검사 항목 내용은 도착분 검사 회차를 시작하는 시점의 해당 구분 현재 양식**으로 고정하고 확정 후 불변 | 기존 상세검사·재검사 계약과 동일한 구조라 변경이 최소이고, 양식 오류·보완이 이후 도착분부터 자연스럽게 반영됨 | 같은 구매품의 도착분끼리 검사 항목이 다를 수 있어 회차별 양식 version 표시가 필요 |
| B | 구매품 저장 시점의 양식 version까지 구매품에 완전 고정 | 구매 저장 시 확인한 항목 그대로 모든 도착분이 검사됨 | 발주~도착 사이 항목 보완이 반영되지 않고, 잘못된 양식이면 구매품을 다시 저장하기 전까지 모든 도착분이 옛 항목으로 검사되며, 기존 검사 계약과 다른 새 snapshot 구조가 필요함 |

권장안은 A다. 잘못된 설정은 과거를 고치지 않고 이후 적용분부터 보정한다는 기존 복구 원칙과 일치한다.
