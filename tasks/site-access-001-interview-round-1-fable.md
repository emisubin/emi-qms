# TASK-SITE-ACCESS-001 — Deep Interview Round 1 (Fable 5)

- taskType: `NEW_FEATURE`

Repository 기준선 확인: 현재 감사 원장은 대화형 Redirect/Popup `LOGIN_SUCCESS`와 명시적 `Logout`만 기록하고, 기존 인증 세션으로 복원된 접속·silent token 갱신은 의도적으로 제외한다. 로그인 사건에만 IP·브라우저·OS 계열을 저장하고, 서버는 client interaction ID 기반 idempotent append로 중복을 막으며, 관리자 `전체 감사 이력` 화면이 `Audit.Read.All`로 조회·필터·상세·선택 Excel을 제공한다. 아래 5개 질문은 모두 이 신규 기능의 blocking 결정 1번(접속 세션 시작·중복 방지·종료/만료·표시·실패 처리)을 확정하기 위한 서로 연결된 질문이다.

### 질문 1 — 한 번의 "사이트 접속"을 어떤 단위로 셀까요?

- 필요한 이유: 새로고침·다중 탭·자동 token 갱신이 접속 이력을 과다 생성하지 않아야 하므로, 접속 1건의 경계를 먼저 확정해야 서버 dedup 규칙과 화면 의미가 정해집니다.
- 답변이 바꾸는 범위: 접속 세션 데이터 개념, 서버 중복 방지 규칙, migration schema, 관리자 화면의 접속 건수 의미 전체.
- 선택지:
  - A. 브라우저 단위: 한 브라우저에서 앱을 처음 열 때 1건을 만들고, 그 브라우저를 닫기 전까지는 며칠이 지나도 같은 접속으로 유지합니다. 장점: 기록 수가 가장 적음. 단점: 브라우저를 계속 켜 두는 사용 패턴에서는 "언제 실제로 사용했는지"가 다시 사라져 이번 기능의 목적에 미달합니다.
  - B. 활동 시간 창 단위: 마지막 활동 이후 일정 시간(만료 기준, 질문 3)이 지난 뒤 다시 PMS를 사용하면 새 접속 세션으로 기록합니다. 새로고침·다중 탭·token 갱신은 같은 활동 창 안에서 하나의 세션으로 묶습니다. 장점: 브라우저를 켜 둔 채 매일 쓰는 패턴에서도 날짜별 실제 사용을 확인할 수 있고 일반 웹 세션 개념과 일치. 단점: A보다 기록 수가 많습니다.
  - C. 하루 최초 1건 단위: 사용자별로 하루 첫 사용만 기록합니다. 장점: 가장 단순. 단점: 하루 안의 시작·종료·재접속을 구분할 수 없습니다.
- 권장안: B. 유지 세션 사용자의 "실제 접속 시각" 확인이라는 요청 목적에 맞고, 기존 login append처럼 서버가 사용자·세션 영수증 기준으로 중복을 확정 거절할 수 있습니다.

### 질문 2 — "최근 활동"은 어떻게 남길까요? (append-only 원칙과의 관계)

- 필요한 이유: 기존 감사 원장은 append-only인데, 접속 세션의 최근 활동 시각은 갱신되는 값입니다. 갱신을 허용할 범위를 정해야 schema와 보존 정책이 확정됩니다.
- 답변이 바꾸는 범위: 접속 세션 저장 방식(갱신 가능 필드 vs event append), 저장량, 상세 화면 표시.
- 선택지:
  - A. 접속 세션 row의 최근 활동 시각만 서버가 낮은 빈도(예: 최소 5분 간격)로 갱신합니다. 별도 클라이언트 ping 없이 인증된 API 요청 처리 중에 갱신합니다. 장점: 저장량이 작고 기존 업무 감사 사건의 append-only는 그대로 유지되며, 갱신 예외를 "접속 세션의 최근 활동·종료 상태 필드"로만 한정할 수 있습니다. 단점: 순수 append-only의 좁은 예외가 생깁니다.
  - B. 활동 갱신마다 별도 사건을 append합니다. 장점: 순수 append-only. 단점: 저장량이 크게 늘고 관리자 화면에 잡음이 많아집니다.
  - C. 시작만 기록하고 최근 활동은 남기지 않습니다. 장점: 가장 단순. 단점: "언제까지 사용했는지"를 알 수 없어 성공 기준에 미달합니다.
- 권장안: A. 비밀·raw 값을 다루지 않는 시각 필드 갱신만 허용하면 개인정보 최소화와 저장 효율을 함께 지킬 수 있습니다.

### 질문 3 — 명시적 종료가 없을 때 접속 세션은 언제 "만료"로 볼까요?

- 필요한 이유: 네트워크 단절·브라우저 강제 종료처럼 로그아웃 없이 끝나는 경우가 일반적이므로, 만료 기준이 없으면 세션이 영원히 "사용 중"으로 남습니다.
- 답변이 바꾸는 범위: 세션 종료 상태 모델, 질문 1-B의 새 세션 분리 기준, 관리자 화면의 상태 표시.
- 선택지:
  - A. 명시적 로그아웃은 "종료"로 확정하고, 그 외에는 "마지막 활동 + 30분 경과"를 만료로 취급합니다. 만료는 별도 쓰기 없이 조회 시 계산하거나 다음 접속 때 확정합니다. 장점: 클라이언트 신호에 의존하지 않아 강제 종료·단절에도 안전하고 쓰기가 적습니다. 단점: 30분은 근사치이며 실제 창 닫은 시각과 다를 수 있습니다.
  - B. A와 같지만 만료 기준을 더 길게(예: 2시간) 잡습니다. 장점: 점심시간 등 잠깐 자리를 비운 경우도 한 세션으로 묶임. 단점: 하루 중 재접속 구분이 흐려집니다.
  - C. 탭을 닫을 때 클라이언트가 종료 신호를 보냅니다. 장점: 종료 시각이 정확할 때가 있음. 단점: 강제 종료·네트워크 단절에서 신호가 유실되어 결국 만료 기준이 또 필요하고, 과다 종료 이벤트가 생깁니다.
- 권장안: A(30분). 일반 웹 세션 관행과 일치하고 서버 단독으로 확정할 수 있습니다. 30분이 업무 패턴과 맞지 않으면 숫자만 알려주시면 됩니다.

### 질문 4 — 관리자 화면 표시와 IP·기기 요약 저장 범위는 어떻게 할까요?

- 필요한 이유: 접속 사건을 기존 `전체 감사 이력`에 통합할지, 로그인 사건과 같은 수준의 IP·브라우저·OS 계열을 저장할지에 따라 화면·Excel·개인정보 범위가 정해집니다.
- 답변이 바꾸는 범위: 관리자 UX(필터·상세·선택 Excel), 저장 필드, 승인 대기·비활성 사용자 표시.
- 선택지:
  - A. 기존 `관리자 → 운영 → 전체 감사 이력`에 새 사건 종류 `사이트 접속`을 추가하고, 상세에서 시작·최근 활동·종료/만료를 보여주며, 로그인 사건과 동일하게 IP·브라우저·OS 계열을 저장하고, 앱 접근 결과(허용/승인 대기/비활성)를 구분 표시하고, 선택 Excel에 포함합니다. 장점: 기존 화면·권한(`Audit.Read.All`)·Excel 재사용, 로그인과 접속을 한 화면에서 대조 가능. 단점: 사건 종류가 하나 늘어 화면 정보량이 증가합니다.
  - B. 별도 "사이트 접속 이력" 화면을 새로 만듭니다. 장점: 화면 단순. 단점: 메뉴·권한·Excel 로직이 중복되고 로그인과의 대조가 불편합니다.
  - C. A와 같지만 IP는 저장하지 않고 브라우저·OS 계열만 저장합니다. 장점: 개인정보 최소화 강화. 단점: 기존 로그인 사건과 정보 수준이 어긋나 대조 가치가 줄어듭니다.
- 권장안: A. 기존 로그인 사건의 저장 원칙과 화면 계약을 그대로 확장하는 것이 일관되고 구현 재사용이 큽니다.

### 질문 5 — 접속 기록이 실패하면 업무 사용을 막아야 하나요?

- 필요한 이유: 접속 계측 쓰기가 일시 실패할 수 있으므로, 감사 완전성과 서비스 가용성 중 우선순위를 확정해야 합니다.
- 답변이 바꾸는 범위: 접속 기록 API의 실패 처리, 사용자 체감 동작, 운영 대응 절차.
- 선택지:
  - A. best-effort: 기록에 실패해도 사용자는 PMS를 계속 사용할 수 있고, 실패는 서버 오류 로그로 관찰해 forward-fix합니다. 기존 대화형 로그인 기록과 동일한 정책입니다. 장점: 가용성 보존, 기존 정책과 일관. 단점: 드물게 접속 1건이 누락될 수 있습니다.
  - B. 기록 실패 시 접속을 차단합니다. 장점: 이력 완전성 보장. 단점: 감사 저장소 장애가 전 사용자 업무 중단으로 번집니다.
- 권장안: A. 이 기능은 통제 차단 장치가 아니라 가시성 확보가 목적이므로 기존 로그인 기록과 같은 best-effort가 적합합니다.
