## 1. 결론

Fable 기획안의 제품 형태는 유지할 가치가 충분하다. 사내 시범 운영 단계에서 별도 동의 화면이나 약관 체계를 크게 만드는 대신, 로그인 후 상시 열람할 수 있는 정적 단일 `개인정보·이용 안내` 페이지를 두고 현재 제공 중인 처리와 채널만 정확히 알리는 접근은 범위와 운영 부담의 균형이 좋다.

다만 현재 안은 **화면 구조를 구현하기에는 충분하지만, 실제 처리방침 문안을 게시하기에는 회사 사실관계가 부족하다.** 구현 승인 전까지 다음 다섯 가지를 회사 기준으로 확정해야 한다.

1. 개인정보를 처리하는 법인명과 문안 승인·게시 책임 부서
2. 개인정보 문의 담당 부서와 공용 업무 연락처
3. 데이터 유형별 처리 목적·근거·보유기간과 시범 운영 종료 시 삭제·보존 기준
4. Microsoft Entra ID·Azure·Teams/Graph·메일·DB·파일 저장소의 위탁, 제3자 제공과 국외 이전 해당 여부
5. 현재 선택 동의 대상이 0건이라는 회사·개인정보 책임자 확인

따라서 이번 기획 작성 단계는 `GO`이지만, 제품 구현·운영 게시는 `NO_GO`다. 위 사실관계와 사용자 기획 승인이 모두 채워진 뒤 별도 구현 세션에서 시작해야 한다.

## 2. 사용자 문제와 제품 방향 검토

### 해결하는 문제

- 실제 임직원 계정, 역할·부서, 업무 기록, 사진·첨부와 알림 이력을 처리하면서도 사용자가 처리 기준과 권리 행사 창구를 상시 확인할 화면이 없는 공백을 해소한다.
- 공지와 설치 팝업에만 정보를 흩어 두지 않고, 시행일과 변경 이력이 있는 하나의 기준 화면을 만든다.
- 아직 제공하지 않는 OS Web Push를 현재 기능처럼 오해하게 하지 않으면서 향후 도입 가능성만 설치 안내에서 알린다.

### Roadmap 정합성

- 기존 Azure 시범 운영, NoticeBoard와 PWA 설치 경험을 재사용하고 이들을 다시 구현하지 않는다.
- Backend·DB·migration·권한·provider를 변경하지 않아 현재 운영 기반의 불변조건을 보존한다.
- Web Push, 앱 내 문안 버전 관리와 권리 행사 접수 기능은 독립된 신규 능력이므로 후속 Task로 분리하는 것이 맞다.

### 추가

#### A. 문안 작성 전 실제 처리 목록

처리방침의 `처리 목적·항목·근거·보유기간`은 일반 문구가 아니라 아래 실제 기능 단위로 대조해야 한다.

- Microsoft 365/Entra 계정 식별자, 이름, 업무 이메일, 부서와 역할
- 프로필 사진
- 프로젝트·업무·검수·상태 변경 및 감사 이력
- 업로드 사진·파일과 그 메타데이터
- 알림 설정, 발송·전달 결과와 수신 이력
- 로그인·접근·보안 로그
- 인증 세션, MSAL cache와 브라우저 local/session storage

각 항목에 `누가/왜 처리하는지`, `필수 업무 근거인지 또는 동의 대상인지`, `언제 삭제하는지`를 붙여야 한다. 코드에 데이터가 있다는 사실만으로 법적 근거나 보유기간을 추정해서는 안 된다.

#### B. 외부 처리 흐름 대조표

Microsoft Entra ID, Azure 호스팅·DB·파일 저장소, Teams/Graph 알림과 메일 발송의 실제 계약·tenant·region·수신자 흐름을 확인해야 한다. 각 흐름을 다음 중 하나로 분류하고 문안에 사실대로 반영한다.

- 개인정보 처리업무 위탁
- 제3자 제공
- 국외 이전
- 해당 없음

Repository 설정만으로 계약상 지위와 실제 저장 지역을 단정하지 않는다. 회사 계약·운영 자료가 최종 근거다.

#### C. 시범 운영 종료 기준

`시범 운영 종료` 자체를 일괄 삭제 시점으로 쓰지 말고 데이터별 기준을 나눈다.

- 서비스 계속 운영 시 승계되는 계정·업무 데이터
- 시범 종료 후 삭제할 시험 데이터와 첨부
- 법적 의무·분쟁 대응·감사를 위해 제한적으로 보존할 기록
- backup에서의 삭제 또는 만료 시점

#### D. 권리 행사 문구의 운영 가능성

열람·정정·삭제·처리정지의 접수 방법, 실제 담당 부서와 적용 가능한 처리 기한을 회사 절차와 맞춘다. 법률상 기한이나 예외를 기획자가 임의 숫자로 정하지 않는다.

#### E. 화면·운영 세부 계약

- URL deep-link와 브라우저 뒤로가기가 기존 `View` 전환 규칙대로 동작해야 한다.
- 세 진입점은 동일한 route와 공통 label을 사용해 경로가 어긋나지 않게 한다.
- 긴 표는 390px와 Teams narrow pane에서 카드 또는 내부 가로 스크롤 중 하나로 명시한다.
- anchor 이동 뒤 keyboard focus를 section heading으로 옮긴다.
- PWA 안내는 알림 권한 허용이 현재 설치 필수조건인 것처럼 쓰지 않는다.
- 변경 이력에는 시행일, 변경 요약과 현재 적용 여부를 표시한다. 과거 전문은 Git에 남지만 사용자가 앱에서 전문을 조회할 수 있다는 인상은 주지 않는다.

## 4. Repository 대조 결과

### 구현 가능성이 높은 부분

- `frontend/src/App.tsx`의 기존 `View`·path 매핑 패턴으로 새 조회 화면과 deep-link를 연결할 수 있다.
- `AccountProfilePanel`, 데스크톱 사이드바 footer와 모바일 메뉴 footer에 동일 route 진입점을 둘 수 있다.
- `frontend/src/PwaInstallExperience.tsx`에 안내 문구를 추가하고 기존 PWA test를 갱신할 수 있다.
- `frontend/src/NotificationPreferencesPage.tsx`가 현재 알림 채널의 사실 기준선 역할을 할 수 있다.
- 신규 API나 DB 모델 없이 별도 페이지 component와 Frontend test만으로 구현할 수 있다.

### 계획과 실제 코드의 차이

- 공지 상세 본문은 현재 문자열 렌더링이며 안내 페이지로 이동하는 내부 링크 기능이 확인되지 않는다. 최초 공지는 링크 대신 진입 경로를 설명하는 것으로 충분하다.
- 앱은 MSAL cache와 PWA dialog의 session storage를 사용한다. 처리방침의 처리 기술 목록에서 인증·세션과 클라이언트 저장을 빠뜨리면 안 된다.
- 프로필 사진, 업무·감사 이력, 첨부와 알림 이력이 존재하므로 단순한 `계정 정보` 수준의 문안은 실제 처리 범위를 충분히 설명하지 못한다.

## 5. 우선순위와 권장 개발 순서

1. **회사 사실관계 확정** — 법인명, 승인 책임, 담당 부서·공용 연락처, 데이터별 목적·근거·보유기간, 외부 처리 흐름과 시범 종료 정책을 확인한다.
2. **문안 원본 승인** — 실제 처리 목록을 기준으로 개인정보 처리방침·권리 행사 안내·이용수칙·시행일·변경 이력을 회사가 승인한다.
3. **정적 조회 화면 구현** — 신규 route/component, 목차·anchor, 뒤로가기와 세 진입점을 구현한다.
4. **PWA 안내 문구 수정** — 현재 채널과 “모바일 푸시 준비 중”을 구분해 표시한다.
5. **자동·접근성 검증** — lint, typecheck, unit test, build, desktop·390px·Teams narrow pane, keyboard·heading·focus를 확인한다.
6. **운영 콘텐츠 준비** — 최초 공지, 개정·정정·rollback SOP와 게시 전 checklist를 준비한다.
7. **사용자 검수 및 별도 게시 승인** — 문안과 화면 검수를 분리 기록한 뒤 기존 release 절차로 진행한다.

1~2번이 끝나기 전에 제품 문안을 placeholder로 구현하거나 게시하지 않는다. 단, 레이아웃 prototype이 별도 승인되면 실제 연락처나 보유기간 없이 synthetic 문안으로만 검증할 수 있다.

| PRIV-PLAN-005 | P2 | OPEN | 코드 기반 데이터 목록과 실제 처리방침 문안 사이의 추적표가 없다. | 구현 change에 항목·목적·근거·보유기간·외부 흐름 매핑을 privacy-safe 형태로 추가한다. |

P1 Finding이 열려 있으므로 구현 완료나 운영 게시를 선언할 수 없다. 이는 기획 비교·검토 산출물의 완료를 막지는 않지만, 후속 구현 승인 gate를 차단한다.

## 7. 사용자 결정 권고

### 지금 채택 권고

- Fable 후보 A: 정적 단일 페이지 + 기존 진입점 재사용
- 권리 행사는 안내만 제공
- 처리방침과 이용수칙은 한 페이지 안에서 구분
- 현재 알림 채널만 처리방침에 반영
- “모바일 푸시 준비 중”은 PWA 설치 안내·공지에만 반영
- 공용 업무 연락처는 제품 문안에 직접 기재
- Backend·DB·migration·provider 변경 없음

### 구현 승인 전에 받을 입력

- 6절 `PRIV-PLAN-001`, `PRIV-PLAN-004`, `PRIV-PLAN-005`의 resolution
- 개인정보 처리방침 문안의 회사 승인본
- Frontend-only 변경 allowlist와 검증·게시 경계에 대한 사용자 승인

## 8. 법적 기준과 기획 해석

- 개인정보보호법 제30조는 개인정보 처리방침의 수립·공개와 주요 기재사항을 요구한다. 담당자는 개인 실명·개인 연락처를 반드시 공개해야 한다는 의미가 아니며, 실제 책임 체계와 연결되는 담당 부서·공용 업무 창구를 정확히 안내하는 안이 이 제품에는 적합하다.
- 시범 운영이나 사내 한정이라는 이유만으로 실제 임직원 개인정보 처리에 대한 고지 의무가 자동으로 사라지는 것으로 기획하지 않는다.
- 동의는 모든 처리의 공통 전제가 아니므로, 현재 처리의 적법한 근거를 먼저 구분하고 동의가 필요한 선택 처리만 별도로 설계한다.
- 처리위탁, 제3자 제공과 국외 이전은 서로 다른 법적·운영 개념이므로 provider 이름만 보고 하나로 묶지 않는다.
