### Figma 100% 동일 구현·검수 기준

- 사용자 “피그마 디자인은 100% 똑같이 구현해야해”를 수락한다. 지정 frame의 레이아웃·간격·크기·색·서체·아이콘·원본 이미지·테두리·그림자·버튼·선택창·팝업을 임의로 재해석하거나 유사 디자인으로 대체하지 않는다.
- 합의된 예외만 적용한다: 오산의 제조 화면 명칭은 `진행 현황`, 단계는 입고검사 → 배치검사 → 배선검사 → 8계통 → 동작검사 → 출하검사 → 포장, 작업 중단·펜딩 버튼/팝업/집계는 제외한다. 공통 로그인은 청주·오산에 동일 적용한다.
- 구현 시작 시 frame/node·확인 시점·원본 자산·실제 디자인 치수와 상태를 고정한다. 같은 화면 폭·상태·샘플 데이터 조건에서 Figma와 실행 화면을 나란히 비교하고 overlay 또는 이미지 차이 검사를 보조로 사용한다. 직접 육안 확인하고 미해결 차이가 있으면 100% 일치 완료로 보고하지 않는다.
- PC 로그인 기준은 1440×810. 모바일은 해당 frame 원본 치수를 확보하고 대표 실제 모바일 폭에서도 잘림·스크롤·터치 동작을 확인한다. 캡처 한 장 또는 코드 테스트만으로 동일성을 판정하지 않는다.
- Figma에 없는 오류·빈 목록·저장 중 상태는 기존 디자인 구성으로 최소 보완한다. 지정 화면 자체의 재설계, 추가 메뉴·알림 기능·사업부 선택 페이지는 범위에 넣지 않는다.

### 기능 분할과 남은 설계 입력

- 기존 진행·현황 Task는 미구현 제품 업무를 이어가며 새 ID로 복제하지 않는다. 사진은 독립적인 등록·보존·조회 능력이므로 PHOTO-001로 분리한다. 공통 로그인은 기존 DESIGN-LOGIN-001을 재사용한다.
- 사진 선택 첨부·여러 장 허용·일괄 대상에 동일 사진 적용 안내·첫 버전 저장 후 조회 중심이라는 직전 권장안은 계획 기본안으로 이어간다. 구체적인 장수/용량, 저장 구조와 일괄 대상 조회 표현은 PHOTO-001에서 확정하고 추적한다.
- 단계 안내 사진과 완료 증빙 사진을 구분한다. 기존 양식의 안내 사진·설명을 사용할 수 있는지 PROGRESS-001에서 대조하며, 등록/편집 능력이 부족하면 그 차이만 설계한다. Figma의 예시 조립 이름을 오산 7단계 대신 사용하지 않는다.
- 전체 실행 순서는 Roadmap 한 곳에서 관리한다. 현재 Task 분할·문서 검토 완료와 제품 구현·자동 검증·사용자 검수·원격 반영·배포를 구분한다.

아래 세 항목은 최초 등록 당시의 요청·승인·기준선이며 현재 디자인 제공 상태를 뜻하지 않는다.

- 상위 목적: 오산 시범 운영 후속 개발. 이번 승인은 Task 등록·개발 순서 조정이며, 아직 제공되지 않은 디자인이나 신규 업무 기능을 확정한 것은 아니다.
- 기준: `b099296`의 하네스 v2, 현재 branch 유지. Task/문서·branch·관련 PR 검색에서 같은 목적의 별도 Figma Task는 확인되지 않아 새 ID로 등록한다. 기존 제품·runner WIP는 변경하지 않는다.

## 목표와 적용 범위

사용자가 지정한 Figma 화면과 동작을 오산 UI/UX의 기준으로 삼고, 현재 제품·승인된 진행/현황 기획과 비교해 필요한 기능 변경까지 개발 범위에 연결한다. 화면 꾸미기만의 Task로 제한하지 않는다.

- 디자인 출처: 위 지정 디자인 표가 현재 출처다. 완료 후 node와 일부 모바일 치수는 아래 재개 관찰에 확보했다. 나머지 치수·자산·상태별 상세 속성은 추가 확보한다.
- 적용 화면: 사용자가 지정한 범위. 기존 프로젝트 생성·목록·상세 또는 후속 진행 관리·현황판을 모두 자동 재설계하지 않는다.
- 지정된 오산 화면은 Figma를 우선하고, 이전의 “청주 UI 그대로” 요구는 그 화면의 디자인 기준에서 대체한다. 미지정 영역은 기존 UI/UX를 유지한다. 재사용 가능한 공통 component와 권한·데이터 계약은 보존한다.
- 화면의 버튼·입력·상태·이동에서 필요한 기능을 추출하고 실제 API·데이터·권한·업무 흐름과 대조한다. 그림에 나타난 새 권한·상태·삭제/정정 기능을 자동 승인된 정책으로 해석하지 않는다.

## 진행과 기존 Task 연결

1. 제공된 frame과 동작 설명을 확인하고 화면·상태·사용자 행동별로 현재 기능과 차이를 정리한다. 실제 결과를 바꾸는 미결정만 질문한다.
2. 차이를 **UI 변경 / 기존 기능 보정 / 새 기능 / 결정 필요**로 나누고 필요한 서버·DB·권한 변경과 검증을 함께 제시한다.
3. 진행 기록·포장 자동 완료는 `TASK-OSAN-PROGRESS-001`, 현황 집계·검색은 `TASK-OSAN-DASHBOARD-001`의 같은 목적 범위에 반영한다. 생성·목록·상세 변경은 기존 `TASK-OSAN-PROJECT-001`의 후속 change로 연결한다.
4. 독립적인 새 업무 능력이 확인됐을 때만 별도 기능 Task를 추가하고 의존성·완료 조건을 지정한다. 이 Task와 기능 Task에서 같은 구현을 중복 수행하지 않는다.
5. 범위가 정해진 화면·기능부터 구현한다. 디자인에 의존하지 않는 조사·기준선 준비는 계속할 수 있으며, Figma 미지정을 오산 전체 작업의 일괄 중단 사유로 사용하지 않는다.

이미 충분히 지정·승인한 내용은 반복 확인하지 않는다. 최종 제품 구현·검증은 [새 하네스](../AGENTS.md)를 따르며 별도 고정 인터뷰·모델 사슬을 추가하지 않는다.

## 보존할 계약과 확인 방법

- 기존 실입력 프로젝트·수량 대상·진행 이력, Directory/청주/오산 DB 분리와 서버 권한을 보존한다.
- 7단계·포장 선행조건·전체 대상 포장 후 자동 완료·중단/펜딩 제외는 현재 업무 계약이다. 디자인에서 변경이 필요해지면 달라지는 계약만 명시해 결정한다.
- 구현 시 같은 상태·데이터 형태·화면 폭에서 Figma와 실제 화면을 직접 비교한다. 필요한 desktop/mobile, loading/empty/error/저장·전환 동작을 확인한다.
- 기능 변경은 해당 Task에서 성공·실패·권한·동시성 반례를 검증한다. 최종 통합과 청주 회귀는 `TASK-OSAN-VALIDATION-001`로 연결하고 동일 전체 테스트를 반복하지 않는다.
