### 질문 1 — 개인정보 처리방침·이용수칙 문안을 정적 페이지로 배포할까요, 앱 안에서 버전 관리할까요

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 정적 문안 페이지 | 문안을 Frontend 코드에 포함하고 시행일·변경 이력을 문서 안에 표기. 수정은 코드 변경·배포로 처리 | migration·DB 변경 없음(이번 Task 제외 범위와 일치). 이전 검증된 Frontend revision으로 즉시 rollback 가능. 가장 빠름 | 문안 수정마다 배포 필요. 게시 권한이 개발 흐름에 묶임 |

### 질문 2 — 개인정보 권리 행사(열람·정정·삭제·처리정지)는 접수 경로 안내까지만 할까요, 앱 안에서 접수·처리 추적까지 만들까요

- **답변이 바꾸는 범위**: 신규 데이터 모델·알림·권한 설계 유무, 접수 성공·실패·처리 상태 UX 유무, 담당자 운영 절차 설계 깊이.

| 선택지 | 내용 | 장점 | 단점 |

### 질문 3 — 현재 처리 항목 중 "동의"를 받을 선택 항목이 실제로 있나요, 아니면 전부 필수 업무 처리로 고지만 할까요

- **참고 기준선**: 현재 앱이 처리하는 항목(계정·부서·역할, 프로필 사진, 업무 이력, 업로드 사진, 알림 이력)은 모두 업무 수행 근거로 처리되고 있고, Teams·메일 알림 켜고 끄기는 이미 "사용자 설정"으로 제공된다. 설정(preference)과 법적 동의(consent)는 다른 개념이다.

### 질문 4 — PWA 설치 안내와 공지의 알림 문구를 어떻게 표현할까요

- **필요한 이유**: 준비 중인 공지·팝업 문구가 "모바일 설치 후 알림을 받을 수 있다"로 나가면, 현재 미구현인 OS 푸시 알림으로 오해될 수 있다. 현재 설치 dialog 코드에는 알림 문구가 없으므로, 추가할 문구의 표현 원칙을 지금 정해야 정책 페이지·공지·팝업이 일관된다.
- **답변이 바꾸는 범위**: 설치 안내 dialog·공지 문구, 처리방침의 알림 채널 기술, Web Push 후속 Task와의 문구 연결 방식.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 현재 채널만 정확히 표현 | "알림은 앱 내 알림함과 Teams·메일로 제공됩니다. 설치하면 홈 화면에서 바로 확인할 수 있습니다"처럼 실제 제공 채널만 기술 | 사실과 일치. 사용자 혼선·운영 위험 없음. Web Push 출시 때 문구만 갱신 | 설치 유인이 "바로 열기" 중심으로 다소 약해짐 |
| B. 후속 예고 포함 | A에 "모바일 푸시 알림은 준비 중" 예고 추가 | 설치 유인 강화 | 일정 미확정 기능의 예고가 부담이 됨. 지연 시 신뢰 저하 |

### 질문 5 — 정책 페이지 진입점은 어디에 둘까요, 그리고 로그인 전에도 볼 수 있어야 하나요

- **필요한 이유**: 현재 앱은 전 화면이 Microsoft 365 로그인 뒤에만 열린다. 로그인 화면에서도 처리방침을 볼 수 있게 하려면 미인증 공개 route라는 새 인증 경계가 필요해 구현 범위와 검증 항목이 달라진다. 로그인 후 진입점 위치(계정 메뉴·공통 footer·홈 공지 링크)도 화면 설계의 전제다.
- **답변이 바꾸는 범위**: 미인증 공개 route 신설 여부(인증 불변조건 영향), 진입점 배치와 390px·Teams narrow 검증 범위, 공지·설치 팝업에서의 링크 연결.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 로그인 후 전용 | 계정 메뉴 + 공통 상시 진입점(예: 메뉴 하단)에서 접근. 로그인 화면은 변경하지 않음 | 기존 인증 경계 무변경(이 Task 불변조건과 일치). 대상이 사내 사용자뿐이라 충분할 수 있음 | 로그인 전(계정 승인 대기 포함) 사용자는 문안을 볼 수 없음 |
| B. 로그인 화면에도 링크 | 처리방침·이용수칙을 미인증 공개 route로 두고 로그인 화면에 링크 | 로그인 시점(개인정보 수집 시작 시점)에 고지 가능 | 미인증 공개 route 신설로 인증 경계 검토·검증 필요 |
