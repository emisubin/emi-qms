## 범위와 선행조건

PROGRESS-001의 프로젝트·수량 대상·7단계 식별과 완료 계약을 선행조건으로 한다. 사진 저장 설계는 진행 구현과 함께 준비할 수 있지만 전체 완료 흐름 연결은 그 계약을 기준으로 한다.

1. 완료 팝업에서 모바일 카메라 촬영 또는 기존 이미지 선택, 저장 전 미리보기와 잘못 고른 사진 제거/재선택.
2. 사진 데이터와 프로젝트·대상·단계·등록자·등록 시각을 연결하여 영구 보존. 오산 DB에 연결 정보와 기록을 저장한다. 원본을 DB에 넣는 방식과 파일 저장소에 두는 방식은 기존 저장 구조·용량·백업 영향을 대조해 명시적으로 확정한다. 임시 미리보기 URL만 저장하고 영구 저장 완료라고 하지 않는다.
3. 완료 후 해당 대상·단계의 사진, 실제 작업자와 완료 일시 조회. 재접속·다른 기기에서도 동일 기록을 조회하고 다른 대상/단계의 사진이 섞이지 않게 한다.
4. 개별/전체 선택 완료와 연결한다. 일괄 적용 사진의 대상 범위를 저장 전 안내하고 사진과 각 대상의 연결을 보존한다.
5. 저장 중 중복 제출 방지, 실패 안내와 재시도. 선택한 사진 저장이 실패하면 성공/완료로 표시하지 않는다. 재시도·경쟁 요청이 사진이나 완료 이력을 중복 생성하지 않도록 한다.

### 권장안과 사용자 결정 대기

1. **원본 DB 보존:** 오산 DB 사진 테이블에 최종 업로드 bytes·MIME·크기·SHA-256·등록자·등록 시각을 저장한다. 프로젝트·대상·단계의 완료 기록에는 별도 연결을 둔다. 일괄 완료 사진은 bytes 한 벌에 대상별 연결을 생성해 대상 수만큼 원본을 복제하지 않는다. DB와 백업 크기는 사진 용량만큼 증가한다.
2. **제한 후보:** JPEG/PNG 5장, 장당 5MiB, 한 완료 요청 총 15MiB. 자동 축소는 하지 않는 안을 제안했다. HEIC 변환·압축은 원본 보존 의미와 기기 지원을 바꾸므로 별도 결정한다. 지원하지 않는 파일은 성공처럼 처리하지 않고 이유와 재선택 방법을 알린다.
3. **대안:** 별도 private 파일 저장소를 선택하면 DB에 object key와 연결 정보를 두며 파일 자체의 영구 보존·권한·백업/복구가 추가로 필요하다. 임시 업로드와 DB 확정 사이의 실패·미연결 파일도 처리해야 한다. DB만 백업해서 원본 보존이 끝나는 구조가 아니다.

2026-09-09 사용자에게 위 DB 원본 보존·제한·자동 축소 없음 안과 HEIC 필요 여부를 질문했다. 사용자는 장단점을 포함한 여러 옵션을 요청했으며 저장 방식·제한은 아직 선택하지 않았다.

비교할 선택지는 A) DB에 업로드 원본 보존, B) 정해진 규격으로 변환/축소한 이미지를 DB에 보존, C) private 파일 저장소에 이미지와 DB에 연결 기록 보존이다. B는 저장된 이미지가 업로드 원본과 달라지며 HEIC 지원은 실제 decoder·기기 검증이 선행돼야 한다. C도 원본/최적화 보존 정책은 별도로 선택해야 한다. DB 원본 방식이 현재 코드와 가장 가까운 권장안이나 신규 정책으로 확정하지 않는다.

### 진행 완료와의 연결 초안

- 카메라·앨범 선택 → 미리보기·재선택 → 선택 대상과 동일 사진 적용 범위 안내 → 최종 저장 요청 → 완료 기록·사진 조회. 사진을 고르지 않은 완료도 허용하는 기존 계획 기본안을 보존한다.
- Figma `53:54`의 회색 `촬영`은 카메라 입력, 회색 `업로드`는 기존 파일 선택, 하단 빨간 `업로드`는 최종 제출로 연결하는 안이다. 버튼의 원본 문구를 임의 변경하지 않는다. 사진 선택 없이도 진행 완료 가능한 안내와 여러 장/실패 상태의 세부 배치는 아직 Figma 보완 설계 대상이다.
- DB 방식 채택 시 사진 저장·대상별 완료·마지막 포장에 따른 프로젝트 완료·audit/outbox를 동일 transaction에 넣는다. 어느 대상이든 권한·선행조건·version 검증에 실패하면 전체 rollback한다.
- 같은 operation ID와 같은 대상/단계/사진 hash 목록은 기존 성공 결과를 반환하고, 같은 ID의 다른 payload는 충돌로 처리한다. 사진이나 대상을 바꾸면 새 operation ID를 사용한다. 응답 유실 시 기존 ID 재시도 또는 재조회로 실제 결과를 확인한다.
- 선택 묶음의 사진·작업자·일시가 다르면 하나의 대표 기록처럼 표시하지 않는다. 대상별 완료 기록을 조회하고, 같은 사진을 공유하는 경우 적용 대상 연결을 유지한다. 구체적인 대상 전환·복수 사진 표시 위치는 원본 영역을 기준으로 별도 확정한다.
- 사진 bytes 조회에도 오산 사업부·프로젝트·대상 연결 권한을 서버에서 검사한다. 공개 URL을 제공하거나 다른 업무의 IQC 테이블/endpoint에 오산 사진을 억지로 넣지 않는다.
