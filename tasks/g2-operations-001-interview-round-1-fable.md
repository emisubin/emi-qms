## Round 1 기준선 확인

이번 질문은 interview 문서 2·3·4·5절의 미확정 항목과 Roadmap 6.4의 "역할·수정·보존·그래프 정책은 Fable interview에서 확정"을 채우기 위한 것이며, 다음 Repository 근거를 기준으로 작성했다.

- 확정된 범위: 기존 PMS 데이터와 연결하지 않는 독립 기능으로, 왼쪽 `G2` 부모 메뉴 아래 `홈`, `생산/출하 관리`, `제조 인원 출근 관리` 세 화면을 두고 홈에서 두 데이터 영역을 그래프와 표로 함께 표시한다(interview 5·6절, Roadmap Decision Log 2026-08-18).
- 권한 기준선: `docs/04-permission-matrix.md`의 공통 원칙은 "모든 활성 사내 사용자는 모든 부서 기능을 조회, 등록·수정은 담당 부서만, 모든 쓰기 API는 서버 권한 검사"이며, Role Code 문자열 비교 대신 Permission·Authorization Policy를 사용한다.
- Frontend 기준선: 좌측 navigation은 부서 단위 부모 메뉴와 하위 항목 구조이고 일부 메뉴(영업)는 권한에 따라 노출을 제한한다. 그래프는 외부 chart 라이브러리 없이 자체 SVG component(예: `frontend/src/SalesKpiChart.tsx`)로 구현돼 있으며, 데스크톱·모바일 공용 navigation과 390px page overflow 0 계약을 보존해야 한다.
- 달력 기준선: 시스템에 토·일·공휴일·회사휴일을 비영업일로 계산하는 기존 데이터가 있다. 다만 이 기능은 독립 기능이므로 비영업일 규칙을 적용할지 자체가 결정 대상이다.

### 질문 1 — 화면별 입력·정정 권한과 G2 메뉴 노출 범위

**필요한 이유**: interview 2절의 역할 표가 전부 미확정이다. 누가 생산·출하 수치를 입력하고 누가 출근 인원을 입력하는지, 그리고 누구에게 G2 메뉴와 홈을 보여줄지 정해야 서버 권한 정책(신규 Permission)과 메뉴 노출 규칙을 설계할 수 있다.

**답변이 바꾸는 범위**: 신규 Permission·Authorization Policy 구성, 좌측 메뉴 노출 조건, 화면별 읽기 전용/입력 가능 상태, 권한 자동 검증 시나리오.

| 선택지 | 내용 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A | 조회는 모든 활성 사내 사용자에게 허용하고, 쓰기는 화면별 담당 부서(예: 생산/출하 관리와 출근 관리 각각 지정한 부서)와 System Administrator에게만 신규 Permission으로 허용한다 | `docs/04` 공통 원칙(전체 조회·담당 부서 쓰기)과 완전히 일치하고 기존 권한 패턴을 그대로 재사용한다 | 어느 부서가 어느 화면의 담당인지 사용자가 지정해야 한다 |
| B | G2 전용 신규 권한을 만들어 관리자가 부서와 무관하게 사용자 개인 단위로 입력 권한을 부여한다 | 실제 담당자가 부서 경계와 다를 때 유연하다 | 부서 기반 권한 원칙과 다른 개인 부여 관리 화면·운영 부담이 새로 생긴다 |
| C | 모든 활성 사내 사용자가 입력·정정할 수 있게 한다 | 구현·운영이 가장 단순하다 | 잘못된 수정의 책임 추적이 어렵고 기존 "담당 부서만 쓰기" 원칙과 어긋난다 |

**권장안**: A. 기존 권한 모델과 가장 잘 맞는다. A를 선택하는 경우 두 가지를 함께 답해 달라. (1) `생산/출하 관리`의 입력 담당 부서(예: 생산관리 또는 제조), (2) `제조 인원 출근 관리`의 입력 담당 부서(예: 제조). 그리고 G2 메뉴 자체를 전체 사용자에게 보일지, 특정 부서에만 보일지도 알려 달라(권장: 조회 원칙에 맞춰 전체 노출).

### 질문 2 — 날짜별 기록 구조와 부분 입력·0 구분

**필요한 이유**: interview 3절의 validation·동시 처리 정책이 미확정이다. 하루에 오전 생산·오후 생산·출하 세 값과 출근 인원 한 값을 어떤 단위로 저장하고, 오전만 먼저 입력하는 부분 입력을 허용할지, "0"과 "아직 미입력"을 구분할지에 따라 데이터 모델과 저장 UX가 달라진다.

**답변이 바꾸는 범위**: 날짜별 레코드 schema(필드 nullable 여부), 저장 버튼·입력 폼 구성, 홈 그래프·표의 미입력 표시 방식, 서버 validation 규칙.

| 선택지 | 내용 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A | 날짜당 1개 레코드로 관리하되 필드별 부분 입력을 허용한다. 미입력은 빈 값으로 남기고 0과 구분해 표시한다 | 실제 업무 리듬(오전 마감 후 입력, 오후 마감 후 입력)과 맞고 0인 날과 안 적은 날을 구분할 수 있다 | 미입력 상태가 오래 남을 수 있어 홈에서 "미입력" 표시 규칙이 필요하다 |
| B | 하루 마감형으로 해당 날짜의 모든 값을 한 번에 입력해야 저장된다 | 데이터 완결성이 높고 화면·검증이 단순하다 | 오전 수치를 실시간으로 기록할 수 없고 하루가 끝나기 전에는 시스템에 아무 값도 없다 |

**권장안**: A. 오전·오후를 나눠 관리하겠다는 최초 요구 자체가 하루 중간 입력을 전제하므로 부분 입력 허용이 자연스럽다. 함께 답해 달라: 토·일·휴일에도 입력을 허용할지(권장: 차단하지 않고 모든 날짜 입력 허용, 그래프에서만 구분 없이 표시).

### 질문 3 — 정정 방식과 수정 이력 보존 수준

**필요한 이유**: interview 4절의 보존·감사 정책이 미확정이다. 이미 입력한 날짜의 숫자를 고칠 때 최종값만 남길지, 누가 언제 무엇을 바꿨는지 이력을 남길지에 따라 DB 구조와 화면이 달라지고 나중에 바꾸기 어려운 결정이다.

**답변이 바꾸는 범위**: 데이터 보존 schema(단일 행 갱신 vs 이력 테이블), 정정 UI, 관리 화면의 이력 조회 기능 유무, 자동 검증 범위.

| 선택지 | 내용 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A | 최종값만 저장하고 각 레코드에 마지막 수정자·수정 시각만 남긴다 | 독립 경량 기능이라는 방향과 맞고 구현·화면이 가장 단순하다. 이력이 필요해지면 나중에 additive로 추가할 수 있다 | 여러 번 정정된 경우 중간 값과 변경 사유를 되짚을 수 없다 |
| B | 값이 바뀔 때마다 변경 전·후 값, 수정자, 시각을 append-only 이력으로 보존하고 관리 화면에서 조회할 수 있게 한다 | 수치 분쟁 시 추적할 수 있고 Repository의 감사 이력 관례와 맞다 | 이력 테이블·조회 UI가 추가돼 범위와 검증이 커진다 |
| C | 일 단위 "확정(마감)" 개념을 두고 확정 후에는 별도 승인 절차로만 정정한다 | 통계 신뢰성이 가장 높다 | 승인 흐름·상태 전이가 새로 생겨 독립 소규모 기능의 범위를 크게 넘는다 |

**권장안**: A. 기존 PMS workflow와 연결하지 않는 독립 수치 기록이라는 확정 방향에서는 최종값+수정자·시각이 비용 대비 충분하다. 정정 빈도가 높고 "누가 바꿨는지"가 실제로 문제가 된다면 B를 선택해 달라. C는 이번 범위에 권장하지 않는다.

### 질문 4 — 과거 날짜 소급 입력 범위와 미래 날짜 차단

**필요한 이유**: interview 4절의 "과거 입력 범위 미확정"을 닫아야 한다. 기능 오픈 전의 과거 데이터를 얼마나 소급 입력할지, 미래 날짜 입력을 막을지에 따라 validation과 홈 그래프의 초기 표시가 달라진다.

**답변이 바꾸는 범위**: 날짜 validation 규칙, 초기 데이터 입력 계획(수기 소급 입력 여부), 홈 그래프의 초기 기간 표시.

| 선택지 | 내용 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A | 과거 날짜는 제한 없이 입력·정정을 허용하고 미래 날짜만 차단한다 | 오픈 후 필요한 만큼 과거 수치를 소급 입력할 수 있고 규칙이 단순하다 | 아주 오래된 날짜의 오입력을 시스템이 막지 못한다 |
| B | 지정한 시작일(예: 2026년 1월 1일) 이후만 입력을 허용하고 미래 날짜를 차단한다 | 통계 시작점이 명확하고 오입력 범위가 줄어든다 | 시작일 이전 데이터가 필요해지면 정책을 다시 바꿔야 한다 |

**권장안**: A. 독립 기능이라 다른 데이터와의 정합 위험이 없으므로 과거 입력을 막을 실익이 작다. 어느 쪽이든, 기능 오픈 시점에 소급 입력할 기존 수기 데이터(예: 올해 초부터의 기록)가 있는지와 그 입력을 누가 할지 함께 알려 달라. 시스템이 자동으로 가져올 원본은 없다는 전제(수기 입력)로 이해하고 있다.

### 질문 5 — 홈 그래프·표의 기본 기간과 집계 단위

**필요한 이유**: interview 1절의 "그래프와 표로 확인"이 확정 요구지만 기본 기간, 집계 단위(일/주/월), 오전·오후를 그래프에서 나눠 보여줄지가 미확정이다. 이 답이 홈 화면 구성과 조회 API 형태를 결정한다.

**답변이 바꾸는 범위**: 홈 조회 API의 기간·집계 파라미터, 자체 SVG 그래프 구성(막대·선·분리 여부), 표의 행 단위, 390px 모바일에서의 표시 방식.

| 선택지 | 내용 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A | 기본은 최근 30일 일별 그래프(생산은 오전·오후 구분 누적 막대+출하 병기, 출근 인원은 별도 그래프)와 같은 기간의 일별 표. 기간은 사용자가 변경할 수 있다 | 일 단위 입력 데이터를 그대로 보여줘 이해가 쉽고 기존 자체 SVG 그래프 패턴을 재사용할 수 있다 | 장기 추세(수개월)는 기간을 바꿔야 보인다 |
| B | 기본은 월별 합계 그래프와 월별 표로 장기 추세를 먼저 보여주고, 월을 선택하면 일별로 내려간다 | 경영 관점의 추세 파악에 유리하다 | drill-down 화면이 추가돼 범위가 커지고 일일 기록·확인이라는 1차 목적과 거리가 있다 |

**권장안**: A. "일일 데이터를 기록·정정·조회하고 그래프와 표로 확인"이라는 확정 목적에는 일별 기본 표시가 맞고 구현 범위도 작다. A를 선택하는 경우 두 가지를 함께 답해 달라. (1) 그래프에서 오전·오후 생산을 구분해 볼 필요가 있는지, 일 합계면 충분한지, (2) 생산·출하와 출근 인원을 홈에서 위아래 두 영역으로 나눠 보여주는 구성이면 되는지.
