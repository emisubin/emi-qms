## 1. 업무 문제와 기대 결과

- 현재 업무 방식: PMS 인앱 알림을 원본으로 Teams Activity Feed, 메일, Teams 공용 채널과 예약 발송이 일부 이벤트에 연결되어 있다.
- 해결할 문제: 같은 성격의 이벤트가 서로 다른 수신자·채널로 발송되고, 프로젝트 완료 단계와 Pending 종류에 따른 정책이 실제 업무와 다르다. 담당자 미지정 시 관리자에게 업무가 배정되고, 업무 예정일이 일정 원본과 자동으로 맞춰지지 않는다.
- 현재 우회 방식: 사용자가 PMS 목록과 외부 채널을 각각 확인하고, 잘못 배정되거나 누락된 업무를 사람이 전달한다.
- 성공했을 때 사용자가 할 수 있는 일: 업무 성격에 맞는 대상자가 정해진 채널에서 한 번만 알림을 받고, 부서 담당자가 없어도 부서장 모두가 업무를 확인하며, 일정 변경에 맞춘 D-1·초과 알림을 받는다.
- 하지 않을 경우 영향: 알림 누락·중복·과다 발송, 최종 완료 의미 혼선, 관리자 오배정, 기한 알림 부정확성이 계속된다.

## 3. 정상·예외·복구 흐름

- 정상 흐름: 업무 이벤트 저장 후 인앱 알림을 원본으로 생성하고, 확정된 수신자·채널별 delivery를 비동기로 처리한다.
- validation 실패: 수신자나 정확한 일정 원본이 없으면 임의의 관리자·영업 담당자 또는 프로젝트 납기일로 대체하지 않는다. 일정이 없으면 `due_date=null`로 유지한다.
- 동시 처리·중복: 같은 이벤트 재시도는 같은 인앱 알림·외부 delivery를 중복 생성하지 않는다. 여러 부서장 중 한 명이 fallback 업무를 완료하면 나머지의 동일 업무가 함께 종료된다.
- 취소·재시도·복구: Teams·메일·PWA 실패는 업무 저장을 취소하지 않으며, 기존 delivery 재시도와 append-only attempt lineage를 유지한다.
- 부분 실패와 rollback: 한 외부 채널 실패가 다른 채널의 성공 또는 원업무를 되돌리지 않는다. provider 비활성화 시 미발송 상태를 관찰 가능하게 유지한다.

## 4. Data·integration·lifecycle

- 신규 또는 기존 data 개념: 기존 notification·recipient·delivery·attempt·work item을 우선 재사용한다. 복수 부서장에게 표시되는 동일 fallback 업무의 묶음 식별과 동기화 종료 표현이 추가로 필요할 수 있다.
- 상태 전이: 원업무 생성 → 인앱 수신자 확정 → 외부 delivery 대기·성공·실패·재시도. fallback 업무는 활성 → 한 명 완료 → 같은 묶음의 나머지 업무 자동 종료로 전이한다.
- 보존·감사·삭제: 인앱 알림은 기간 기준 자동 삭제하지 않는다. 읽음 상태, 수신자, delivery와 attempt 이력을 보존한다.
- attachment·Excel·PDF: 변경 없음.
- 외부 연동·notification: Teams 개인 Activity Feed와 메일을 사용하고 Teams 공용 채널은 사용하지 않는다. PWA Web Push는 별도 `TASK-PWA-PUSH-001` 구현이 인앱 원본을 그대로 파생한다.
- migration·기존 데이터: 신규 묶음 식별 또는 동기화 상태가 필요하면 migration을 사용한다. 기존 완료 업무의 예정일 이력은 재계산하지 않는다. 미완료 업무의 일정 원본 연결 가능 여부와 backfill 범위는 기획에서 안전하게 확정한다.

## 5. UX와 운영 적용

- 진입 화면과 핵심 행동: 기존 알림 센터·업무 목록·사용자 알림 설정을 유지한다. 허용된 세 항목만 개인 설정에서 끌 수 있게 한다.
- 사용자 설정 가능: 일반 자동 업무 배정 Teams, D-1 Teams, 평일 Daily Digest 메일.
- 필수 알림: Pending, 프로젝트 생성·납기·상태·납품 완료·재검사·재조치 등은 사용자가 끌 수 없다.
- loading·empty·error·success feedback: 기존 흑백 와이어프레임과 공통 피드백 규격을 유지하며 delivery 실패를 사용자 업무 실패로 표시하지 않는다.
- 접근성·390px·Teams narrow: 기존 알림 센터와 설정 화면의 좁은 화면 동작을 보존한다.
- UAT와 rollout: 실제 provider 발송은 별도 승인된 안전 계정·대상에서만 검증한다. 자동 테스트는 실제 Teams·메일·PWA를 발송하지 않는다.
- rollback과 운영자 대응: 신규 worker·scheduler 설정은 채널별 비활성화가 가능해야 하며, 업무·인앱 원본은 외부 채널 rollback과 독립적으로 보존한다.

## 8. Fable 확인용 요약

- 해결할 문제: 알림 이벤트별 수신자·채널·시점의 불일치와 중복을 제거하고, 담당자 미지정·일정 변경에서도 현장 업무가 누락되지 않게 한다.
- 권장 범위: 확정된 정책을 기존 인앱 원본과 delivery worker 구조에 반영하고, 신규로 필요한 복수 부서장 동기화와 예정일 자동 연결만 최소 추가한다.
- 확정한 정책: 위 7개 round와 14개 결정 항목 전체.
- 명시적 제외: Teams 공용 채널, L2·L3 확대, quiet hours, 임의 예정일, 자동 삭제, 새 provider.
- Deferred 비차단 결정: 실제 provider 운영 검증과 공개 배포는 구현·자동 검증 뒤 별도 승인 경계로 둔다.
- Fable 판정: `COMPLETED_CONFIRMED`

## 9. 성공 기준

- 업무 결과: 각 이벤트가 확정된 수신자와 채널로 한 번만 생성되고, 불필요한 공용 채널·관리자 fallback·중복 제조 중단 알림이 없다.
- 권한·데이터 불변조건: 필수 알림은 사용자가 끌 수 없고, 외부 발송 실패가 업무를 취소하지 않으며, attempt lineage와 완료 이력이 보존된다.
- 자동 검증: 수신자·채널 매트릭스, idempotency, 부서장 동기화 완료, 일정 동기화, digest·D-1·초과 스케줄, 실제 provider 무발송을 Backend와 Full-Stack test로 검증한다.
- 사용자 검수: 알림 설정 화면, 주요 인앱 알림, 복수 부서장 업무, 프로젝트 생성·변경·납품·최종 완료와 Pending 흐름을 역할별로 확인한다.
