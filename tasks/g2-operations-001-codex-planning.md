## 0. 문서 지위

사용자가 확인한 Fable deep-interview를 구현 가능한 제품 계약으로 정리한 Codex 작성 기획안이다. Fable planning 실행이 현재 세션 한도로 실패한 뒤 사용자가 `codex 기획해봐`라고 명시해 작성자를 Codex로 전환했다.

이 문서는 Fable 원문이 아니며 표준 Fable 대상인 `tasks/g2-operations-001-planning.md`를 생성하거나 대체하지 않는다. 사용자 승인 전에는 기획 초안이고, 승인 이후에도 별도의 구현 지시가 있기 전까지 코드·DB·runtime·Git 게시 변경은 허용하지 않는다.

## 1. 목표와 기대 결과

기존 PMS 프로젝트·생산계획·물류·근태 데이터와 연결되지 않는 독립적인 `G2` 운영관리 영역을 추가한다. 사용자는 날짜별 생산·납품·제조 출근 인원을 간단히 입력하고, G2 홈에서 이번 달 생산·납품·재고·조별 생산·출근 현황을 한눈에 확인할 수 있어야 한다.

완료 후 다음 업무가 가능해야 한다.

1. 오전조·오후조 생산량을 서로 다른 담당자가 각각 입력하거나, 권한 있는 한 사용자가 한 번에 입력한다.
2. 일일 납품량과 오전·오후별 EMI/도급 출근 인원을 기록한다.
3. 과거와 미래 날짜를 제한 없이 입력하고, 미래 날짜 값은 화면에서 `예상`으로 구분한다.
4. 생산·납품으로 자동 계산한 재고와 재고 실사 기준점을 함께 관리한다.
5. 적용 시작일별 생산목표·재고목표를 그래프에 표시한다.
6. 모든 활성 사내 사용자는 G2를 조회하고, 부서별 담당자만 허용된 값을 변경한다.

## 2. 화면과 메뉴 구조

왼쪽 메뉴에 부모 메뉴 `G2`를 추가하고 다음 세 하위 메뉴를 제공한다.

| 메뉴 | 경로 | 목적 |
| --- | --- | --- |
| 홈 | `/g2` | 이번 달 생산·납품·재고·조별 생산 그래프와 제조 출근 현황표 조회, 재고 실사·목표 관리 |
| 생산/출하 관리 | `/g2/operations` | 날짜별 오전조·오후조 생산량과 일일 납품량 입력·정정 |
| 제조 인원 출근 관리 | `/g2/attendance` | 날짜별 오전·오후 EMI·도급 출근 인원 입력·정정 |

모든 활성 사내 사용자는 세 화면을 조회한다. 수정 권한이 없는 사용자는 입력 컨트롤 대신 읽기 전용 값과 마지막 수정 정보를 본다.

### 2.1 이번 범위에 포함하지 않는 메뉴

`손익관리`는 향후 영업팀 전용 `NEW_FEATURE`로 추적한다. 이번 Task에서는 숨겨진 route, 빈 화면, 메뉴 placeholder, permission을 만들지 않는다.

## 3. 권한 계약

화면 숨김만으로 권한을 처리하지 않고 API에서 동일한 규칙을 강제한다. System Administrator는 모든 G2 변경 권한을 가진다.

| 기능 | 조회 | 변경 가능 부서 |
| --- | --- | --- |
| G2 전체 | 모든 활성 사내 사용자 | 해당 없음 |
| 오전조·오후조 생산량 | 모든 활성 사내 사용자 | 제조, 영업, System Administrator |
| 일일 납품량 | 모든 활성 사내 사용자 | 영업, 물류, System Administrator |
| 출근 인원 4개 값 | 모든 활성 사내 사용자 | 제조, 영업, System Administrator |
| 일 생산목표 | 모든 활성 사내 사용자 | 제조, 영업, System Administrator |
| 재고목표 | 모든 활성 사내 사용자 | 제조, 영업, System Administrator |
| 재고 실사 | 모든 활성 사내 사용자 | 제조, 영업, System Administrator |

권장 permission은 다음처럼 업무 능력별로 분리한다.

- `G2.Read`
- `G2.Production.Update`
- `G2.Delivery.Update`
- `G2.Attendance.Update`
- `G2.Inventory.Manage`
- `G2.Target.Manage`

오전조 담당자와 오후조 담당자를 별도 사용자 권한으로 나누지 않는다. 제조·영업 권한자는 둘 중 하나만 저장하거나 둘을 한 번에 저장할 수 있다.

## 4. 업무 데이터 계약

### 4.1 날짜별 운영 값

날짜마다 다음 7개 원본 값을 독립적으로 저장한다.

| 구분 | 원본 값 | 규칙 |
| --- | --- | --- |
| 생산 | 오전조 생산량 | 0 이상의 정수, 선택 입력 |
| 생산 | 오후조 생산량 | 0 이상의 정수, 선택 입력 |
| 납품 | 일일 납품량 | 0 이상의 정수, 조 구분 없음 |
| 출근 | 오전 EMI 직원 | 0 이상의 정수, 선택 입력 |
| 출근 | 오전 도급 직원 | 0 이상의 정수, 선택 입력 |
| 출근 | 오후 EMI 직원 | 0 이상의 정수, 선택 입력 |
| 출근 | 오후 도급 직원 | 0 이상의 정수, 선택 입력 |

파생값은 다음과 같이 계산하고 별도 원본으로 입력하지 않는다.

- 일 생산량 = 오전조 생산량 + 오후조 생산량
- 오전 출근 합계 = 오전 EMI + 오전 도급
- 오후 출근 합계 = 오후 EMI + 오후 도급
- 하루 총원 = 오전 출근 합계 + 오후 출근 합계

같은 사람이 오전과 오후에 모두 근무했더라도 두 번 합산한다. 개인 식별정보나 근무자 명단은 저장하지 않는다.

### 4.2 빈 값과 0의 구분

입력하지 않은 값과 실제 `0` 입력은 관리 화면에서 구분한다. 그래프와 표도 가능한 범위에서 이를 구분하고, 빈 값을 사용자가 실제 0으로 입력한 것처럼 표시하지 않는다.

단, 자동 재고 공식에서만 빈 생산량·납품량을 0으로 취급한다. 이 예외는 재고선을 끊지 않기 위한 계산 규칙이며 원본 데이터의 입력 여부를 변경하지 않는다.

### 4.3 예상값

- 과거·오늘·미래 날짜 모두 입력할 수 있다.
- 서울 기준 오늘보다 미래인 날짜의 값은 별도 상태를 저장하지 않고 화면에서 날짜 기준으로 `예상` 표시한다.
- 날짜가 도래하면 같은 최종값이 현재값으로 보이며, 담당자가 실제값으로 덮어쓴다.
- 예상값과 교체 전 값의 별도 이력·예상 대비 실적은 만들지 않는다.
- 각 원본 값에는 현재 값, 마지막 수정자, 마지막 수정 시각, 동시성 version만 보존한다.

### 4.4 목표

목표 유형은 두 개다.

- 일 생산목표
- 재고목표

납품목표는 만들지 않는다. 각 목표 변경에는 `적용 시작일`을 저장하며, 날짜별로 가장 최근에 시작된 목표를 적용한다. 월중 변경 시 그래프 목표선은 적용일에서 계단 형태로 바뀐다. 과거·미래 적용일 모두 허용하되, 같은 목표 유형과 같은 적용일에는 하나의 값만 존재한다.

업무상 과거 목표값의 별도 수정 이력을 추가로 만들지 않는다. 동일 적용일의 잘못된 목표는 version 확인 후 현재 행을 정정하고, 정상적인 목표 변경은 새 적용 시작일로 추가한다.

### 4.5 재고 실사

- 재고 실사는 `오늘 또는 과거 날짜`에만 입력한다.
- 날짜당 실사값 하나를 저장한다.
- 가장 이른 실사값이 재고선의 최초 시작점이다.
- 실사 날짜의 자동 계산값은 실사값으로 대체하며 그래프에 `실사`로 표시한다.
- 실사값은 수정·삭제할 수 있으며 version 충돌 검사를 적용한다.
- 일별 자동 재고값을 직접 수정하는 별도 화면이나 필드는 만들지 않는다.

## 5. 자동 재고 계산

재고는 materialized 일별 행으로 저장하지 않고 조회 시 원본 생산·납품과 실사 기준점으로 계산한다. 계산 결과와 원본 사이의 불일치를 막기 위함이다.

### 5.1 기본 공식

실사 없는 날짜의 재고는 다음과 같다.

`당일 재고 = 전일 재고 + 당일 오전조 생산량 + 당일 오후조 생산량 - 당일 납품량`

생산량·납품량의 빈 값은 이 공식 안에서만 0으로 처리한다.

### 5.2 기준점과 정정 경계

1. 조회 범위 이전 또는 범위 안에서 사용할 수 있는 가장 가까운 실사 기준점을 찾는다.
2. 실사가 전혀 없으면 재고선은 표시하지 않고 `재고 실사를 입력하면 재고 추이가 시작됩니다`라고 안내한다.
3. 실사 날짜에는 공식 결과 대신 실사값을 사용한다.
4. 과거 생산·납품을 정정하면 해당 날짜부터 다음 실사 전날까지만 결과가 달라진다.
5. 다음 실사 날짜부터는 그 실사값을 새 기준으로 사용하므로 앞선 정정이 실사값을 덮지 않는다.
6. 실사를 수정·삭제하면 해당 기준점부터 다음 실사 전날까지 다시 계산한다. 최초 실사를 삭제하면 다음 실사부터 재고선을 시작한다.

### 5.3 미래 예상 재고

미래 생산·납품 값에도 같은 공식을 적용해 선택한 달의 말일까지 예상 재고를 계산한다. 오늘 이후 구간은 점선으로 표시한다. 미래 실사는 허용하지 않는다.

계산 결과가 음수가 되어도 0으로 보정하거나 숨기지 않는다. 입력 누락이나 운영상 부족을 발견할 수 있도록 음수 값을 그대로 표시하고 경고 상태를 함께 표시한다.

### 5.4 조회 범위

월별 조회는 필요한 가장 가까운 이전 실사 한 건, 해당 월의 실사·일별 원본·목표만 사용하도록 날짜 index를 둔다. 전체 이력을 매번 처음부터 순회하지 않는다.

## 6. G2 홈 상세

기본 조회 기간은 서울 기준 이번 달이다. 월 이동을 제공하되 한 번에 한 달을 조회한다.

### 6.1 생산·납품·재고 그래프

날짜별로 다음을 한 그래프에 표시한다.

- 생산량 세로 막대
- 납품량 세로 막대
- 자동 계산 재고수량 선
- 적용일별 재고목표 계단선
- 오늘 이후 예상 재고 점선
- 실사 날짜의 `실사` marker

생산량과 납품량은 날짜마다 나란한 두 막대로 표시한다. 재고·재고목표는 막대와 값의 규모가 다를 수 있으므로 명확한 보조축, 단위, 범례를 제공한다.

실사 marker 또는 같은 날짜의 접근 가능한 `실사 입력/수정` 동작으로 편집 dialog를 연다. pointer 조작만 강제하지 않고 키보드, focus 이동, 오류 안내, 저장 중 중복 제출 차단과 저장 결과 `aria-live`를 제공한다.

### 6.2 조별 생산량 그래프

날짜별 오전조 생산량 위에 오후조 생산량을 쌓은 세로 막대로 표시한다. 적용일별 일 생산목표는 계단선으로 표시한다.

### 6.3 제조 인원 출근 현황표

이번 달 날짜별로 다음 열을 표시한다.

| 날짜 | 오전 EMI | 오전 도급 | 오후 EMI | 오후 도급 | 오전 합계 | 오후 합계 | 하루 총원 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |

미래 날짜 값에는 `예상` 표시를 붙인다. 390px 화면에서는 페이지 전체 가로 스크롤이 생기지 않도록 표 영역 안에서만 가로 스크롤을 허용하고, 날짜 열을 식별하기 쉽게 유지한다.

### 6.4 그래프 접근성

두 그래프는 시각화와 같은 수치를 제공하는 화면 읽기용 표를 포함한다. 색상만으로 생산·납품·예상·실사를 구분하지 않고 범례, 선 종류, 문자 label을 함께 사용한다.

## 7. 관리 화면 상세

### 7.1 생산/출하 관리

- 날짜를 선택해 오전조 생산량, 오후조 생산량, 일일 납품량을 본다.
- 권한 있는 필드만 수정할 수 있다.
- 오전 또는 오후 한 필드만 저장해도 다른 필드를 덮어쓰지 않는다.
- 한 사용자가 수정 가능한 여러 필드를 한 번에 저장할 수 있다.
- 미래 날짜에는 입력 영역과 행에 `예상` 표시를 제공한다.
- 각 값의 마지막 수정자·수정 시각을 표시한다.
- 빈 값 삭제와 숫자 0 저장을 구분한다.

서로 다른 권한이 섞인 저장 요청은 서버가 제공된 필드 각각을 검사한다. 하나라도 권한이 없으면 전체 요청을 저장하지 않고 명확한 권한 오류를 반환한다.

### 7.2 제조 인원 출근 관리

- 날짜를 선택해 오전 EMI, 오전 도급, 오후 EMI, 오후 도급 네 값을 입력한다.
- 오전 합계, 오후 합계, 하루 총원을 즉시 계산해 보여준다.
- 미래 날짜에는 `예상` 표시를 제공한다.
- 마지막 수정자·수정 시각과 version 충돌 안내를 제공한다.

### 7.3 입력 공통 규칙

- 정수만 허용하고 음수, 소수, 허용 범위를 넘는 값은 저장 전에 필드 가까이에서 설명한다.
- 저장 중 같은 버튼의 중복 실행을 막는다.
- 서버 오류·권한 오류·동시 수정 충돌은 해당 날짜와 필드 근처에 표시한다.
- 다른 사용자가 먼저 같은 값을 수정했으면 자동 덮어쓰지 않고 최신 값을 다시 불러오도록 안내한다.
- 서로 다른 날짜 또는 서로 다른 원본 값 수정은 불필요하게 충돌시키지 않는다.

## 8. 권장 데이터 구조

구현 시 최신 원격 `main`의 migration 번호를 다시 확인하고 다음 사용 가능한 additive migration 하나를 사용한다. 현재 관찰한 번호만으로 migration 번호를 미리 고정하지 않는다.

### 8.1 `g2_daily_metrics`

날짜·metric 단위로 현재 최종값을 저장한다.

- `id`
- `work_date`
- `metric_code`
- `quantity`
- `version`
- `created_at`, `created_by`
- `updated_at`, `updated_by`
- unique: `(work_date, metric_code)`

`metric_code`는 오전/오후 생산, 납품, 오전/오후 EMI·도급 출근의 7개 값으로 제한한다. 날짜별 하나의 넓은 행이 아니라 metric별 행을 사용해 오전·오후 담당자의 독립 저장과 동시성 검사를 분리한다.

### 8.2 `g2_inventory_counts`

- `count_date` unique
- `quantity`
- `version`
- 생성·수정자와 시각

서울 기준 미래 날짜를 서버에서 거부한다.

### 8.3 `g2_targets`

- `target_type`: `DailyProduction` 또는 `Inventory`
- `effective_date`
- `quantity`
- `version`
- 생성·수정자와 시각
- unique: `(target_type, effective_date)`

목표 변경은 새 적용일 행을 추가하는 것을 기본으로 한다.

### 8.4 변경 이력과 감사

업무 화면과 G2 테이블에는 과거 수량 snapshot을 보존하지 않는다. Repository 공통 감사 정책에 이벤트 기록이 필요하면 대상·행위·사용자·시각·결과만 남기고 교체 전 수량을 별도 업무 이력으로 복제하지 않는다.

## 9. 권장 API 경계

| API | 역할 |
| --- | --- |
| `GET /api/g2/home?month=YYYY-MM` | 한 달 그래프·출근표·목표·실사와 권한 projection 반환 |
| `GET /api/g2/operations?from=...&to=...` | 생산·납품 관리 범위 조회 |
| `PUT /api/g2/operations/{date}` | 제공된 생산·납품 필드만 version 조건으로 원자 저장 |
| `GET /api/g2/attendance?from=...&to=...` | 출근 관리 범위 조회 |
| `PUT /api/g2/attendance/{date}` | 제공된 출근 4개 필드만 version 조건으로 원자 저장 |
| `PUT /api/g2/inventory-counts/{date}` | 실사 생성·수정 |
| `DELETE /api/g2/inventory-counts/{date}` | version 조건으로 실사 삭제 |
| `GET /api/g2/targets` | 목표 적용 이력 조회 |
| `PUT /api/g2/targets/{targetType}/{effectiveDate}` | 목표 적용일 생성·정정 |

모든 mutation은 `ExpectedVersion` 또는 동등한 CAS 계약을 사용한다. 일부 필드만 보낸 요청은 보내지 않은 필드를 변경하지 않는다. mixed permission 요청은 저장 전에 전부 검증하고 transaction 안에서 처리한다.

ReviewSafe 실행에서는 G2 mutation을 허용하지 않는다. 오류 응답은 Repository의 안정된 권한·validation·conflict 형식을 재사용한다.

## 10. 구현 구조 권장안

### Backend

- `backend/src/Emi.Qms.Api/G2/` 아래 contracts, store, endpoint extensions를 분리한다.
- 기존 `Program.cs`의 store 등록·endpoint mapping 방식을 따른다.
- `TimeProvider`와 서울 업무 날짜 helper를 사용해 오늘/미래 판정을 한 곳에서 수행한다.
- 권한 seed는 migration과 코드 상수를 함께 추가하되 기존 role·permission을 재해석하지 않는다.
- 재고 계산은 별도 순수 domain 함수로 분리해 실사 경계와 미래 계산을 단위 테스트한다.

### Frontend

- 기존 `App.tsx`의 부모/하위 메뉴와 desktop/mobile navigation 방식을 재사용한다.
- G2 전용 page와 API client를 추가한다.
- 기존 `SalesKpiChart`를 확장해 다른 업무 계약을 섞지 않고, G2 전용 접근 가능한 SVG chart component를 만든다.
- 기존 디자인 token, form, dialog, loading/error 패턴을 재사용한다.
- route와 수정 control 모두 permission projection을 사용하되 서버 권한 검사를 최종 기준으로 둔다.

## 11. 오류·동시성·복구

| 상황 | 처리 |
| --- | --- |
| 같은 metric을 두 사용자가 수정 | 먼저 저장한 값 성공, 뒤 요청은 `409 Conflict`; 최신 값 재조회 안내 |
| 오전조와 오후조를 동시에 각각 수정 | metric별 version으로 서로 충돌 없이 저장 |
| 납품 권한 없는 제조 사용자가 생산+납품 동시 저장 | 전체 요청 `403`, 어느 값도 저장하지 않음 |
| 실사 없는 기간 | 재고선 미표시, 최초 실사 입력 안내 |
| 과거 값 정정 | 다음 실사 전날까지만 계산 결과 변화 |
| 미래 실사 입력 | 서버 validation 오류 |
| 음수 재고 계산 | 값을 그대로 표시하고 경고, 자동 보정 금지 |
| 네트워크·서버 실패 | 입력값 보존, 재시도 가능, 성공으로 오인하지 않음 |

## 12. 검증 계획

### 12.1 Backend·DB

- Backend solution build

- fresh DB와 기존 DB에서 additive migration 적용
- migration catalog·순서·중복 번호 확인

- 최초/중간/연속 실사, 실사 수정·삭제, 다음 실사 경계 재계산

- transaction 중 일부 실패 시 전체 rollback

### 12.2 권한

최소 다음 persona로 API allow/deny를 자동 검증한다.

- 영업: 생산·납품·출근·목표·실사 변경 허용
- 제조: 생산·출근·목표·실사 허용, 납품 거부
- 물류: 납품 허용, 생산·출근·목표·실사 거부
- 일반 조회 사용자: 조회만 허용
- 비활성·미인증 사용자: 기존 인증 계약대로 차단

### 12.3 Frontend

- lint, typecheck, frontend tests, production build
- desktop과 390px에서 G2 부모·하위 메뉴, 세 route, loading/error/empty 상태 확인
- 권한별 control 표시와 실제 서버 거부가 일치하는지 확인

- 실사 입력·수정·삭제를 mouse와 keyboard로 확인

- console error와 실패 network request 없음 확인

### 12.4 통합 검수

격리된 full-stack 환경에서 다음 대표 시나리오를 확인한다.

1. 제조 사용자가 오전조만 저장하고 영업 사용자가 오후조를 추가한다.
2. 물류 사용자가 납품량을 저장하고 제조 사용자의 납품 변경은 차단된다.
3. 과거 생산 정정이 다음 실사 전까지만 재고를 바꾼다.
4. 미래 생산·납품·출근이 `예상`으로 보이고 예상 재고가 점선으로 이어진다.
5. 목표 적용일 변경 시 두 목표선이 날짜에 맞게 계단으로 변한다.
6. 모바일에서 세 화면과 실사 dialog를 조작할 수 있다.

1. 구현 시작 시 최신 `origin/main`을 기준으로 instruction chain·Task Identity Gate를 다시 수행하고, 현재 생산관리·인증 변경과 충돌 여부를 재확인한다.
2. additive schema, permission 상수·seed, 날짜/수량 constraint를 구현한다.
3. 재고 계산 domain, store, API, 동시성·권한 tests를 구현한다.
4. G2 route·메뉴·API client와 생산/출하·출근 관리 화면을 구현한다.
5. G2 홈의 두 그래프, 출근표, 목표·실사 편집을 구현한다.
6. Backend·Frontend·migration·권한·동시성·desktop/mobile full-stack 검증을 수행한다.
7. Implementation report, privacy-safe 증빙과 사용자 검수 checklist를 작성한다.
8. local commit, push, PR, merge, Azure 공개배포는 각각 사용자가 승인한 범위에서만 진행한다.

## 14. 완료 기준

- G2 메뉴와 세 하위 화면이 모든 활성 사내 사용자에게 보인다.
- 부서별 수정 권한이 UI와 API에서 동일하게 적용된다.
- 오전·오후 생산량을 독립 또는 일괄 저장해도 다른 값이 유실되지 않는다.
- 일별 납품량과 출근 4개 원본 값, 세 합계가 계약대로 동작한다.
- 미래 값은 날짜 기준 `예상`으로 명확히 표시된다.
- 재고는 실사를 시작점·불변 계산 경계로 삼아 공식대로 계산되고, 미래 구간은 점선이다.
- 생산·납품·재고 그래프, 조별 생산 그래프, 출근 현황표가 이번 달 데이터를 올바르게 표시한다.
- 생산목표·재고목표 이력이 적용 시작일별 계단선으로 표시된다.
- 실사를 홈에서 접근 가능하게 입력·수정·삭제하고 `실사` marker를 확인할 수 있다.
- 동시성·권한·migration·desktop/mobile 접근성 검증에 미해결 P0/P1/P2 Finding이 없다.
- 기존 PMS 데이터와 업무 흐름을 연결하거나 변경하지 않는다.
