## 1. 이번에 바꾸려는 것

작은 수정에도 전체 지침 읽기, 고정 모델 분업, 여러 승인 상태, 여러 보고서와 검증 단계가 따라붙는 구조를 바꾼다. 기본 흐름은 **현재 상태 확인 → 필요한 결정만 정리 → 구현 → 변경에 맞는 확인 → 결과 기록**이다. 운영 데이터·권한·병합·배포 경계는 별도로 유지한다.

이 문서는 교체할 실행 규칙의 원문과 파일별 정리 방향을 함께 제공한다. 과거 승인 이력을 지우거나 오래된 작업 폴더를 최신 제품 상태로 간주하지 않는다. 모든 개인 스킬을 PMS에 적용하거나 새 실행 프레임워크를 설치하는 계획도 포함하지 않는다.

Change 021에서 최초 설계와 사후 검토를 완료했다. 이번 Change 022는 “분석 결과 반영해” 요청에 따라 OmO·CodexClaw의 유용한 원칙을 이 설계에 반영한다. 활성 지침 변경이나 플러그인 설치 승인을 뜻하지 않는다. 기존 미커밋 AGENTS·로드맵·설정은 보존하며, 실제 적용 때 재량이 넓어질 부분은 §6.3에 표시한다.

Directory ledger `0004`, business ledger `0088`, identity schema contract `0001`/`0086`은 감사 시점의 서로 다른 종류의 값이다. 같은 숫자여야 한다는 gate를 만들지 않는다. 이후 변경에서는 최신 migration catalog·live ledger·identity의 의미를 다시 확인한다.

## 3. 적용 후 Root AGENTS.md 교체 원문

아래 블록만 Root의 항상 읽는 지침으로 사용하고, 세부 실행법은 뒤의 관련 문서에 둔다. 상위 실행 정책·도구 제한을 이 문서가 해제할 수는 없다.

```markdown
# EMI PMS 작업 지침

## 시작과 사실 확인
- 현재 사용자 요청과 유효한 기존 승인을 해당 범위의 실행 근거로 사용한다. 같은 승인을 문서 미기록만으로 다시 묻지 않는다.
- 시작할 때 현재 branch/WIP, 적용 AGENTS, 해당 Task의 최신 계약·상태와 관련 코드부터 확인한다. 지침·base·작업 경계가 바뀌면 영향받는 자료만 다시 읽는다.
- 기존 목적의 수정은 같은 Task/change를 이어간다. 새 Task 생성이나 목적 모호성이 있을 때만 과거 Task·branch·PR까지 검색을 넓힌다.
- 사용자가 이름을 지정한 작업은 실질 선행조건을 확인해 진행한다. 제품·권한·운영 경계를 바꾸는 순서 변경만 추가 결정 대상으로 보고한다. “다음 작업”은 현재 실행 큐의 이름 있는 미완료 작업을 사용한다.
- 실행 지침은 AGENTS, 승인된 제품 계약은 해당 Task/ADR, 구현 사실은 코드·검증, 현재 작업 상태는 Task가 소유한다. 코드가 제품 정책을 자동 변경하지 않는다.
- 역사 기록을 현재 명령으로 재실행하지 않는다. 의미 있는 충돌은 영향과 근거를 밝히고 그 해결에 의존하는 변경만 보류한다.

## 작업과 모델
- 목표·범위·보존할 계약·완료 조건·검증 방법을 Task/change 한 곳에 짧게 정리한다. 작은 수정은 기존 기록에 추가한다.
- 작업 절차는 실제 동작·권한·데이터 영향으로 정한다. 파일 수나 디렉터리 이름만으로 작은 수정을 큰 절차로 올리지 않는다.
- 기획 요청은 기획까지, 구현 요청은 범위 내 구현·필요한 검증·결함 보정까지 진행한다. 실제 결과를 바꾸는 미결정만 질문한다.
- 모델은 모델 작업 방식 문서의 위험·복잡도별 기준으로 선택한다. GPT-6의 직접 구현을 허용하고 모든 코딩의 Sol 위임을 강제하지 않는다.
- 독립적으로 맡길 이익이 있을 때만 범위·소유 파일·완료/중단 조건과 반환 증거를 정해 위임한다. 같은 파일의 동시 편집을 피한다.
- 사용자 지정 모델은 준수한다. 요청 모델과 도구가 관측한 모델을 구분하며 관측되지 않은 값을 실행 사실로 기록하지 않는다.

## 변경·권한·환경
- 승인된 업무 범위의 구현 선택과 결함 보정은 계속한다. 새로운 제품 능력·정책·권한·외부 영향은 범위를 다시 확정한다.
- main에서 직접 개발하거나 push하지 않는다. 범위 밖 WIP, 사용자 자원과 다른 작업의 runtime을 임의 변경·정리하지 않는다.
- 기존 branch에서 안전하게 이어갈 수 있으면 사용한다. branch 전환 전 WIP·commit 보존과 runtime source 의존성을 확인한다. worktree는 실제 격리가 필요할 때만 만든다.
- 로컬 실행은 목적·소유·DB·provider 경계를 확인한다. 5174 실행 사실만으로 main 검수 환경이라고 판단하지 않는다.
- Persistent UAT/운영 DB의 drop·truncate·reset과 영구 volume 삭제를 일반 작업·검증·복구 수단으로 사용하지 않는다. migration·배포 승인에 이 금지 행동이 포함된 것으로 해석하지 않는다.
- E2E와 migration 검증은 전용 disposable DB·container·storage 및 합성 데이터를 사용한다. 이미 main에 반영된 migration은 수정하지 않고 추가 migration으로 보정한다.
- 운영·Persistent UAT 데이터/환경 변경, 실제 provider 동작, 유료 자원 생성, 파괴적 작업, push·PR·merge·정리는 해당 대상·행동의 명시적 승인 범위에서만 한다.
- main merge는 자동 검증과 사용자 검수 뒤 해당 병합의 명시적 승인 1회를 유지한다. 완료한 승인 범위의 local commit은 별도 질문 없이 수행한다.
- 승인 범위의 개별 경로만 stage하고 cached diff에서 범위 밖 변경·secret·불필요한 생성물이 포함되지 않았는지 확인한다.
- 도구 정책 거부를 명령 변형·대체 CLI·권한 설정 변경으로 우회하지 않는다. 확인된 거부 이유와 영향 범위를 보고하고 독립적인 허용 작업은 계속한다.

## PMS 품질
- 청주·오산·Directory 데이터와 서버 권한 경계를 보존한다. 화면 숨김만으로 권한을 구현하지 않는다.
- 기존 청주 UI 재사용 요청은 실제 공용 구성을 재사용하고 동일 조건에서 화면으로 비교한다. 승인되지 않은 UI/업무 흐름 재설계를 하지 않는다.
- 검증표에서 변경과 직접 연결된 테스트를 선택한다. 권한 거부·DB migration·동시성 등 실제 위험의 반례가 해당 분기를 실행하고 기대 결과를 보이는지 확인한다.
- 화면이 바뀌면 관련 상태와 필요한 화면 폭을 눈으로 확인한다. 이미지 생성만으로 검증 완료라 하지 않는다. 증거는 합성 데이터·최소 정보로 남긴다.
- 전체 회귀는 사용자 검수 후 최종 병합 후보에서 책임 실행 1회를 원칙으로 한다. 변경·실패·새 위험이 있으면 영향받는 검증을 다시 한다.
- 권한·DB·동시성·운영/CI·공통 계약 변경과 큰 기능은 fresh 검토를 받는다. 작은 가역 수정은 직접 diff 검토와 관련 검증으로 끝낼 수 있다.
- 구현·자동 검증·사용자 검수·원격 반영·배포를 서로 다른 상태로 기록한다. 실행하지 못한 확인과 남은 문제를 완료라고 표현하지 않는다.

## 기록과 재개
- Task/change에 현재 목표·승인 경계·실제 변경·검증 근거·남은 일을 한 번 기록한다. Roadmap은 우선순위와 해당 Task 링크만 소유한다.
- 압축·재개 시 이 기록과 실제 branch/diff를 대조한다. 끝난 작업을 다시 수행하거나 과거 승인을 다른 범위로 옮기지 않는다.
- 최종 보고는 결과, 확인한 근거, 남은 사용자 행동과 게시 상태를 간단히 설명한다. 상세 로그는 필요한 경우에만 연결한다.
- 반복 절차가 필요할 때만 해당 스킬/SOP를 읽는다. 개인 스킬의 일반적인 자동 트리거로 승인·리뷰·재설계 단계를 추가하지 않는다.
```

## 4. 모델 호출과 작업 분배

### 4.1 기본값 제안

현재의 `6 High → Sol Extra high → 6 High → 추가 fresh 6 High`를 모든 코딩에 강제하지 않는다. **일상 채팅은 GPT-6 Medium, 권한·DB·운영 판단은 GPT-6 High, 좁고 명확한 구현은 필요할 때 Sol Medium/High**를 권장 시작점으로 한다. 이것은 PMS 실측 최적 조합이 아니라 검증할 운영 가설이다.

| 작업 | 기본 제안 | 검토 |
| --- | --- | --- |
| 설명·조회·오타·좁은 문서 수정 | 현재 parent가 처리, 새 agent 없음 | 직접 확인 |
| 범위가 명확한 일반 기능/버그 | GPT-6 Medium이 방향·구현·관련 테스트까지 처리 | 큰 기능/공통 계약이면 fresh GPT-6 High |
| 기존 패턴 반복, 독립된 제한 구현 | 필요할 때 Sol Medium/High 1명 | parent가 실제 diff와 반례 확인; 위험 기준에 따라 fresh 검토 |
| 인증·권한·3-DB·migration·동시성·배포/CI | GPT-6 High가 원인과 구현을 담당하거나 좁은 구현을 위임 | fresh GPT-6 High 필수 |
| 원인이 불명확한 반복 실패·복잡한 설계 | 먼저 범위를 좁힌 뒤 해당 부분만 xhigh 고려 | 난도를 높인 이유와 결과 기록 |

사용자가 High로 시작한 현재 채팅의 강도가 문서만으로 Medium으로 바뀌지는 않는다. 실제 설정·호출 수단이 없으면 그 세션의 모델로 진행하고 선택값을 정확히 설명한다. 사용자가 특정 모델만 사용하라고 지정한 작업에서는 조용한 대체를 하지 않는다.

설정 적용 때 `.codex/config.toml`의 parent 기본값을 위 원칙에 맞추고, 기본 subagent를 Sol xhigh로 고정하는 값은 제거 또는 재설정한다. 중요한 위임은 호출 인자에 역할 모델·강도를 명시해 의도치 않은 상속을 피한다. 동시 한도는 항상 그 수만큼 agent를 쓰라는 지시가 아니다. 일상은 0~1명, 독립 작업이 있을 때만 늘린다.

위임 내용은 **목표·현재 사실·변경 범위/불변조건·완료 조건/검증·반환 조건**으로 충분하다. 작은 구현에 7개 빈 항목을 채우는 별도 문서를 만들지 않는다. 범위 내 세부 방식은 구현자가 결정할 수 있지만 업무·권한·운영 경계는 넓힐 수 없다. 읽기 전용 reviewer에게는 대상 파일 쓰기 금지와 기준선을 전달한다. 문장으로 read-only를 지정한 것과 OS가 쓰기를 차단한 실행은 구분한다.

반환 조건에는 언제 완료하고 언제 parent에게 돌려줄지 적는다. 결과는 **완료 / 차단 / 판단 불충분** 중 하나와 실제 diff·검증 근거·남은 가정으로 전달한다. 재위임은 별도 지시가 있을 때만 한다. parent는 결과 형식이 갖춰졌다는 이유로 검증을 통과시키지 않고 근거를 읽는다. 호출 인자는 현재 도구가 지원하는 schema를 사용한다. 전체 대화 상속과 모델 override의 양립 여부를 확인하며, 외부 하네스의 역할명·설정 예시를 그대로 호출하거나 실제 모델 관측값으로 기록하지 않는다.

독립 검토는 구현자의 결론을 복사하지 않고 실제 diff·계약·테스트를 본다. parent가 직접 구현했고 독립 검토 대상인 경우 fresh reviewer 한 번으로 검토 책임을 분리한다. parent 통합 확인을 별도의 전체 검토 회차로 부풀리지 않는다. 결함 수정 후에는 해당 변경과 영향을 다시 보며, 아직 결함이 있으면 횟수 제한으로 통과시키지 않는다.

### 4.2 비용·속도 판단

OpenAI의 모델/추론 가이드는 강도를 작업에 맞추고 높은 강도의 추가 비용·지연을 평가하도록 안내한다. 모델 선택만으로 최적 조합이 증명되지는 않는다. [모델 선택](https://learn.chatgpt.com/docs/models#choosing-sol-terra-and-luna), [추론 강도](https://developers.openai.com/api/docs/guides/reasoning#reasoning-effort)

현재 비교의 단위는 답변 한 번의 가격이 아니라 **요청부터 검증된 완료까지의 parent+child 전체 시간·사용량·재작업**이다. 실제 Codex 사용량과 API 환산 비용을 섞지 않는다. 이 설계에서 비용 절감률을 보장하거나 큰 유료 벤치마크를 자동 실행하지 않는다. 이후 일반 UI 수정·권한 버그·기능 구현 사례에서 완료 시간, 불필요한 질문, 중복 전체 테스트, 리뷰 결함과 재작업만 간단히 기록해 기본값을 조정한다. 서로 다른 모델을 비교할 때는 같은 코드 기준선·요구사항·검증 기준을 사용한다.

커뮤니티의 [lazycodex](https://github.com/code-yeongyu/lazycodex), [harness-subagent](https://github.com/ptmrio/harness-subagent)는 작업 분리·완료 증거를 참고한 사례다. 해당 저장소의 주장이나 역할 조합을 PMS의 성능 증거로 사용하지 않고, 외부 하네스를 설치하지 않는다. 앞선 SNS 논의의 백분율도 같은 문제·채점·도구 조건을 확인하지 못하면 이 설계의 품질 근거로 채택하지 않는다.

### 4.3 작업에 맞는 절차의 깊이

| 실제 변경 영향 | 필요한 절차 |
| --- | --- |
| 동작을 바꾸지 않는 문구·좁은 스타일 수정 | 직접 수정·해당 문구/화면 확인. 별도 인터뷰·계획서·agent를 만들지 않음 |
| 범위가 명확한 일반 동작 변경 | 기존 Task에 짧은 방향·완료 조건, 관련 테스트와 필요한 화면 확인 |
| 권한·3-DB·migration·동시성·외부 실행 경계 변경 | 영향받는 계약과 실패 조건을 먼저 명시, §4.1의 High·독립 검토 및 해당 검증 적용 |

인증 파일의 오타 수정까지 권한 변경으로 취급하지 않는다. 반대로 한 줄이어도 사업부 접근 권한을 바꾸면 높은 위험으로 다룬다. 조사 중 위험이 드러나면 영향을 받는 부분의 절차를 보강한다. 정보가 부족하다는 이유만으로 모든 단계를 강제하지 않고, 코드·계약으로 해소하지 못한 실제 결정만 질문한다.

지침을 정리할 때 **필수 계약 / 기본 방식 / 판단 참고 / 예시 / 추가 결정이 필요한 경계**를 구분한다. 예시의 파일명·항목 수·화면 크기를 필수 규칙으로 확대하지 않는다. 기존 사용자 지시·상위 정책·명확한 승인 요구를 에이전트가 임의로 “기본값”으로 낮추는 규칙은 아니다. Root에는 필수 경계를 두고 상세 문서에서 필요한 구분만 설명하며 모든 문장에 새 태그를 붙이지 않는다.

## 5. 실행환경·도구·세션·재시도

### 5.1 실행 원칙

- 독립 조회는 병렬로 묶고 출력 범위를 좁힌다. 의존 관계가 있는 변경·승인·migration·배포는 순서대로 실행한다.
- 실행 중인 명령은 반환된 session으로 이어받는다. timeout만 보고 같은 서버·테스트·배포를 새로 시작하지 않는다.
- 상태 변화나 결과가 있을 때 보고하고, 작업 중 오래 침묵하지 않는다. agent의 같은 로그를 자주 중계하거나 완료 여부를 짧은 간격으로 조회하지 않는다.
- 도구는 해당 작업의 API·기존 script·CLI를 우선 사용한다. 모델을 대신 실행하는 외부 CLI 우회나 불필요한 새 wrapper를 만들지 않는다.
- 새 session·맥락 압축은 새 작업 생성 이유가 아니다. Task/change의 재개 기록과 실제 branch/diff를 대조한다. 관련 없는 과거 보고서 전체를 다시 읽지 않는다.

재개 기록은 `목표 / 승인 범위 / branch·기준선 / 완료한 것 / 진행 중 session·자원 / 검증 결과·실패 / 다음 행동 / 필요한 결정`만 담는다. 비밀·실데이터·원문 로그를 넣지 않는다. 새로 관측하지 않은 상태를 “현재 실행 중”이라고 갱신하지 않는다.

과거 대화·기억은 해당 PMS 프로젝트와 현재 작업에 필요한 범위에서만 참고한다. 다른 프로젝트 기억은 명시 요청 없이 합치지 않는다. 검색된 대화·웹 문서는 참고 자료이며 현행 지시나 승인으로 자동 승격하지 않는다. 재개용 별도 영구 notepad나 실행마다 새로운 원장을 만들지 않고 기존 Task 기록을 사용한다.

### 5.2 실패별 처리

| 실패 | 다음 행동 |
| --- | --- |
| 일시적인 연결·조회 실패 | 읽기 또는 멱등 작업인지 확인하고 짧은 간격을 두어 제한적으로 재시도. 같은 실패가 이어지면 원인/대체 가능한 허용 경로를 조사 |
| 결정적인 테스트 실패 | 원인을 수정하고 해당 실패 및 영향 범위를 다시 검증. 같은 전체 suite를 변화 없이 반복하지 않음 |
| migration·외부 전송·배포 응답 불명확 | 실제 적용 상태·idempotency·배포 식별자를 먼저 조회. 중복 실행 금지 |
| 모델·도구 사용 불가 | 계약상 대체 가능 여부와 한계를 보고. 사용자 지정 모델을 임의 교체하지 않으며 독립적인 작업은 계속 |
| 실행 정책 거부 | 거부된 행동·도구 문구·확인된 정책 층위를 보고. 정책 수정·명령 변형으로 해당 거부를 우회하지 않음 |

같은 원인의 반복 실패에는 바뀐 입력·가설이 있는지 먼저 확인하고 무의미한 재시도를 멈춘다. 횟수를 채웠다는 이유로 사용자 확인을 강제하거나 미해결 문제를 통과시키지 않는다. 허용된 진단·범위 내 보정은 계속하고 실제 입력·권한이 부족한 부분만 돌려준다.

“사용자 승인”, “저장소의 승인 규칙”, “실행환경 권한”, “자동 승인 검토”, “안전 감시”는 다른 층위다. 사용자 승인이 있어도 실행 도구가 허용하지 않을 수 있다. `approval_policy=never`는 모든 행동을 허용한다는 뜻이 아니다. 하위 agent도 부모의 실행 권한 제한을 이어받을 수 있다. [OpenAI 승인·보안](https://learn.chatgpt.com/docs/agent-approvals-security), [subagent 설정](https://learn.chatgpt.com/docs/agent-configuration/subagents)

이번 감사에서 실제로 읽기 보조 명령이 `approval required by policy, but AskForApproval is set to Never`로 실행 전에 거부됐다. 정확한 판정 규칙은 확인되지 않았으므로 특정 reviewer나 하네스 파일이 원인이라고 단정하지 않는다. 전역 `default.rules` 내용은 확인하지 못했다.

### 5.3 실행 규칙 정비 대상

`.codex/rules/project-safety.rules`의 `gh pr view`, 모든 `psql`, 일반 shell wrapper에 대한 광범위 prompt는 승인된 읽기 조사까지 막을 수 있다. 향후 적용에서는 **명령 이름만이 아니라 실제 행동·대상·출력 범위**를 구분하도록 검토한다. 조회 허용을 이유로 모든 Python·shell·SQL을 일괄 허용하지 않는다. PR 본문·DB 결과도 필요한 부분만 읽고 비식별 요약한다.

main 직접 push 금지, history/WIP 파괴, 영구 DB/volume 삭제 보호는 유지한다. 인자 순서나 옵션 형태에 따라 의도한 보호가 누락되지 않는지 규칙 match/not_match와 기존 안전 script 검증으로 확인한다. legacy Fable runner의 넓은 allow는 현재 기본 실행에서 제거하고, 필요하면 사용자가 선택한 legacy 절차에만 한정한다.

실제 정책 파일 편집은 실행 동작 변경이므로 별도 적용 범위와 검증이 필요한 코딩 작업이다. 이번 문서 작성은 현재 거부를 통과시키기 위한 실행 정책 변경을 승인하거나 수행하지 않는다. 전역 설정·공용 플러그인·회사 관리 정책은 프로젝트 문서 적용만으로 변경하지 않는다.

### 5.4 자원과 강제 장치

새 임시 자원이 필요하면 기존 Task 기록에 목적·소유자·source/식별자와 유지/정리 조건을 남긴다. 공유 runtime·사용자 검수용 서버·사용자가 나중에 지우기로 한 컨테이너는 일괄 종료하지 않는다. 이미 승인된 정리는 그 범위에서 수행하며, 미승인·소유 불명·정책 거부인 정리는 추적 상태로 남긴다. 이 추적은 자원 누수나 필수 정리 실패를 숨기는 수단이 아니다. 필수 완료 조건에 포함된 정리만 해당 완료 판정에 반영한다.

Markdown은 행동 지침이며 자체로 실행을 차단하는 장치가 아니다. 실제 차단은 적용된 실행 정책·CI·권한 검사·DB identity guard 등에서 확인한다. 반복 결함을 자동 차단할 필요가 입증됐을 때만 기존 장치 보완을 검토한다. 여러 hook·전역 플러그인·별도 단계 상태 기계를 먼저 설치하지 않는다. 이후 hook을 도입한다면 적용 범위·재시도/시간 한도·실패 상태를 검증하고, 증거 누락을 조용한 성공으로 바꾸거나 끝없는 반복으로 처리하지 않는다.

## 6. 질문과 승인

### 6.1 질문하는 조건

질문은 답에 따라 사용자 결과·업무 정책·데이터·권한·외부 영향이 달라지고 현재 계약으로 결정할 수 없을 때 한다. 파일 배치·기존 패턴 활용·범위 내 결함 보정·이미 확인된 요약을 다시 묻지 않는다. 중요하지 않은 구현 선택은 기존 구조에 맞춰 진행하고 필요하면 결과에 가정을 남긴다.

새 기능의 미결정은 비교와 권장안을 묶어서 제시한다. 이미 요구사항이 충분하면 필수 인터뷰를 열지 않는다. “기획해줘”는 구현 승인이 아니고, “이대로 수정해”는 명확한 해당 범위 구현의 실행 근거다. 명시적 승인 요구가 있는 운영·게시 행동은 이 해석으로 생략하지 않는다.

### 6.2 행동별 경계

| 행동 | 제안 규칙 |
| --- | --- |
| 읽기 조사, 범위 내 문서·코드 수정, 관련 검증·결함 보정 | 해당 작업 지시로 진행. 기획만 요청한 경우 구현 제외 |
| 완료된 승인 범위 local commit | 범위·검증 확인 후 자동. 기존 사용자 승인 유지 |
| 이름을 지정한 작업의 우선 진행 | 실제 선행조건과 안전 경계가 유지되면 진행. 단순 순서 차이로 별도 재승인하지 않음 |
| 새 업무 능력·확정 정책·권한 의미 변경 | 결정이 필요한 부분만 계약 갱신 후 승인. 기존 범위 내 방법 선택과 구분 |
| 공유 runtime handover, Persistent UAT/운영 DB 변경, 실제 provider, 유료 자원 | 대상·행동·영향·복구를 구체화해 명시 승인 범위에서 실행 |
| push·PR | 명시 요청 범위에서 실행. local commit 승인과 구분 |
| main merge | 자동 검증·사용자 검수 뒤 해당 병합 명시 승인 1회 유지 |
| 공개 배포 | 대상·배포 내용·migration·복구 경계의 명시 승인 유지. merge 승인이 자동으로 배포 승인은 아님 |
| 자원 삭제·정리 | 소유·미사용·보존·명시 승인 확인. 사용자가 직접 나중에 지운다고 한 자원은 추적만 함 |

한 번 받은 승인은 동일 작업·대상·행동·환경·조건에서 재사용한다. 변경된 head가 승인한 내용과 실질적으로 달라지거나 조건이 깨졌으면 달라진 부분만 다시 확정한다. 과거 다른 Task의 포괄 승인을 새 배포나 새 데이터 작업에 이식하지 않는다.

### 6.3 현행보다 재량이 넓어지는 부분

아래는 표현 정리가 아니라 실제 정책 변경 제안이다. 제품/운영 권한이 모두 늘어나는 것으로 설명해서는 안 되며, 확대되는 종류를 구분한다.

1. **모델/구현 재량:** GPT-6 직접 구현, Sol/추론 강도 선택을 허용하고 고정 위임 의무를 제거한다.
2. **작업 순서 재량:** 선행조건을 보존하는 사용자 지정 작업을 우선 진행 지시로 인정한다.
3. **승인 절차:** 명확한 작업 지시가 있으면 별도 인터뷰 요약 확인·기획/리뷰 해결사항의 중복 승인 상태를 만들지 않는다. 신규 정책·운영·게시 승인은 유지한다.
4. **검증 재량:** 작은 가역 변경의 fresh review와 전체 suite 의무를 줄이고 영향 기반 검증을 허용한다. P0/P1·권한·DB 검증을 면제하지 않는다.
5. **증거 조회 재량:** 승인된 조사에 필요한 PR 내용·실화면 최소 관찰과 비식별 요약을 구분해 허용하는 방향이다. 현행 원문 접근 제한보다 넓어질 수 있다. 실데이터 원문 저장·외부 게시 권한은 추가하지 않는다.
6. **기록 갱신 재량:** 승인 범위의 현재 Task 계약 보정은 같은 기록에 반영한다. 과거 승인본·작성 이력 삭제 또는 새 제품 기획의 무승인 redraft는 허용하지 않는다.

Change 022의 작업 분류·위임·기록·검증 보강은 위 재량 제안의 실행 기준을 구체화한다. 강제 절차를 줄이는 부분은 실제 적용 시 에이전트의 절차 선택 재량을 넓힌다. 플러그인 설치, 교차 프로젝트 기억 조회, 공유 자원 삭제, 운영·게시 권한은 추가하지 않는다. 이번 문서 갱신 자체는 활성 권한을 바꾸지 않는다.

## 7. 개발 기록·Roadmap·프로젝트 지식

### 7.1 한 사실의 소유자는 한 곳

| 정보 | 소유 위치 | 다른 문서의 역할 |
| --- | --- | --- |
| 일반 실행·승인 원칙 | Root AGENTS | 링크, 독자적인 우선순위/승인 횟수 재정의 금지 |
| 영역별 구현 계약 | backend/frontend/scripts AGENTS | 해당 경로 변경 때 읽음 |
| 제품 방향·실행 순서·선행조건 | Roadmap | Task ID와 의존성/다음 행동을 연결 |
| Task의 현재 범위·승인·완료 상태·검증 | canonical Task 또는 최신 change의 명시된 현재 기록 하나 | Roadmap·보고서는 링크. 중복 “현재 Next” 서술 금지 |
| 제품 업무 결정 | 해당 제품 Task/ADR | 코드와 차이가 있으면 결함/정책 충돌로 처리 |
| 실행 환경·현재 owner/source·명령 | 해당 환경의 현재 SOP | 공통 Scripts 지침에 특정 실험 주소를 영구 명령으로 넣지 않음 |
| 과거 결정·승인·배포 | 기존 history/change/Decision Log | 당시 기록으로 보존하고 실행 지침으로 재활성화하지 않음 |

Roadmap은 제품 방향, 이름 있는 미완료 작업의 우선순위·선행조건, 각 작업의 현재 기록 링크를 앞에 둔다. 누적 결정과 완료 이력은 역사 영역/기존 Task로 연결한다. 같은 Task 상태를 표·본문·추적 목록 여러 곳에 복제하지 않는다. 하네스 적용 때 최신 main의 상태와 맞추며 이미 배포된 오산 등록/접근 기능을 PLANNED로 되돌리지 않는다.

실험 완료·대표 main 반영·사용자 검수·운영 배포는 구분한다. 완료된 experiment 기능을 사용자 일괄 검수 대기만으로 재구현하지 않는다. 원장과 Roadmap이 다르면 해당 기능·change를 확인해 상태부터 정리한다. 제목이 비슷하다는 이유로 서로 다른 제품 목적을 합치지 않는다.

### 7.2 기본 Task 기록

다음은 하나의 Task/change 안에서 관리한다. 이미 있는 항목을 다시 만들지 않는다.

```markdown
# <기존 Task / change — 사용자 결과>
- 목표와 요청/승인 출처:
- 현재 사실, 변경 범위와 보존할 계약:
- 완료 조건과 필요한 검증(조건부 동작은 발동 조건·기대 결과):
- 실제 변경, 완료 조건별 증거 위치·검증 기준선, 미실행 사유:
- 상태: 구현 / 자동 검증 / 사용자 검수 / 원격 반영 / 배포
- 남은 문제·다음 행동/재개 조건·진행 중 자원과 유지/정리 조건:
```

모든 작업에 SOP·manual·블로그·별도 implementation report를 만들지 않는다. 사용자 행동이 바뀌면 안내/검수 항목을, 반복 운영 절차가 바뀌면 SOP를, 제품 순서·상태가 바뀌면 Roadmap을 갱신한다. 단순 문서 수정에 무관한 산출물 다섯 개의 N/A를 반복하지 않는다.

### 7.3 하위 AGENTS 교체 내용

- **Backend:** endpoint/service/store 경계, 서버 권한, 3-DB routing/identity, transaction·멱등·동시성, main migration 수정 금지와 추가 migration 보정, 실제 provider 비호출 테스트를 유지한다. 기존/새 DB 검증은 운영/Persistent UAT와 분리한 합성 데이터 환경에서 수행한다. 전체 실행·승인·모델 규칙은 Root 참조로 바꾼다. 의미 없는 추상화나 광범위 구조 개편을 요구하지 않는다.
- **Frontend:** 기존 공용 화면 구성 재사용, 저장/중복 제출/오류 처리, 키보드 접근, 좁은 화면, 관련 UI·API 계약을 유지한다. 변경과 무관한 전체 suite는 최소값에서 제거하고 검증표를 참조한다. 화면 변경은 실제 눈으로 확인한다.
- **Scripts:** process owner/cwd/source 확인, strict port, liveness/readiness 구분, DB guard·복구·격리 자원 ownership을 유지한다. 특정 과거 실험 runtime의 자동 갱신·항상 열어 두기를 제거하고 환경 SOP로 연결한다.

공통 프로젝트 지식은 기존 Roadmap·제품 Task에 연결한다. 별도 거대한 지식 사전이나 새로운 전체 구조 문서를 추가하지 않는다. 청주 제조양식 snapshot/동기화처럼 현행 문서 안에서 충돌하는 제품 정책은 실제 change·migration을 대조하기 전 임의 단순화하지 않는다.

## 8. 테스트·화면·검토·완료

### 8.1 변경별 검증 선택

| 변경 | 개발 중 필수 확인 | 병합 시 확인 |
| --- | --- | --- |
| 문서·지침 문안 | 링크·범위·상호 모순·승인/권한 의미 검토. 실행 규칙이면 거부/허용 사례를 설계와 대조 | 문서 대상 required CI. 제품 전체 테스트를 무관하게 추가하지 않음 |
| 좁은 UI/스타일 | 관련 기존 테스트, 실제 화면의 변경 상태. 타입/번들/공통 구성에 영향 있으면 해당 검사 | 최종 후보에 해당하는 CI·사용자 검수 |
| 일반 FE/BE 동작 | 증상 재현·성공·실패·경계의 관련 테스트, 영향받는 build/typecheck/lint | 변경 범위에 맞는 회귀 |
| 로그인·사업부·부서·역할 | 허용/거부, 잔여 권한 회수, 승인 readiness, 3-DB 격리·전환의 실제 API/browser 경계 | 전용 사업부·오산 suite 포함 여부를 확인한 회귀 + 사용자 업무 검수 |
| schema/migration | 격리된 새 DB와 기존 schema/데이터 경로, catalog/ledger/identity, 실패 복구 검증 | DB 회귀·운영 적용 준비 증거 |
| 동시성·완료 상태 | 경쟁 요청, 재전송·stale version·부분 실패·원자성 반례 | 해당 domain 회귀 |
| runtime·CI·배포 script | 해당 script/분류/gate 테스트, no-provider·DB/자원 guard, 실패/복구 경로 | 실제 영향 suite와 배포 전 준비 확인 |

테스트는 구현 내용을 그대로 반복하기보다 사용자 증상·실패 반례를 검증한다. 가역적·낮은 영향의 수정에 형식적인 새 테스트를 만들지 않는다. 반대로 재현 가능한 결함이나 권한 위험의 직접 검증을 “빨리” 또는 “한 번”을 이유로 생략하지 않는다.

조건부 동작은 **발동 입력 → 해당 경로 실행 → 관측 결과**를 연결한다. 예를 들어 부서 이동 버그는 새 부서·명시 역할에서 더 이상 허용하지 않는 이전 부서의 자동 권한이 회수되는지, 사업부 격리는 잘못된 사업부 요청이 다른 DB로 넘어가지 않는지 확인한다. 앞으로 진행 기능을 구현할 때는 마지막 포장 완료와 프로젝트 자동 완료의 원자성을 검증한다. 모든 예시를 매 작업에 실행하지 않고 변경된 계약에 해당하는 사례만 선택한다. 테스트 이름이나 전체 PASS 수만으로 해당 경로가 검증됐다고 판단하지 않는다.

기존 실행 진입점을 재사용한다. Backend build/test, Frontend lint/typecheck/test/build, mock/full-stack browser 및 다음 script의 실제 대상과 옵션을 해당 Task에서 확인한다.

- `scripts/test-business-unit-isolation.sh`
- `scripts/e2e-business-unit-access-full-stack.sh`
- `scripts/e2e-osan-project-registration-full-stack.sh`
- `scripts/test-azure-pilot-release.sh`, `test-change-scope.sh`, `test-ci-gate.sh`, `test-main-pr-ci.sh`

일반 `playwright.full-stack.config.ts`는 사업부·오산 전용 spec을 제외한다. 일반 full-stack 한 번을 돌린 사실만으로 모든 사업부 검증 완료라 하지 않는다. 현재 CI의 별도 실행 목록까지 확인한다.

### 8.2 전체 회귀를 중복하지 않는 방법

사용자의 기존 지시대로 **개발 중 직접 검증 → 사용자 검수 → 최종 병합 후보의 전체 회귀 책임 실행** 순서를 기본으로 한다. 마지막 책임 실행은 CI가 맡을 수 있다. parent와 reviewer는 동일 결과를 읽으며 같은 suite를 각자 다시 실행하지 않는다.

단, required CI PASS와 제품 전체 회귀 PASS는 다르다. full-stack이 skip되었으면 실행한 것으로 기록하지 않는다. 특히 사용자에게 전체 회귀를 약속한 제품 병합은 필요한 backend/frontend/일반 full-stack/해당 전용 suite가 실제 실행됐는지 확인하고, 누락된 범위만 기존 지원 방식으로 실행한다. 문서만 변경한 병합에 제품 전체 회귀를 강제하지 않는다.

재사용 근거에는 코드 SHA/tree, 검사 범위/명령, 관련 설정·dependency·DB fixture·runtime profile, 결과를 연결한다. 코드·의존성·환경·실패 수정이 바뀌면 영향받는 결과는 다시 만든다. 관련 없는 문서 수정만 있었다고 하여 모든 테스트를 다시 수행하지 않지만 required CI를 거짓 PASS로 대체하지도 않는다. main의 PR CI 재사용은 기존 `verify-main-pr-ci.sh`의 tree·ruleset·trust source 조건을 따른다.

현재 `classify-change-scope.sh`의 일반 scripts 분기와 e2e 전용 분기 순서는 정적 검토상 확인이 필요한 후보다. 분류기가 모든 영향을 자동 판단한다고 가정하지 않는다. 이번 문서 작업에서 그 코드를 수정하거나 실행 검증하지 않았다.

### 8.3 화면 확인과 증거

청주와 동일한 UI 요청은 같은 viewport·상태에서 header/filter/summary/navigation/tools/content와 loading/empty/error를 비교한다. 공용 component를 쓴다는 코드 사실만으로 시각적 동일성을 통과시키지 않는다. 오산에서 지원하지 않는 기능은 비활성 버튼으로 무조건 복제하지 않는다.

변경 상태를 desktop과 관련 좁은 화면에서 확인한다. 합성 계정·데이터의 스크린샷을 기본 증거로 하고 중복 이미지·동영상은 만들지 않는다. 사용자가 실제 페이지 확인을 요청하면 해당 권한과 조사 목적 안에서 필요한 부분을 관찰하되, 원문 계정·사업 데이터·token을 보고서·공유 이미지에 남기지 않는다. 이 최소 실화면 관찰 허용은 현행 개인정보 지침보다 넓어질 수 있는 제안이며 아직 적용되지 않았다.

실행한 페이지나 생성한 이미지를 실제로 열어 확인한 결과를 남긴다. 문제를 고치면 바뀐 화면을 다시 보고, 관련 상태가 정상으로 확인되면 멈춘다. 기준선·화면 상태에 변화가 없는데 reviewer마다 같은 캡처를 새로 만들지 않는다. 문서에 스크린샷 경로가 있다는 사실과 누군가 실제 화면을 확인했다는 사실을 구분한다.

화면 도구 실패는 구현 실패와 구분한다. 확인하지 못한 화면을 확인했다고 하지 않고, 가능한 자동/코드 확인을 마친 뒤 시각 검증의 미완료와 이유를 표시한다. 개인정보 증거 절차를 보정하면 오염된 증거와 의존 결론만 재검증하며 무관한 제품 검증 전체를 초기화하지 않는다.

### 8.4 검토와 완료 판정

- 변경 범위의 P0/P1 또는 권한·데이터 불변조건 위반은 완료/게시를 차단한다. 영향받지 않는 독립 작업의 조사·보정은 계속한다.
- P2는 사용자 결과·계약에 미치는 영향으로 판단한다. 승인된 범위를 충족하지 못하면 보정하거나 사용자가 구체적인 잔여 위험·담당·후속을 승인해야 한다. 무관한 과거 문서 문제를 모든 제품 작업의 차단 사유로 연결하지 않는다.
- 낮은 영향의 후속 개선은 기존 Task/Finding에 기록한다. 발견할 때마다 별도 Task·계획·승인 round를 자동 생성하지 않는다.
- fresh reviewer가 필요한 범위에서는 도구가 없다고 직접 검토를 독립 검토로 이름만 바꾸지 않는다. 미완료 gate와 가능한 다음 행동을 분리한다.
- 완료 기록은 실제 변경과 완료 조건별 근거를 연결한다. CI skip, 실계정 미검수, 배포 기록 확인, 직접 운영 관측을 구분한다.
- 증거에는 해당 기준선·환경·결과 위치와 검증 주체를 연결한다. 구현자의 완료 선언, 형식 검사 통과 또는 reviewer의 결론 문구만으로 사용자 결과를 증명하지 않는다. 유효한 기존 실행 증거는 §8.2에 따라 재사용한다.

최종 사용자 보고는 무엇이 달라졌는지, 무엇으로 확인했는지, 남은 검수/제약, commit·원격·배포 상태로 충분하다. 작은 작업마다 고정된 10개 제목을 쓰거나 관련 없는 다음 제품 Task까지 조사하지 않는다.

## 9. 스킬 정리

개인 스킬 29개의 목록·트리거를 조사하고 PMS의 자율성·승인·반복 작업과 직접 관련된 본문을 상세 검토했다. 모든 개인 스킬 전문과 모든 플러그인 구현을 검증했다는 뜻은 아니다. 정확한 범위는 검토 보고서에 남긴다.

| 스킬/유형 | PMS에서 사용할 조건 | 없앨 기본 동작 |
| --- | --- | --- |
| readchk | 목표·범위가 복합적일 때 내부 이해 점검, 실제 미결정만 질문 | 명확한 지시를 매번 확인 질문으로 전환 |
| re0 | 사용자가 기존 문서·지침 정리를 요청한 경우 | 제품 버그 수정에 전체 재설계 추가 |
| openai-docs / modelchk | 모델·설정·비용 판단이 필요한 때 | 모든 Task의 모델 조사·최적화 의무 |
| sip | 선택된 중요한 산출물의 검토 필요 시 기존 검토와 통합 | 매 편집 뒤 여러 스킬을 연쇄 호출하는 자동 리뷰 |

실제 적용은 프로젝트에서 필요 없는 자동 호출을 줄이는 범위로 한다. 다른 저장소도 사용하는 `~/.agents/skills`나 bundled plugin을 일괄 편집·삭제하지 않는다. 스킬의 명시적 승인이 필요하면 기존 사용자 승인으로 충족하는지 먼저 확인하고, 충족하지 않는 실제 경계만 설명한다. 사용자가 직접 지목한 스킬은 그 요청 범위에서 적용한다.

새 PMS 전용 스킬을 미리 여러 개 만들지 않는다. 반복되는 runtime·검증·배포 절차는 우선 기존 SOP/script를 연결한다. 독립적으로 재사용할 필요가 확인된 절차만 나중에 스킬로 추출한다.

## 11. 실제 적용 순서와 종료 조건

1. **이 문서와 독립 재검토 보고 완성:** 활성 규칙과 구분하고 권한이 넓어지는 부분을 공개한다.
2. **적용할 작업 상태 정리:** 기존 WIP와 최신 main을 비교해 보존할 수정과 새 설계 차이를 확인한다. 현재 dirty 폴더를 자동 전환하지 않는다.
3. **문서 정합성 적용:** Root·관련 하위 지침·현재 안내·Task 템플릿의 소유 관계를 함께 맞춘다. 최신 제품 Task 상태는 덮어쓰지 않는다.
4. **실행 설정 적용:** 명시된 모델/도구 규칙 변경만 검증한다. 사용자 전역 설정·공용 스킬·실행 중 서버는 자동 변경하지 않는다.
5. **작은 시나리오로 검증:** 명확한 UI 수정, 권한 결함, 압축 후 재개, 정책 거부, 운영 migration 요청, 최종 병합 준비에서 불필요한 질문은 줄고 필수 경계가 남는지 확인한다. 문서 시나리오 검토와 실제 실행 검증을 구분한다.
6. **결과 기록:** 실제 적용 파일, 남은 충돌, 수행/미수행 검증과 모델/권한 영향 설명. 승인 범위 완료 시 local commit하며 원격 게시·배포는 별도 경계 유지.

이 재설계 문서의 완료 조건은 요구된 모든 하네스 영역의 설계, PMS 사실 대조, 불필요한 절차의 구체 삭제/축소안, 권한 확대 표시, 독립 검토와 그 지적 보정이다. **활성 하네스가 이미 변경됐다는 뜻은 아니다.** 적용 후 성능 개선은 실제 사용으로 검증하며 추정치를 완료 증거로 쓰지 않는다.
