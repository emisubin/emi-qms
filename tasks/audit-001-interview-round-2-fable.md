# TASK-AUDIT-001 — Deep Interview Round 2 (Fable 5)

## Round 2 안내

Round 1 질문 5개에 대해 사용자는 결정 대신 전달 방식 변경을 요청했다(`실제 사람이 질문하듯이 물어봐`). Round 2는 round 1의 blocking 결정 1~5번을 목적·선택지·권장안 변경 없이 자연스러운 대화형 질문으로 다시 제시한다. 새 blocking 결정은 추가하지 않았으며, 각 질문 끝의 답변 예시 중 하나를 고르거나 자유롭게 답하면 된다. 기준선(운영 인증은 Microsoft Entra 위임, 기존 감사 자산 4종 재사용 가능, 최신 migration `0082`로 신규 원장은 additive `0083+`)은 round 1에서 확인한 그대로다.

### 질문 1 — 로그인 기록은 어디까지 남기면 될까요?

먼저 배경을 하나 말씀드릴게요. 우리 시스템은 로그인 자체를 Microsoft(Entra)가 대신 처리해요. 그래서 비밀번호를 틀렸거나 MFA에 실패한 경우는 우리 앱까지 아예 도달하지 않아요. 앱이 스스로 100% 확실하게 남길 수 있는 건 세 가지뿐이에요 — ① 성공한 로그인, ② 앱이 거절한 접근(승인 대기·비활성 계정), ③ 명시적 로그아웃.

그래서 여쭤봅니다. **비밀번호 오류 같은 Microsoft 단계의 실패까지 우리 관리자 화면에서 보고 싶으신가요?** 그걸 포함하려면 Microsoft 쪽 기록을 주기적으로 가져오는 외부 연동을 새로 만들어야 하고(tenant 권한 승인 필요), 수집이 늦거나 중복될 수 있어서 "추정이 아닌 확정 기록"이라는 이번 Task의 성격이 약해져요. 반대로 앱이 확정할 수 있는 세 가지만 남기면 외부 연동 없이 전부 우리 transaction 안에서 확정되고, Microsoft 단계 실패는 지금처럼 Azure portal에서 따로 확인하면 됩니다.

이 답에 따라 외부 연동 추가 여부, 로그인 사건의 저장 구조, 관리자 화면의 로그인 결과 필터가 정해져요.

- **A. 앱이 확정할 수 있는 것만** (성공·앱 거절·로그아웃) — 제 권장안이에요. 승인 대기 사용자의 성공 인증도 로그인으로 기록하고, 자동 세션 갱신은 로그인으로 세지 않는 걸 함께 권장해요.
- **B. A에 더해 Microsoft 실패 기록도 연동 수집** — 한 화면에서 다 보이지만 외부 연동·지연·중복 관리가 따라와요.
- **C. 성공 로그인만** — 가장 단순하지만 거부 이력을 조사에 못 써요.

답변 예시: "A로 해주세요" / "실패까지 다 보고 싶어요, B로" / "성공만요, C".

### 질문 2 — 접속한 IP와 브라우저 정보도 저장할까요?

계정 공유나 이상한 접속이 의심될 때는 "어디서, 어떤 기기로 들어왔는지"가 좋은 단서예요. 다만 이 시스템은 개인정보를 최소한만 저장한다는 원칙을 지켜왔기 때문에, IP 같은 정보를 어디까지 저장할지 정해주셔야 해요. 이 답에 따라 원장의 저장 항목, 관리자 화면·Excel에 보이는 열, 개인정보 안내 문구가 정해집니다.

- **A. 로그인 기록에만 IP·브라우저 정보를 남기고, 데이터 변경 기록은 그 로그인에 연결만** — 제 권장안이에요. 조사 단서는 유지하면서 개인정보 원문이 저장되는 지점을 로그인 사건 하나로 최소화해요. 브라우저 정보는 원문 대신 "Chrome·Windows" 수준의 요약 저장을 함께 권장해요.
- **B. 모든 기록마다 IP·브라우저 정보를 중복 저장** — 한 건만 봐도 완결되지만, 개인정보 원문이 전체 원장에 퍼져서 최소화 원칙과 부딪혀요.
- **C. 아예 저장 안 함** — 개인정보 부담은 없지만 이상 접속 조사 단서를 잃어요.

답변 예시: "A, 요약 저장으로요" / "그래도 매번 남겨줘요(B)" / "IP는 빼요(C)".

### 질문 3 — 데이터 변경 기록은 어느 범위까지 전부 남길까요?

이번 기능의 핵심인데, 비용이 제일 갈리는 지점이라 확인이 필요해요. 우리 시스템은 프로젝트·패널·구매·자재·검사·제조·물류·영업·관리자 등 약 30개 영역이 각자 데이터를 저장하고 있고, 한 곳에서 전부 가로챌 공통 지점이 없어요. 그래서 "어디까지 기록하나"가 곧 구현·검증 비용이에요. 이 답에 따라 대상 영역 수, 항목별 기록 설계, 검증 범위, 후속 Task 필요 여부가 정해집니다.

- **A. 로그인한 사용자가 성공시킨 업무 변경 전체** — 제 권장안이에요. 이전에 전체 field-level 추적을 다른 일보다 우선하겠다고 승인해주신 방향과 일치하고, "이 화면은 추적되는데 저 화면은 안 되는" 혼선이 안 생겨요. 다만 비밀번호·token·첨부 내용·대용량 값은 서버가 허용 목록으로 걸러 기록하고, 시스템이 자동으로 바꾸는 값(알림 발송 상태 등)은 제외하기를 권장해요. 대신 구현·검증 비용은 가장 커요.
- **B. 핵심 업무 영역부터 먼저** (프로젝트·구매·자재·검사·제조·물류·영업 등), 나머지는 후속 확장 — 비용을 나눌 수 있지만, 미적용 영역은 지금처럼 "복원 불가" 공백이 남아요. 이걸 고르시면 잔여 영역 확장 Task를 바로 Roadmap에 고정해야 해요.
- **C. 관리자·권한 변경 중심 최소** — 가장 작지만 일반 업무 변경이 빠져서 이번 Task의 핵심 문제를 못 풀어요.

답변 예시: "전체로 가요, A" / "핵심부터요, B — 나머지는 후속으로" / "최소만요, C".

### 질문 4 — 실패한 저장 시도와 첨부파일은 어떻게 할까요?

두 가지가 붙어 있는데 같이 정하면 좋아요.

**4-a. 저장에 실패한 시도도 기록할까요?** 예를 들어 입력값이 잘못돼서 저장이 거절된 경우예요. 참고로 권한이 없어서 거절된 경우는 이미 별도 감사 기록이 있어요.

- **A. 새 원장에는 성공한 변경만 기록** — 제 권장안이에요. "실제로 일어난 변경"과 1:1이라 해석이 명확하고 기존 거부 감사와 중복이 없어요.
- **B. 실패 시도도 기록** — 이상 행동 탐지엔 유리하지만 기록량이 급증하고, 실패한 입력 원문에 개인정보·오입력이 섞여 들어올 위험이 있어요.

**4-b. 첨부파일 관련 행동은요?** 파일 내용 자체는 절대 저장하지 않는다는 게 확정 정책이라, 남길 수 있는 건 "누가 어떤 파일을 언제 올리고·바꾸고·지웠는지"(파일명·크기·시각) 수준이에요.

- **A. 그 metadata 수준으로 기록** — 제 권장안이에요. 파일 삭제 책임을 추적할 수 있어요.
- **B. 첨부는 아예 제외** — 단순하지만 "누가 이 파일 지웠어요?"에 답을 못 해요.

답변 예시: "둘 다 A로요" / "실패 시도도 남겨요(4-a B), 첨부는 A" 등 조합으로 답해주세요.

### 질문 5 — 관리자 화면은 기본 며칠 치를 보여주고, 기록은 얼마나 보관할까요?

전체 변경을 기록하면 이 원장이 시스템에서 제일 빨리 자라는 데이터가 돼요. 그래서 두 가지를 정해야 화면 성능 기준과 운영 절차가 확정됩니다. 기간은 화면에서 언제든 바꿀 수 있고, 날짜 경계는 기존 알림 설정 감사 조회와 같은 한국 시간 기준이에요.

**5-a. 화면을 열었을 때 기본으로 보여줄 기간은요?**

- A. 최근 7일 — 제일 빠르지만 "지난달 누가 바꿨나" 같은 흔한 문의마다 기간을 바꿔야 해요.
- **B. 최근 30일** — 제 권장안이에요. 일반적인 조사 범위와 맞고 성능·편의 균형이 좋아요.
- C. 최근 90일 — 기간 변경은 드물지만 초기 조회가 제일 무거워요.

**5-b. 오래된 기록은요?**

- **A. 기한 없이 계속 보관** — 제 권장안이에요. "감사 기록은 수정·삭제하지 않는다"는 확정 정책과 완전히 일치하고, 수년 뒤 저장량 관리는 운영을 지켜본 후 별도로 결정하면 돼요.
- B. 일정 기간(예: 1~3년) 지난 기록은 파일로 내리고 원장에서 삭제 — DB 크기는 관리되지만 "삭제하지 않는다" 정책과 충돌하고, 내린 파일의 무결성·권한 관리가 새 위험이 돼요.

Excel 내보내기는 기존 선택 export 방식을 재사용해서 지금 보고 있는 필터·선택 범위만 내보내고, 내보내기 실행 자체도 기존 export 감사로 남기는 걸 전제로 하고 있어요.

답변 예시: "30일에 무기한 보관이요(B·A)" / "7일에 무기한(A·A)" / "30일로 하되 보관은 3년만(B·B)".
