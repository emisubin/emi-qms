## 2. 목록·필터·KPI

- 상세 조회 후 돌아오면 이전 필터·검색어·페이지·스크롤 위치를 복원한다.
- 고객사·상태 필터는 복수 선택한다. 같은 필터 안에서는 OR, 서로 다른 필터끼리는 AND로 조합한다.
- KPI는 하나만 선택한다. 다른 KPI를 누르면 전환하고 선택된 KPI를 다시 누르면 해제한다. 고객사·날짜·검색 조건은 유지하며 선택 상태를 표시한다.
- 날짜 조회는 납기일 기준이다. 하루 또는 시작일~종료일 기간으로 조회할 수 있게 한다.
- 홈·진행 현황은 페이지당 50개. 프로젝트 메뉴의 페이지 크기를 임의로 바꾸지 않는다.
- 홈·진행 현황의 조회 대상·KPI 집계 기준은 동일하다. 홀드도 포함하되 아래에 배치하는 기존 계약을 유지한다. 기존 완료 프로젝트 제외 조건은 이번 변경에서 임의 변경하지 않는다.
- 홈·진행 현황의 포장완료 KPI를 공정 이상 KPI로 교체한다. 미조치 이상이 하나 이상 남아 있는 프로젝트만 계산하고, 한 프로젝트에 여러 이상이 있어도 1건이다. 조치가 모두 끝나면 제외한다.
- 프로젝트 메뉴는 완료 건까지 보존하는 전체 목록이다. 일반 프로젝트 → 납품완료 프로젝트 → 홀드 프로젝트 순으로 표시한다. 납품완료이면서 홀드인 건은 홀드 그룹에 둔다. 그룹 내부 기존 정렬은 유지한다.

## 3. 홀드·납품완료 변경 권한

- 프로젝트 메뉴의 기존 선택 제어를 사용한다. QR 출력 옆에 일괄 홀드 지정·해제 기능을 둔다.
- 일반 프로젝트는 기존 프로젝트 수정 권한을 기준으로 처리한다. 권한 범위를 이번 문서가 임의 확대하지 않는다.
- 납품완료 프로젝트는 일반 사용자의 데이터 변경을 서버에서도 차단한다. 프로젝트 정보뿐 아니라 사진·코멘트·진행 기록에도 적용한다.
- 관리자는 납품완료 프로젝트의 정보·진행 기록 수정, 반려·초기화·삭제 및 홀드 지정·해제가 가능하다. **납품완료 건의 관리자 홀드 금지라는 앞선 안은 폐기됐다.**
- 초기화는 해당 단계를 미완료로 돌리고 진행률·프로젝트 상태를 재계산한다. 기존 사진·처리 이력은 보존한다. 삭제도 기존 이력 보존 방식으로 처리한다.
- 납품완료 표시는 기존의 모든 단계 완료와 납기일 경과 기준을 유지한다. 별도 납품 확정 기능을 신설하지 않는다.
- 현재 확인한 main에는 납품완료 공통 수정 잠금이 없다. 프로젝트 수정·삭제와 단계 초기화는 관리자 권한이며, 사진·코멘트는 기존 승인 후 1회 저장 규칙이다. 이번 구현에서 새 보호 조건을 서버·화면에 일치시켜야 한다.

## 4. Gate 승인 대기·Gate 설정

### 승인 대기

- 왼쪽에 별도 `Gate 승인 대기` 메뉴를 둔다. 관리자 메뉴의 하위 항목으로 넣지 않는다.
- 관리자에게만 표시하고 서버 조회·승인 권한도 검사한다.
- 기존 사진·코멘트 수정 승인 요청 중 대기 건만 보여준다. 승인하면 목록에서 제외한다.
- 공정 진행 요청은 담당자에게 보내는 알림이므로 승인 대기 목록에 섞지 않는다. 처리 완료 조회 페이지를 추가하지 않는다.

### 단계별 완료 가능 부서

- 오산 관리자 메뉴에 `Gate 설정`을 둔다. 오산 관리자·총괄 관리자만 설정한다.
- 입고검사 → 배치검사 → 배선검사 → 8계통 → 동작검사 → 출하검사 → 포장의 각 단계에 복수 부서를 지정한다.
- 선택 대상은 제조·품질에 한정하지 않고 등록된 전체 부서다(시안 확인 중 사용자 추가 확정).
- Gate 완료·조치 완료에만 적용한다. 공정 이상 발생 등록·사진/코멘트 수정 요청 등은 기존 권한을 유지한다.
- 관리자는 지정 부서와 무관하게 완료할 수 있다. 기존 단계 순서·동작검사 예외·이상 등록 후 후속 단계 진행·미조치 이상이 있으면 포장 차단 계약은 유지한다.

## 5. 고객사 관리·프로젝트 매칭

- 오산 관리자 메뉴에 고객사 관리를 추가한다. 오산 관리자·총괄 관리자만 등록·관리한다.
- 고객사 이름 그대로 관리한다. 사업장·현장별 분류 구조를 추가하지 않는다.
- 프로젝트 생성 시 텍스트를 직접 입력하며 등록된 고객사와 연결해야 저장할 수 있다. 기존 필드 위치와 전체 페이지 구성을 유지한다.
- 입력 과정에서 매칭 후보와 실제 연결된 정식 이름을 화면에 보여준다. 생성자가 저장 전에 무엇과 연결됐는지 확인할 수 있어야 한다.
- 후보 1개는 자동 연결, 2개 이상은 팝업에서 선택, 0개는 미연결 안내와 프로젝트 등록 차단이다.
- 입력이 바뀌면 이전 연결을 무효화하고 다시 매칭한다. 클라이언트 표시뿐 아니라 서버에서도 등록 고객사 연결을 검증한다.
- 엑셀 업로드도 같은 계약을 따른다. 미매칭·복수 후보는 미리보기에서 해결하고 기존 유효 행 부분 등록 계약을 보존한다.
- 알림·프로젝트 연결은 고객사 고유 식별자로 유지한다. 이름 변경만으로 담당자 연결이 끊기지 않게 한다.
- 기존 자유 입력 이름은 목록을 조사해 중복·표기 차이를 확인한 뒤 연결한다. 비슷하다는 이유만으로 서로 다른 고객사를 자동 통합하지 않는다. 프로젝트·진행 이력을 보존한다.
- 유사도 알고리즘·입력 타이밍은 구현/시안 검증 사항이다. 앞서 제안된 최소 2글자·별칭 정책은 확정된 별도 기능으로 취급하지 않는다. 후보·연결 표시와 선택 흐름을 실제 레퍼런스로 검토한다.

## 6. 담당 고객사·알림 수신

- 사용자↔고객사는 다대다 관계다. 관리자 메뉴에서 담당 고객사를 복수 지정한다.
- 기존 사용자 전환 시 당시 등록 고객사를 모두 배정한다. 신규 가입자도 가입 시점의 등록 고객사를 모두 배정한다.
- 이후 신규 고객사가 등록되면 모든 사용자에게 미배정으로 시작하고 관리자가 추후 지정한다. 모든 고객사 선택 상태가 미래 고객사 자동 구독을 의미하지 않는다.
- 일반 사용자·오산 관리자·총괄 관리자 모두 같은 배정 규칙을 적용한다. 미배정 고객사 업무 알림은 수신하지 않는다.
- 메일·푸시·인앱 모두 동일 적용한다. 기존 관리자 공통 알림 설정의 켜기/끄기도 함께 존중한다.
- 직접 지정한 공정 진행 요청과 본인 관련 반려 알림은 고객사 배정 제한에서 제외한다. 이 예외가 기존 채널 설정·수신 대상 권한을 무시하는 뜻은 아니다.
- 프로젝트 조회 권한은 담당 고객사와 무관하게 유지한다. 부서·사업부 서버 권한은 보존한다.

## 7. 공지사항·첨부·팝업

- 왼쪽 메뉴 맨 아래에 다른 메뉴와 간격을 두고 공지사항을 독립 배치한다. 오산 사용자 모두 조회·등록 가능하다.
- 작성자는 본인 글 수정·삭제, 오산 관리자·총괄 관리자는 모든 글 수정·삭제가 가능하다. 삭제 이력을 보존한다.
- 관리자는 중요 공지를 상단 고정하고 게시글을 팝업으로 지정할 수 있다.
- 읽음 상태는 계정별로 관리한다. 팝업 표시 이력과 읽음 상태를 구분해 관리하고, 다른 기기에서도 같은 팝업을 반복하지 않는다.
- 팝업은 지정된 공지에 대해 계정별 한 번 표시한다. 단순 글 수정으로 다시 표시하지 않는다. 관리자가 `다시 알리기`를 실행하면 계정별 한 번씩 재표시한다.
- 게시글 등록에 따른 메일·푸시·인앱 알림을 발송하지 않는다. 공지 팝업과 메뉴의 읽음 표시는 별개다.
- 자동 업데이트 공지를 포함한 모든 글에 첨부 가능: 최대 10개, 파일당 20MB, 게시글 총 100MB. 이미지·PDF·Office·한글 문서·ZIP 허용, 기존 파일 보안 검사 적용.
- 첨부 다운로드에도 공지 조회 권한과 삭제 상태를 적용한다. 확장자만으로 파일을 허용하지 않는다. 실제 허용 형식 목록·크기 단위의 바이트 환산·검사 불가 파일 처리는 기존 업로드 계약과 대조해 명시한다.

## 8. 공개배포 공지·서버 저장 차단

- 앞으로 공개배포 때마다 업데이트 공지를 자동 등록한다. 변경 기능·사용 방법·저장 차단 시작 및 종료 예정 시간을 안내한다. 내부 코드·로그를 사용자 공지에 노출하지 않는다.
- 배포 전에 영향을 받는 사이트에 팝업을 계정별 한 번 표시하고 서버 데이터 변경을 잠시 차단한다. 공통 배포는 청주·오산·부스바의 실제 영향 범위에 적용한다. 공지사항 메뉴 신설 자체는 오산 범위다.
- 등록·수정·삭제를 화면에서만 막지 않고 서버에서도 막는다. 조회는 가능한 범위에서 유지한다.
- 팝업을 닫아도 상단에 저장 제한 안내를 유지한다. 저장 시 일반 오류 대신 업데이트 중임과 완료 후 재시도 필요를 명확히 알린다.
- 작성 중 내용은 보존한다. 자동 새로고침·자동 저장하지 않으며 종료 후 사용자가 다시 저장한다.
- 예정 시간이 변경되면 변경 안내를 계정별 한 번 더 표시한다. 배포가 지연되면 지연 안내와 차단을 유지한다. 예정 시간 경과만으로 자동 해제하지 않는다.
- 실제 배포 완료·정상 동작을 확인한 후 제한을 해제한다. 실패·복구 상황에서도 실제 상태와 맞게 공지를 갱신한다.
- 구현 전 반드시 진입 중 요청, 여러 서버 간 상태 전파, 배경 작업·실제 외부 전송, 배포 제어 자체의 예외 범위를 설계한다. 차단 활성화 전에 시작된 쓰기와 migration의 경합을 방치하지 않는다.
- 이 정책은 배포 기능의 요구사항이다. 이번 문서 작성 요청이 실제 배포·운영 저장 차단·실제 공지 발송을 승인하는 것은 아니다.

## 8-1. 사용자 동작별 상세 흐름

### A. 목록을 탐색하고 돌아오기

1. 고객사 여러 개와 상태 여러 개, 납기일 범위, 검색어를 입력한다.
2. KPI 하나를 선택하면 다른 필터 조건을 유지한 채 해당 조건을 함께 적용한다.
3. 프로젝트/진행 상세를 확인하고 뒤로 돌아오면 같은 조회 조건·페이지·스크롤 위치를 복원한다.
4. 선택 KPI를 다시 누르면 KPI 조건만 해제한다. 다른 KPI를 누르면 그 KPI로 교체한다.
5. 필터에 따라 대상이 달라져도 홈과 진행 현황이 서로 다른 업무 집계를 만들지 않게 공통 기준을 사용한다.

### B. 여러 프로젝트에 홀드 부여

1. 프로젝트 목록의 기존 체크 기능으로 대상을 선택한다.
2. QR 출력 옆의 홀드 기능을 사용한다. 기존 홀드 사유·변경 이력 계약을 보존한다.
3. 서버가 대상별 권한·납품완료 상태·동시 변경 여부를 확인한다.
4. 일반 사용자는 납품완료 건을 변경하지 못한다. 관리자는 납품완료 건도 홀드 처리한다.
5. 처리 후 목록과 KPI를 갱신하고 홀드 건은 맨 아래로 이동한다. 선택 범위 밖의 프로젝트는 변경하지 않는다.

### C. 고객사를 입력해 프로젝트 생성

1. 생성자가 고객사명 텍스트를 입력한다. 처음부터 긴 전체 고객사 목록에서 골라야 하는 UI를 강요하지 않는다.
2. 현재 입력에 대한 등록 고객사 후보와 연결 상태를 바로 보여준다.
3. 후보가 하나면 정식 이름으로 연결됐음을 표시하고 생성자가 확인할 수 있게 한다.
4. 후보가 여러 개면 선택 팝업에서 하나를 고른다. 팝업을 닫기만 한 것을 선택으로 간주하지 않는다.
5. 후보가 없거나 선택하지 않았다면 저장을 막고 관리자 등록/선택이 필요함을 안내한다. 자유 입력 문자열로 신규 고객사를 자동 생성하지 않는다.
6. 고객사 입력을 다시 바꾸면 이전 연결을 재사용하지 않는다. 최종 저장 시 서버가 연결 유효성을 다시 검증한다.

### D. 담당 고객사 설정과 알림

1. 관리자에게 고객사 목록과 사용자별 배정 상태를 보여준다.
2. 기존 사용자 전환 및 신규 가입에서는 그 시점의 전체 고객사를 배정한다.
3. 그 이후 고객사 C를 신규 등록하면 기존 사용자들은 C에 미배정이다. 담당자를 관리자가 지정한 뒤 C의 업무 알림 수신 대상에 포함된다.
4. 아무 고객사도 배정하지 않은 사용자는 고객사 기반 알림을 받지 않는다. 직접 지정된 공정 진행 요청과 본인 반려는 배정과 관계없이 기존 수신 정책을 따른다.
5. 담당에서 제외돼도 프로젝트를 못 보게 만들지 않는다. 총괄 관리자에게 무조건 전체 고객사 알림을 보내는 과거 예외는 새 정책에서 적용하지 않는다.

### E. 공지 작성·팝업·읽음

1. 사용자가 하단 공지사항 메뉴에서 글과 첨부를 등록한다.
2. 본인 글만 수정/삭제할 수 있고 관리자는 모든 글을 처리할 수 있다. 서버가 작성자를 검증한다.
3. 관리자가 글을 상단 고정하거나 팝업으로 지정할 수 있다. 게시만으로 메일·푸시·인앱 알림을 발송하지 않는다.
4. 지정 팝업을 본 계정에는 같은 팝업을 다음 접속/다른 기기에서 다시 띄우지 않는다.
5. 본문 수정은 기존 표시 이력을 초기화하지 않는다. 관리자가 다시 알리기를 실행해야 새 1회 표시 대상으로 전환한다.
6. 삭제한 글의 처리 이력은 남긴다. 삭제 글이나 첨부가 다른 직접 주소에서 권한 없이 노출되지 않게 한다.

### F. 공개배포와 작성 중 화면

1. 배포 시작 전에 업데이트 내용·저장 차단 예정 구간을 자동 공지한다.
2. 열려 있는 화면에도 업데이트 상태가 전달돼야 한다. 배포 중 처음 접속한 사용자에게도 현재 상태를 안내한다.
3. 서버 저장 차단이 적용된 동안 등록·수정·삭제는 실행하지 않는다. 버튼 잠금만으로 처리하지 않는다.
4. 사용자가 작성 중이던 값을 보존하고, 안내 팝업을 닫아도 상단 상태 안내는 유지한다.
5. 예정 시간 변경 시 변경 안내를 새로 한 번 표시한다. 지연/실패 시 일반 저장 오류처럼 보이지 않게 실제 상태를 안내한다.
6. 배포와 정상 확인을 마친 뒤 서버 차단을 해제한다. 자동 제출하지 않고 사용자가 다시 저장하도록 한다. 다른 사용자가 데이터를 바꾼 경우 기존 충돌 검사를 유지한다.

## 8-2. 확정 정책과 구분할 구현 확인 사항

아래는 사용자 정책을 추가 확정한 것으로 간주하지 않는 설계·현행 코드 대조 항목이다. 정책대로 구현 가능한 것은 담당자가 결정하며, 새로운 권한·외부 영향·데이터 손실 위험이 생길 때만 해당 쟁점을 질문한다.

- KPI 숫자를 고객사/날짜/검색 조건에 따라 재집계하는 정확한 방식과 수동 상태 필터와의 표시 관계를 현재 화면과 대조한다. 홈·진행 현황 동일 기준과 KPI 단일 선택은 필수다.
- 월 빠른 선택을 유지할지와 달력 구성은 기존 디자인 재사용 여부로 결정한다. 납기일 일자/기간 조회는 확정 사항이다.
- 일괄 홀드의 일부 실패 표시·재시도 단위는 기존 일괄 처리 계약과 대조한다. 전체 무조건 성공 또는 무조건 원자 처리로 이미 확정됐다고 하지 않는다.
- 기존 수정 권한과 현재 관리자 전용 서버 경로의 관계를 확인한다. 정책 문구만으로 일반 사용자에게 프로젝트 수정 권한을 새로 부여하지 않는다.
- 고객사 표기 정규화·매칭 유사도·중복 등록 방지·이름 변경/사용 중지 처리·기존 데이터 연결 계획을 설계한다. 별칭/고객사 통합 전용 UI를 자동 추가하지 않는다.
- 기존 고객사 목록 확정/초기 사용자 전체 배정/신규 가입/신규 고객사 등록이 동시에 일어날 때 기준 시점을 일관되게 적용한다.
- 첨부 20MB/100MB의 정확한 바이트 한도와 허용 확장자, 압축 파일 검사, 실패/격리/다운로드 계약은 기존 공용 업로드와 대조한다. 사진 전용 기존 한도를 모든 첨부에 그대로 적용하지 않는다.
- 계정별 읽음과 팝업 표시 이력의 저장 시점 및 여러 기기 동시 접속 처리를 설계한다. 읽지 않은 개수 배지의 구체 디자인은 시안 검토 사항이다.
- 자동 공지 작성자·배포 식별자·재시도 중복 방지·예정 시간 입력 경로·실패 시 해제 책임·운영 알림/worker 범위를 설계한다. 운영 공지 제어까지 차단돼 복구할 수 없는 구조를 피한다.

## 9. 디자인 확인과 후속 순서

1. 최신 제품 main·현행 AGENTS·관련 Task·실제 메뉴/화면/권한을 대조한다. 다른 WIP·runtime은 보존한다.
2. 기존 디자인/공용 구성을 재사용할 수 있는지 확인한다. 기존 디자인이 있으면 시안을 중복 제작하지 않는다.
3. 새 시안 필요 후보: 고객사 매칭 입력·복수 후보 선택, 담당 고객사 관리, Gate 승인 대기·설정, 공지 목록/작성/첨부/팝업, 배포 안내. 이는 시안 확정 목록이 아니라 실제 재사용 여부를 조사할 목록이다.
4. 새 시안은 UI·UX 제작 가이드와 실제 운영 사이트 사례 각각 최소 1개를 확인하고 적용 근거·직접 링크를 보고한다. 이번 문서 작성에서는 시안이나 레퍼런스 조사를 수행하지 않았다.
5. 확정 디자인에 맞춰 기존 Task 후속 구현, 영향 검증, 사용자 검수로 이어간다. 원격 병합·공개배포는 해당 시점의 명시 승인 후 진행한다.

### 시안으로 먼저 확인할 최소 범위와 순서

1. **프로젝트 생성의 고객사 입력 부분**: 기존 생성 양식 유지, 입력 전/후보 없음/1개 자동 연결/복수 선택 팝업/선택 후/텍스트 재수정 상태. PC와 모바일 확인. 첫 번째로 진행할 시안이다.
2. **오산 관리자 기능의 새 편집 부분**: 고객사 등록, 사용자별 담당 고객사 선택, Gate별 부서 선택. 기존 목록/선택 패턴을 유지하며 관계와 편집 상태만 확인한다.
3. **공지 관리자 제어와 일반 공지 팝업**: 기존 글 작성·첨부 배치는 유지. 고정/팝업 지정/다시 알리기와 계정 1회 팝업을 확인한다.
4. **업데이트 안내 팝업·상단 배너**: 예정 저장 차단 시간, 진행 중/시간 변경/지연/완료, 작성 내용 유지 상태를 확인한다.

필터의 체크 선택·날짜 입력, KPI 선택 표시, QR 옆 홀드 버튼, 승인 대기 목록, 하단 메뉴는 기존 디자인을 재사용하는 변경이다. 이 부분을 별도 대시보드 재디자인 시안으로 만들지 않는다. 새 관리자/독립 승인/공지 메뉴의 위치는 위 시안 공통 탐색 틀에서 함께 확인한다.

새 시안을 만들기 직전에 제작 가이드와 실제 운영 사이트 레퍼런스를 확인하고 출처를 기록한다. 컴포넌트 데모만 보고 실제 운영 사례를 확인했다고 표현하지 않는다. 합성 고객사/사용자/프로젝트 데이터만 사용한다. 이번 단계까지 제품 구현·새 시안 제작·제품 테스트·원격 반영·공개배포는 수행하지 않았다.

- 시각·동작 확인: PC 1440×1000, 모바일 390×844 설정에서 단일 연결과 복수 선택 팝업을 직접 관찰했다. 모바일 문서 가로 넘침 없음(clientWidth/scrollWidth 모두375). 복수 선택 취소 시 등록 차단, 선택 후 시안 등록 메시지, 재입력 미등록 시 차단을 브라우저에서 확인했다. 한글 조합 중 Enter가 선택을 실행하지 않도록 방어했다. 실제 모바일 키보드/IME 기기 검증은 미실시다.
- 상태: 첫 시안 작성·직접 확인 완료, 사용자 디자인 확정(2026-09-24). 제품 기능 구현·자동 제품 회귀·원격 반영·공개배포는 미실시. 다음 시안은 제12절의 고객사 관리·담당 배정·Gate 부서 편집 부분이다.

- 배포 절차: 최종 모의34개 시나리오 통과, Bash 구문·ShellCheck·actionlint·Azure 산출물 정적 검사 통과. Bicep 컴파일과 실제 Azure 실행은 하지 않았다. 코드/DB변경 모두 차단을 선행하며 prepare/activate/complete 실패·rollback 경로를 모의 검증했다.
- 준비 상태 보정: 일반 실행에서도 DB가 준비되지 않으면 /health/ready가503을 반환한다. 기존에는 payload만 degraded이고 HTTP200이었다. Azure 내부 readiness probe가 이를 반영하며, 변경 테스트와 최종 로컬 준비 상태200을 확인했다. 최종 독립 검토에서 migration-only 경로의 배포 후 준비 상태 확인 누락을 발견했으며, 제한 해제 CLI가 전체 DB 준비 상태를 직접 확인하도록 보정했다. 추가 격리 DB 검증4개(완료 직전 ledger 변경 시 거부, 준비 상태·정보 비노출 재검증)도 통과했다. DB-only migration은 기존 이미지의 ledger와 호환되지 않으므로 어떠한 운영 변경보다 앞서 거절하도록 script/workflow를 보정했고 독립 재검토에서 해당 P1 해결을 확인했다.
- 최종 로컬 API5281 재시작 후 DB 준비200, 프런트5258 응답200. 테스트 유지보수는 종료된 상태이며 운영 차단·실제 메일/푸시·원격 작업 없음.
- 작성자와 분리된 프런트/공지/배포 경로 검토에서 계정 전환 팝업, StrictMode 표시 손실, 일정 변경 팝업 버전, drain 잠금 해제 문제를 보정했다. 사용자 제품 검수는 다음 단계이며 전체 제품 최종 후보 회귀와 required CI는 병합 후보에서 별도 수행한다.


### 20-5. 공지 읽음 표시 보정·승인 대기 화면 안내

- 로컬5258 반영. 원격/배포 없음.

### 20-13. 배포 일시 중단·업데이트 공지 양식 우선

- 사용자가 원격 병합·배포를 요청했으나 바로 후속 요청으로 중단하고, 공지 우선 규칙과 업데이트 양식 확정을 먼저 지시했다. 원격 fetch/상태 조회까지만 진행, push/PR/merge/운영 변경/배포 없음.
- Root AGENTS에 배포 요청→확정 양식의 공지 작성·게시→병합·배포 순서를 추가. 초기 양식 확정 대기 기록은 아래 최종 확정으로 갱신한다. 게시 기능이 없는 첫 배포를 게시 완료로 가장하지 않으며 최초 전환 방식을 따로 정한다.
- 독립 배포 검토: 기존 이미지에는 maintenance CLI가 없어 현재 스크립트의 사전 prepare/activate를 수행할 수 없음. 새 이미지로만 교체해 우회하는 것도 구버전 worker 차단·미적용 DB 문제를 해결하지 못함. 최초 전환 절차는 양식 확정 뒤 재개할 선행 작업으로 유지.

### 20-14. 업데이트 공지·별도 팝업 최종 정책 확정

- 사용자 확정: 제목 `YYYY.MM.DD 업데이트 공지`, 쉬운 기능 제목+설명, 이용 안내, 마지막 `박수빈 올림`. 공지 본문 일시·대상 삭제, 완료/일정 변경 안내 문장 삭제. 확정 양식은 `docs/development/update-notice-template.md`가 소유한다.
- 배포 지시 시 공지 작성·게시→별도 업데이트 팝업 활성화 확인→병합·배포. 배포 전 서버 저장 차단·요청 종료, 정상 확인 후 재개. 일반 공지사항 팝업은 중복으로 자동 띄우지 않는다.
- 이번 요청은 규칙 기록이며 운영 공지·팝업 활성화나 배포 재개를 실행하지 않았다. 팝업 본문/중복 안내 코드 보정 및 최초 운영 도입 경로 해결은 남아 있다. 20-13의 최초 전환 제약을 그대로 유지한다.
- 문서 diff 및 공지/팝업 역할·양식 정합성 확인. 제품 코드 변경 없으므로 제품 테스트는 실행하지 않았다.
