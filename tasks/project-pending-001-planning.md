# TASK-PROJECT-PENDING-001 구현 계획

- 작성자: Codex
- 유형: `APPROVED_FEATURE_IMPLEMENTATION`
- 승인 근거: 사용자가 후속 작업 1·2를 한 Task로 묶고 Fable 없이 Codex가 기획·구현하도록 명시 승인
- 기준선: `origin/main` `af796547ffb260ae427932a4734894af23c21ae6`

## 사용자 문제

1. 영업이 프로젝트를 등록할 때 사내 업무번호인 LSE TASK NO를 함께 기록할 수 없고 상세에서도 확인할 수 없다.
2. Pending 화면에서 우리 부서가 처리해야 할 항목만 바로 보기 어렵고, 현재 처리 중인 항목과 종결된 항목의 구분도 한눈에 들어오지 않는다.

## 구현 계약

### LSE TASK NO

- 프로젝트 생성 화면의 `프로젝트 기본 정보`에 선택 입력 한 칸을 추가한다.
- 값은 앞뒤 공백을 제거하며 최대 100자다. 빈 값은 `null`로 저장한다.
- 프로젝트 수정 화면에서 계속 변경할 수 있고 변경 사유와 함께 감사 이력에 남긴다.
- 프로젝트 상세 기본정보에 표시하며 빈 값은 `-`로 표시한다.
- 기존 프로젝트는 migration 후에도 빈 값으로 정상 조회한다.
- 이번 범위에서 목록 검색·Excel import/export 열은 추가하지 않는다.

### 우리 부서 Pending과 상태군

- 새 메뉴를 만들지 않고 기존 Pending 화면 첫 조회 조건에 `조회 범위`와 `처리 상태`를 둔다.
- 조회 범위는 `우리 부서`, `전체`이며 우리 부서는 서버가 로그인 사용자의 부서를 직접 조회해 판정한다. 클라이언트가 임의 부서 코드를 전달하지 않는다.
- Pending에 조치 부서가 있으면 그 부서를 우선하고, 없으면 지정 담당자의 부서를 사용한다.
- 처리 상태는 `오픈`, `종결`, `전체`다. 오픈은 기존 세부 상태 중 `Closed`가 아닌 모든 상태다.
- 전체 Pending 화면에서 운영 부서 사용자의 기본값은 `우리 부서 + 오픈`이다. 시스템 관리자 또는 운영 부서가 없는 사용자는 `전체 + 오픈`이다.
- 특정 프로젝트의 Pending으로 들어온 경우에는 그 프로젝트의 타 부서 Pending도 놓치지 않도록 `전체 + 오픈`을 기본값으로 사용한다.
- 기존 상태·유형·긴급도 필터는 유지한다. 상태군과 충돌하는 세부 상태는 화면에서 자동 해제한다.
- 프로젝트 대시보드는 현재 조회 조건에 해당하는 Pending이 있는 프로젝트만 표시한다.
- 카드에는 `오픈` 또는 `종결` 구분을 기존 세부 상태와 별도로 표시한다.

## UI 원칙

- 현재 흑백 와이어프레임의 입력칸, 선택창, 일반 테두리와 간격을 재사용한다.
- 좌측 색상선, 굵은 강조선, 그라데이션 강조, 신규 강조색을 추가하지 않는다.
- 390px 모바일에서는 조회 범위와 처리 상태를 먼저 보이고 나머지 세부 조건은 기존 필터 sheet에서 조정한다.
