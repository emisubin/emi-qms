- delivery worker는 재시도 예약, terminal Failed, dry-run 발송과 관리자 재처리 상태를 이미 구분한다. 알림 상세 웹 경로 `/teams/activity/notifications/{id}`가 `NotificationLinkBuilder`로 이미 생성된다.

### 질문 1 — 푸시 권한 요청을 언제, 어떤 진입점에서 시작하는가

- 필요한 이유: 브라우저 푸시 권한은 사용자 gesture 없이 요청하면 차단되기 쉽고, 특히 iPhone은 설치형 PWA 안에서 사용자 행동으로만 요청할 수 있다. “사용자 동의 없는 강제 권한 요청”은 이미 제외 범위이므로, 남는 결정은 안내를 언제 보여주고 어디에서 요청을 시작하는가다.
- 답변이 바꾸는 범위: 설치형 PWA 첫 실행 안내 UI의 존재 여부, 알림 설정 화면의 진입점 구성, 권한 거절·나중에 하기 상태의 재안내 정책과 UAT 시나리오.

| 선택지 | 설명 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A. 설치형 PWA 첫 로그인 후 앱 내 사전 안내 1회 + 설정 화면 상시 진입점 | 설치형 PWA에서 인증·앱 shell 준비 뒤 “푸시 켜기” 안내를 한 번 보여주고, 사용자가 버튼을 누를 때만 브라우저 권한 요청을 시작한다. 닫으면 다시 자동으로 띄우지 않고 알림 설정에서 언제든 켤 수 있다 | 발견 가능성과 opt-in 원칙을 모두 충족. 기존 PWA 설치 안내의 “인증 뒤 자동 안내 + session 닫기” 패턴을 재사용 | 안내 dialog·재안내 억제 상태 관리가 추가됨 |
| B. 알림 설정 화면에서만 수동 opt-in | 자동 안내 없이 설정 화면에 켜기 버튼만 둔다 | 구현 최소, 안내 피로 없음 | 현장 사용자가 기능 존재를 모르면 켜지 않아, 모바일 알림 누락 문제 해결이라는 Task 목적 달성이 불확실 |
| C. 로그인 직후 매번 안내 | 허용 전까지 로그인할 때마다 안내를 반복 | 전환율 최대 | 안내 피로·반복 거절 유도로 브라우저 영구 차단 위험. 무동의 요청 제외 취지와 긴장 |

- 권장안: **A**. 설치형 PWA에서만 자동 안내를 열고(브라우저 탭에서는 설정 진입점만 노출), 요청 자체는 항상 사용자 버튼 클릭으로 시작한다. iPhone 요구사항과 기존 `PwaInstallExperience` 안내 패턴에 가장 자연스럽게 맞는다.

### 질문 2 — 사용자가 PWA 푸시를 끌 수 있는 범위를 어디까지 두는가

- 필요한 이유: 확정 정책은 “PWA 푸시는 인앱 알림과 일치”다. 그런데 기존 알림 설정은 Teams 개인·메일 채널의 이벤트별 on/off를 제공하고 긴급 항목은 해제 불가로 잠근다. Web Push를 같은 이벤트별 preference 체계에 넣을지, 기기 구독 단위 on/off만 둘지에 따라 데이터 모델·설정 UI·발송 필터가 달라진다.
- 답변이 바꾸는 범위: 알림 설정 화면의 Web Push 항목 구성, preference taxonomy 확장 여부, 발송 시 수신자 필터 로직과 감사 기록 범위.

| 선택지 | 설명 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A. 기기 구독 단위 on/off만 | 켜면 그 기기에서 인앱 알림 전체를 푸시로 받고, 끄는 방법은 기기별 구독 해제뿐. 이벤트별 세분화 없음 | “인앱과 일치” 정책과 정확히 일치. 인앱에도 이벤트별 preference가 없으므로 체계가 단순·일관 | 특정 이벤트만 끄고 싶은 사용자는 전체를 꺼야 함 |
| B. 기기 구독 + 사용자 단위 전체 일시 끄기 | A에 더해 알림 설정에서 “모든 기기 푸시 일시 끄기” 스위치를 제공 | 기기 여러 대를 한 번에 제어. 구독은 보존되어 다시 켜기 쉬움 | 상태 축이 하나 늘어(기기 활성 × 사용자 스위치) 안내·검증 조합 증가 |
| C. 기존 preference처럼 이벤트별 on/off | Web Push를 이벤트 단위 항목으로 taxonomy에 추가 | 세밀한 제어 | “인앱 알림과 일치” 확정 정책과 어긋나는 파생 정책 생성. 긴급 잠금 항목과의 정합 등 설계·감사 부담이 가장 큼 |

- 권장안: **A**. 이번 Task의 확정 정책(인앱 일치, 최소 채널)과 가장 정합적이다. 여러 기기 일괄 제어가 실제로 필요하다고 판단되면 B를 선택해도 인앱 일치 정책은 보존된다. C는 권장하지 않는다.

### 질문 3 — 여러 기기 구독 관리와 만료·해제 lifecycle을 어떻게 확정하는가

- 필요한 이유: 한 사용자가 Android·iPhone·PC 등 여러 기기를 가질 수 있고, 구독 endpoint는 브라우저 사정으로 수시로 만료·갱신된다. 사용자가 관리할 수 있는 범위(현재 기기만 vs 본인 전체 기기 목록)와 서버의 자동 비활성 기준을 정해야 데이터 모델·설정 UI·발송 정리 로직이 확정된다.
- 답변이 바꾸는 범위: 구독 저장소의 조회·해제 API 표면, 알림 설정 화면의 기기 표시 범위, 만료 구독 자동 비활성 규칙과 자동 검증 시나리오.

| 선택지 | 설명 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A. 현재 기기만 관리 + 서버 자동 정리 | 각 기기에서는 그 기기의 구독 상태 확인·해제만 제공한다. 서버는 push service가 구독 소멸을 알리면(만료·해지 응답) 해당 구독을 즉시 비활성하고, 반복 실패 구독도 비활성 사유와 함께 정리한다. 계정 비활성 시 발송 대상에서 제외 | API·UI 표면이 최소. 구독 secret 노출 표면도 최소 | 분실·교체한 옛 기기의 구독을 다른 기기에서 끌 수 없음(다만 만료·실패 정리로 자연 소멸하고, payload는 인앱 수준 요약이라 노출 위험이 제한적) |
| B. 본인 기기 목록 조회·원격 해제 | 알림 설정에서 본인 구독 기기 목록(등록 시점·마지막 성공 등)을 보고 개별 원격 해제 가능 | 분실 기기 즉시 차단, 상태 가시성 좋음 | 목록·원격 해제 API와 기기 식별 표시(이름 붙이기 등) 설계가 추가되어 최소 범위를 넘음 |

- 권장안: **A**. “최소 Web Push channel” 권장 범위와 일치하고, 서버 자동 정리(구독 소멸 응답 즉시 비활성 + 사유 기록)가 lifecycle의 실질 위험을 처리한다. 분실 기기 원격 차단이 업무상 필요하면 B를 선택하되 후속 확장으로 분리하는 것도 가능하다.

### 질문 4 — 푸시에 어떤 내용을 싣고 클릭 시 어디로 이동시키는가

- 필요한 이유: 푸시는 기기 잠금 화면에 인증 없이 표시된다. “인앱보다 자세한 민감 내용 금지”는 확정됐지만, 인앱 알림 제목 수준을 실을지 완전 일반 문구로 할지는 미확정이다. 클릭 이동도 기존 알림 상세 경로를 쓸지 업무 화면으로 바로 보낼지에 따라 Service Worker click handler와 라우팅 범위가 달라진다.
- 답변이 바꾸는 범위: 푸시 payload 구성 규칙, 잠금 화면 노출 범위, notification click handler의 이동 대상, 미인증 상태 클릭 시 로그인 후 복귀 흐름과 검증 항목.

| 선택지 | 설명 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A. 인앱 알림 제목 수준 요약 + 클릭 시 해당 인앱 알림 상세로 이동 | payload는 인앱 알림의 제목·짧은 요약까지만 싣고, 클릭하면 기존 `/teams/activity/notifications/{id}` 상세로 이동한다. 상세 화면이 인증·본인 확인을 강제하고, 업무 화면 이동은 상세의 기존 링크를 재사용 | 어떤 알림인지 바로 식별 가능. 이동 대상이 단일 경로라 인증·권한 검사가 기존 화면에 위임되어 안전·단순 | 잠금 화면에 업무 제목 수준 문구가 노출됨(인앱 이상의 상세는 싣지 않음) |
| B. 일반 문구(“새 업무 알림이 있습니다”) + 클릭 시 알림 목록 | payload에 업무 내용을 전혀 싣지 않는다 | 잠금 화면 노출 최소 | 어떤 알림인지 몰라 열람 동기가 약해지고, 목록에서 다시 찾아야 해 “해당 업무로 바로 이동” 목표가 약화됨 |
| C. 업무 화면으로 직접 deep link | 클릭 시 알림 상세를 거치지 않고 대상 업무 화면으로 이동 | 이동 단계 최소 | 알림 유형별 대상 경로 매핑을 푸시 계층에 중복 구현해야 하고, 권한·삭제된 대상 등 예외 처리가 분산됨 |

- 권장안: **A**. Stage 18 등 메일 전용 event가 애초에 대상이 아니고 인앱 원본이 source of truth이므로, 인앱 제목 수준 요약과 알림 상세 단일 진입이 확정 정책·보안 경계와 가장 잘 맞는다. 잠금 화면에 업무 제목 노출도 피하고 싶다면 B를 선택해 달라.

### 질문 5 — 신규 구독 적용 시점과 운영 rollout·중지 경계를 어떻게 확정하는가

- 필요한 이유: interview 6장은 “허용 이후 새 인앱 알림부터 적용” 방향을 질문으로 남겼다. 또한 실제 provider key·운영 발송은 별도 승인 경계이므로, 그 전 단계의 검증 방식(기존 dry-run 상태 재사용 여부)과 운영 중 채널만 끄는 kill switch를 확정해야 rollout·rollback 계획을 쓸 수 있다.
- 답변이 바꾸는 범위: 구독 활성 시점과 delivery 생성 조건, 서버 설정 기반 채널 활성/중지 방식, 검증 단계(dry-run→실기기)와 rollback 절차, Implementation report의 운영 전 checklist.

| 선택지 | 설명 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A. 구독 활성 이후 새 알림만 + 설정 기반 채널 kill switch + dry-run 선검증 | 구독이 활성화된 이후 생성되는 인앱 알림에만 Web Push delivery를 만든다. 서버 설정으로 Web Push delivery 생성만 전역 중지할 수 있고(기존 채널 무영향), 실제 provider 승인 전에는 기존 delivery worker의 dry-run 상태로 발송 경로를 검증한다 | 소급 푸시 금지·실패 격리·별도 provider 승인 경계라는 기존 확정 사항과 모두 정합. 기존 worker의 Disabled/DryRunSent 상태를 재사용 | 구독 직전 생성된 알림은 푸시되지 않음(인앱·Teams·메일로는 계속 전달) |
| B. 구독 시 최근 미확인 알림 일부 소급 발송 | 켜는 순간 최근 미확인 인앱 알림 몇 건을 함께 푸시 | 켠 직후 체감 가치 | “기존 알림 소급 푸시 금지” 제외 후보와 충돌하고 소급 범위·중복 억제 규칙이 새로 필요 |

- 권장안: **A**. 소급 없음은 이미 제외 후보로 기록된 방향이므로 A를 확정하고, 운영 rollout은 “코드 반영 → dry-run 검증 → 별도 승인 후 운영 VAPID key·실발송 활성 → Android·iPhone 실기기 검수” 순서로 planning에 고정하는 것을 권장한다.
