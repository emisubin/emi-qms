## 주요 사용자 원문

> 이번에 시범 운영하는 오산은 제조 시스템은 그대로 사용하되, 이름을 제조로 하지 않을거야.

> 제조 시스템의 우리 아이템별 제조 양식에 넣는 제조 항목에 넣는 느낌으로 가면 될 것 같아.

> 마지막 7단계 포장 단계가 완료 되면 프로젝트도 자동 완료.

모든 대상의 포장이 완료돼야 한다는 확인에 사용자는 “네”라고 답했다.

> 중단 기능은 없어. 펜딩 기능을 오산에는 아직 넣지 않을거니까.

프로젝트 생성 항목은 다음 사용자 입력으로 확정했다.

1. 프로젝트 title
2. 프로젝트 코드
3. 거래처
4. PO No
5. W/O No
6. 납기일
7. 제품명 (자유 텍스트)
8. 수량

이 8개 입력·공통 7단계·수량별 대상·전체 포장 시 자동 완료 요약에 사용자는 “네”라고 답하고 기획 시작을 요청했다.

## 기획 승인과 DB 재확인

대화 기획 초안은 입력 필수 여부(PO/W/O 선택), 오산 내 프로젝트 코드 중복 차단, 앞 6단계 완료 후 포장 허용을 권장안으로 제시했다. 이후 사용자가 승인한 “지금한 오산 기획”의 근거 초안에 포함된 사항으로 기획안에 보존한다. 현장 사용 검수 완료를 뜻하지 않는다.

> 아 아니야 db는 분리하고 서버는 하나로 써도 무방해.

DB 개수와 Azure 서버 구매·과금의 차이를 설명한 뒤 최종 요청:

> 오케이 좋아. 지금한 오산 기획 승인. 문서화 하고 task 단위로 나눠서 개발 로드맵까지 작성해줘.

이는 승인된 업무 기획의 문서화·Task 분해·개발 Roadmap 등록 지시다. 이후 추가되는 세부 구현 권장안, 독립 review resolution, 실제 제품 구현·게시·운영 적용 승인과 구분한다.

## 정상·실패 흐름과 후속 경계

정상 흐름은 소속/업무 권한 확인 → 8개 정보로 프로젝트 생성 → 진행 시작/단계 기록 → 전체 포장 완료 → 현황판 완료다. 저장 오류·재시도·동시성·무권한 요청의 기술적 처리는 기획안의 검증 가능한 불변조건으로 설계한다. 오산 현장에 아직 없는 별도 검사 성적서·불량 판정·펜딩·물류 증빙·외부 발송을 추정해 추가하지 않는다.

승인된 핵심 업무에 blocking 질문은 없다. 사용자별 실제 권한 배정, 운영 자원 용량·접속 비밀값·실제 개통 시점은 운영 Task의 입력이며 이 문서에 개인정보나 secret을 기록하지 않는다.
