# TASK-QUALITY-OPERATING-MODEL-001 Change 005 — Deep Interview Round 2 (Fable 5)

- taskType: `NEW_FEATURE`
- interviewOwner: `FABLE_5`

## Round 2 기준선 확인

Round 1은 검사 방식을 범용 3-mode 선택 문제로 추상화해 사용자가 무효 처리했다. Round 2는 interview 문서 0.1의 재조사와 실제 코드·기존 현장 조사를 기준선으로 다시 작성했다. 확인한 사실은 다음과 같다.

- 실제 IQC 대상은 외함·판금류·부스바·명판 네 종류다. 네 종류 모두 육안 확인 대상이지만 공식 수입검사서를 보관하는 대상은 현재 외함뿐이고, 외함은 협력사 종이 검사서를 품질팀이 추가 확인·서명한 스캔본으로 판정하는 정책이 이미 확정·구현돼 있다.
- 현재 코드에서 `CategoryBased` 프로젝트는 구분의 `IQC 필요`가 켜져 있으면 category와 무관하게 항상 외함형 스캔 검사로 생성된다. 따라서 판금류의 `IQC 필요`만 켜면 구분별 상세검사가 아니라 외함 스캔 검사로 잘못 연결된다.
- 구매품 저장 시 구분 id·code·표시명·`IQC 필요`가 구매품에 snapshot되고, 도착 이력이 생긴 구매품은 구분 변경이 차단된다. 상세검사의 검사 항목은 검사 회차 생성 시점의 활성 양식 version으로 고정된다.
- 전역 `MATERIAL_IQC` 상세 양식은 migration `0067` 이전 `AllReceipts` 프로젝트에만 사용되며, `CategoryBased` 프로젝트의 판금류·부스바·명판은 이 양식을 한 번도 사용한 적이 없다.
- 현재 구매품 구분 관리(생성·수정·`IQC 필요` 토글 포함)는 시스템 관리자 또는 품질 부서 활성 사용자가 수행할 수 있다. 반면 Change 004의 Item별 LQC 운영 상태 변경은 시스템 관리자 전용으로 확정됐다. 같은 양식 관리 영역 안에 서로 다른 두 권한 계약이 공존한다.

다음은 이번 round에서 질문하지 않는 항목이다. 0.1 재조사에서 확인된 방향을 그대로 따른다: 기존 상세 IQC 엔진(항목·사진·판정·PDF·부적합 Pending·재검사) 재사용, 양식 관리의 "대상 선택 → 현재 양식 관리" UX와 검색·필터 재사용, 전역 `MATERIAL_IQC`의 legacy 프로젝트 전용 보존, `AllReceipts` 기존 프로젝트의 현행 전역 상세검사 유지.

아래 5개 질문은 모두 구현 범위를 직접 바꾸는 blocking 결정이다.

### 질문 1 — 스캔형 검사는 외함 전용으로 고정하는가

**필요한 이유**: 협력사가 종이 검사서를 동봉하고 품질팀이 서명 스캔본으로 판정하는 운영은 현재 외함 협력사와의 실제 업무 방식이다. 구분별 설정을 만들 때 "스캔형"을 외함에 고정된 기존 동작으로 보존만 할지, 다른 구분도 선택할 수 있는 방식으로 노출할지에 따라 설정 값 집합과 화면이 달라진다.

**답변이 바꾸는 범위**: 구분별 설정의 값 집합(검사 안 함/상세형 2택 + 외함 고정 vs 3택), 도착 등록 시 검사 생성 분기, 양식 관리 화면의 방식 표시.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A (권장) | 외함은 기존 스캔형 그대로 고정 보존하고, 그 외 구분은 `검사 안 함 / 상세 체크리스트형` 중 하나만 선택 | 실제 업무(종이 검사서 동봉은 외함 협력사만)와 정확히 일치하고, 확정된 외함 정책이 설정 실수로 바뀔 여지가 없음 | 이후 다른 협력사도 종이 검사서 동봉 운영을 시작하면 그때 기능 확장이 필요 |
| B | 모든 구분이 `검사 안 함 / 스캔형 / 상세형` 세 방식을 자유 선택 | 향후 스캔형 운영 확산에 미리 대응 | 현재 확인된 업무 요구에 없는 확장이고, 외함 정책을 실수로 변경할 수 있는 경로가 생김 |

권장안은 A다. 재조사에서 범용 3-mode는 사용자 요구에서 확인되지 않은 과도한 확장 후보로 판단됐고, 필요해지는 시점에 additive로 확장할 수 있다.

### 질문 2 — 상세형 구분의 검사 항목은 무엇에서 시작하는가

**필요한 이유**: 판금류·부스바·명판은 지금까지 전역 `MATERIAL_IQC` 양식을 사용한 적이 없고 서로 검사 내용도 다르다. 상세형으로 켠 구분의 양식이 비어 있는 상태로 도착분이 등록되면 검사할 항목이 없으므로, 시작점과 빈 양식 방지 규칙을 확정해야 한다.

**답변이 바꾸는 범위**: 구분별 양식 데이터의 초기 생성 규칙, 상세형 전환·양식 저장의 validation, 도착 등록 시 오류 처리.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A (권장) | 빈 양식에서 시작하되, 검사 항목이 1개 이상 저장돼 있어야 해당 구분을 상세형으로 켤 수 있고, 상세형인 동안에는 항목 0개 저장을 차단 | 구분마다 실제 검사에 맞는 항목만 입력하게 되고, 빈 양식 검사와 임의 fallback이 구조적으로 불가능 | 구분마다 항목을 처음부터 입력해야 함 |
| B | 상세형 전환 시 전역 `MATERIAL_IQC` 현재 양식을 복제해 시작 (LQC Change 004의 초기 복제와 유사) | 빈 화면이 아닌 상태에서 시작 | 복제되는 항목은 legacy 전 품목 공용 항목이라 판금류·부스바·명판의 실제 검사와 맞지 않아 대부분 지우고 다시 작성해야 함 |

권장안은 A다. LQC는 모든 Item이 기존 공통 양식으로 실제 검사되던 상태라 복제가 맞았지만, 이 구분들은 전역 양식을 사용한 이력이 없어 복제가 도움이 되지 않는다.

### 질문 3 — 이번 작업에서 판금류·부스바·명판 검사를 실제로 켜는 것까지 포함하는가

**필요한 이유**: 기존 현장 조사에서 사용자는 판금류·부스바·명판도 각각 기준을 만들어 기록을 남기는 방안을 검토하고 싶다고 밝혔다. 이번 산출물이 "구분별 양식 기능 제공"까지인지, 세 구분의 실제 검사 항목을 사용자에게 받아 등록하고 상세형으로 켜는 운영 적용까지인지에 따라 검증·검수 범위와 필요한 사용자 입력이 달라진다.

**답변이 바꾸는 범위**: migration 이후 초기 상태, 구현·검증 시나리오의 데이터, 사용자 검수 checklist, 이번 작업에서 사용자가 제공해야 하는 검사 항목 목록 여부.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A (권장) | 기능만 제공한다. migration·초기 상태는 현재 동작 그대로(외함=스캔형, 나머지=검사 안 함) 두고, 실제 검사 항목 등록과 상세형 전환은 이후 품질팀이 화면에서 수행 | 배포 시점 실동작 변화가 없어 안전하고, 검사 기준 확정을 기다리지 않고 기능을 완료할 수 있음 | 기능 완료 후 품질팀이 항목을 등록하기 전까지 세 구분은 계속 검사 없이 입고됨 |
| B | 이번 작업에서 세 구분의 실제 검사 항목을 사용자에게 받아 등록하고 상세형까지 켠 상태로 마무리 | 완료 즉시 세 구분의 검사가 시작됨 | 세 구분의 검사 기준 확정이 선행돼야 해서 그 확정이 늦어지면 작업 전체가 지연되고, 기준 자체는 시스템이 아니라 품질팀이 정할 내용 |

권장안은 A다. B를 원하면 세 구분 각각의 검사 항목 목록(항목명·필수 여부·사진 필수 여부·응답 형식)을 답변에 함께 제공해야 한다.

### 질문 4 — 이미 저장된 구매품에 새 설정이 적용되는 시점

**필요한 이유**: 현재 계약은 구매품 저장 시 구분과 검사 여부를 snapshot으로 고정한다. 이 계약을 그대로 따르면, 판금류를 상세형으로 켜도 진행 중 프로젝트에 이미 저장된 판금류 구매품의 이후 도착분은 계속 검사 없이 입고된다. 사용자가 이 결과를 의도하는지 확정해야 도착 등록 분기와 운영 안내를 설계할 수 있다.

**답변이 바꾸는 범위**: 구매품·도착분의 방식 snapshot 설계, 도착 등록 transaction 분기, "설정을 바꾸면 언제부터 적용되는가" 운영 안내와 검증 시나리오. 두 선택지 모두 검사 항목 내용은 기존 상세검사와 동일하게 검사 회차 시작 시점의 해당 구분 현재 양식으로 고정하고 확정 후 불변으로 보존하며, 이미 시작·확정된 회차는 바꾸지 않는다.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A (권장) | 기존 snapshot 계약 유지: 검사 방식은 구매품 저장(수정 저장 포함) 시점의 구분 설정으로 고정. 이미 저장된 구매품은 기존 동작을 유지하고, 설정 변경 후 새로 저장·수정한 구매품부터 적용 | 구매팀이 저장 시 확인한 검사 여부와 실제 검사가 항상 일치하고, 기존 구분 snapshot·비소급 계약과 정확히 같은 구조라 변경이 최소 | 진행 중 프로젝트의 기존 구매품에 새 검사를 적용하려면 구매팀이 해당 구매품을 다시 저장해야 함 |
| B | 검사 방식을 도착 등록 시점의 현재 구분 설정으로 결정 | 설정을 켜면 진행 중 프로젝트의 다음 도착분부터 바로 검사 시작 | 구매 저장 시 안내된 검사 여부와 실제가 달라질 수 있고, 구매품 snapshot 계약을 바꾸는 더 큰 변경이며 설정 변경이 소급처럼 보이는 혼란이 생김 |

권장안은 A다. 잘못된 설정은 과거를 고치지 않고 이후 적용분부터 보정한다는 기존 복구 원칙과도 일치한다.

### 질문 5 — 구분별 검사 방식 변경 권한

**필요한 이유**: 현재 구매품 구분 관리(`IQC 필요` 토글 포함)는 품질 부서 사용자와 시스템 관리자가 수행할 수 있지만, Change 004에서 Item별 LQC 운영 상태 변경은 시스템 관리자 전용으로 확정됐다. 이번 구분별 검사 방식(검사 안 함↔상세형)은 사실상 기존 `IQC 필요` 설정을 대체·확장하므로 어느 계약을 따를지 확정해야 API 권한과 화면 활성 조건을 설계할 수 있다.

**답변이 바꾸는 범위**: Backend 권한 검사, 감사 기록 주체, 방식 선택 UI의 disabled 조건, 기존 구분 관리 화면 권한과의 정합.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A (권장) | LQC와 동일한 분리: 방식 변경(검사 안 함↔상세형)은 시스템 관리자 전용, 품질 부서는 방식 조회와 검사 항목 편집 | "검사를 생략한다"는 고위험 결정의 통제 기준이 LQC와 일관되고, 같은 양식 관리 영역의 권한 규칙이 하나로 정리됨 | 현재 품질 부서가 직접 바꾸던 `IQC 필요` 설정보다 통제가 강해져 방식 변경마다 관리자 개입이 필요 |
| B | 현행 구분 관리 계약 유지: 품질 부서 사용자가 방식과 검사 항목을 모두 변경 | 현재 화면 권한과 동일해 운영 변화가 없음 | 검사 생략 전환이 관리자 통제 없이 가능해 Change 004에서 확정한 LQC 기준과 어긋남 |

권장안은 A다. A를 선택하면 기존 구분 관리 화면의 `IQC 필요` 토글 권한도 새 방식 설정과 같은 기준으로 정리하는 범위를 planning에 포함한다.
