# TASK-AUDIT-001 — Deep Interview Round 3 (Fable 5)

## Round 3 안내

Round 2 사용자 답변(`4번 실패한 저장 시도는 실패 시도도 기록한다. 나머지는 모두 권장안으로 진행`)을 interview 문서 기준으로 확인했다. 결정 1·2·3·4-b·5-a·5-b는 모두 권장안으로 확정됐고 새 질문이 없다. 다만 결정 4-a에서 사용자가 권장안 대신 **실패한 저장 시도도 기록**을 선택하면서, round 1에서 위험으로 표시했던 두 가지 하위 경계가 미확정 blocking 결정으로 새로 열렸다 — ① 실패 사건에 무엇을 저장하는가(실패한 입력 원문의 개인정보 유입 위험), ② 어떤 실패까지 기록하는가(기존 권한 거부 감사 `authorization_audit_events`와의 역할 분담 포함). 이 두 가지는 원장 schema·개인정보 정책·계측 범위를 직접 바꾸므로 Fable이 임의로 확정할 수 없다. 아래 두 질문에 답해주시면 다음 round에서 확인용 요약을 출력한다.

### 질문 1 — 실패한 저장 시도 사건에는 어떤 내용까지 저장할까요?

- 필요한 이유: 성공한 변경은 검증을 통과한 값만 field allowlist로 기록하지만, **실패한 시도의 입력값은 검증을 통과하지 못한 원문**이에요. 예를 들어 비밀번호를 엉뚱한 칸에 붙여넣어 저장이 거절된 경우, 그 시도값을 기록하면 비밀번호 원문이 감사 원장에 들어가요. 그런데 결정 5-b에서 원장은 **기한 없이 append-only로 보관하고 수정·삭제하지 않기로** 확정했기 때문에, 한 번 유입된 비밀·오입력 원문은 영구히 지울 수 없어요. "비밀번호·token·인증 헤더는 절대 기록하지 않는다"는 확정 불변조건과 정면으로 부딪히는 지점이라 저장 범위를 먼저 정해야 해요.
- 답변이 바꾸는 범위: 실패 사건의 schema(시도값 컬럼 유무), 개인정보 검토 결과와 운영 SOP 문구, 관리자 상세 화면·Excel에 보이는 내용, 서버의 실패 사유 분류 설계.

| 선택지 | 설명 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A. metadata와 실패 사유만 기록, 시도한 입력값은 미저장 | 행위자, 대상 영역·행동, 확인 가능한 대상 key, 실패 종류와 서버가 만든 사유 요약(예: "필수값 누락", "동시 수정 충돌"), 시각, 로그인 correlation만 저장 | "누가 언제 무엇을 시도해 왜 실패했는지"는 전부 답할 수 있고, 검증 안 된 원문·비밀이 영구 원장에 유입될 경로가 없음 | "어떤 값을 넣으려다 실패했는지"는 조회 불가 |
| B. A에 더해 시도한 field 값도 성공 사건과 같은 allowlist로 기록 | 성공 변경과 동일한 field projection을 실패 시도에도 적용 | 시도 내용까지 완결 조회 가능 | allowlist는 field 단위 필터라, 허용된 field에 잘못 붙여넣은 비밀·개인정보 원문은 걸러지지 않음. 무기한 append-only 정책상 사후 제거 불가 |

- 권장안: **A**. 실패 시도 기록의 목적(반복 실패 패턴·이상 행동 조사)은 metadata와 사유 분류만으로 성립하고, 삭제 불가 원장에 미검증 원문을 넣는 위험은 확정 불변조건과 양립하기 어려워요. 답변 예시: "A로요" / "시도값도 남겨요, B".

### 질문 2 — 어떤 실패까지 "실패한 저장 시도"로 기록하고, 기존 권한 거부 감사와는 어떻게 나눌까요?

- 필요한 이유: round 2 답변의 "validation 등"이 열려 있어요. 저장 실패에는 입력값 거절(validation) 외에도 동시 수정 충돌(다른 사용자가 먼저 저장), 중복 요청 거절, 서버 내부 오류가 있고, 권한 거부는 이미 별도 감사(`authorization_audit_events`)가 기록하고 있어요. 어디까지가 신규 원장 사건인지에 따라 계측 범위·기록량·화면 필터가 정해집니다.
- 답변이 바꾸는 범위: 전 도메인 실패 계측 지점 수, 실패 종류 분류 체계, 기존 권한 거부 감사와의 중복 여부, 관리자 화면의 실패 필터와 표시 범위.

2-a. 신규 원장에 기록할 실패 종류:

| 선택지 | 설명 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A. 사용자의 저장 의도가 거절된 경우 전체 | validation 실패 + 동시 수정 충돌 + 중복 요청 거절. 서버 내부 오류(5xx)는 제외하고 기존 오류 로그·운영 관찰이 담당 | "사용자가 시도했지만 반영되지 않은" 경계와 1:1이라 해석이 명확. 조사 목적(반복 실패 패턴)에 충분 | 서버 오류로 인한 실패는 신규 화면에서 안 보임(오류 로그로 확인) |
| B. A에 더해 서버 내부 오류도 기록 | 5xx 실패도 사건으로 append | 사용자 관점 실패를 빠짐없이 한 화면에서 조회 | 장애 시 오류 폭주가 원장을 급증시키고, 원장 기록 자체도 같은 장애로 실패할 수 있어 완결성을 보장 못 함 |
| C. validation 실패만 | 동시 충돌·중복 거절은 제외 | 가장 작음 | 같은 "저장 안 됨" 문의인데 실패 종류에 따라 보이거나 안 보여 조사 시 혼선 |

2-b. 기존 권한 거부 감사와의 분담:

| 선택지 | 설명 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A. 기록은 기존 감사에 그대로 두고, 신규 관리자 화면에서 권한 거부도 함께 조회 표시 | 권한 거부는 지금처럼 `authorization_audit_events`에만 기록(중복 저장 없음)하고, 신규 화면이 읽기 전용으로 합쳐 실패 종류 필터의 하나로 보여줌 | 이중 기록 없이 "실패 시도 전체"를 한 화면에서 조사 가능 — 실패 시도를 남기기로 한 취지와 일치 | 신규 화면 조회가 두 원장을 함께 읽어야 함(조회 구현 비용 소폭 증가) |
| B. v1 신규 화면은 신규 원장 사건만 표시 | 권한 거부는 기존 테이블 유지, 화면 통합은 후속 결정 | 화면 범위 최소 | validation 실패는 보이는데 권한 거부는 안 보여 "실패 시도 조회"가 반쪽이 됨 |

- 권장안: **2-a는 A, 2-b는 A**. 사용자가 실패 시도를 남기기로 한 목적이 조사이므로, "사용자 의도가 거절된" 경계 전체를 기록하고 권한 거부는 중복 저장 없이 화면에서만 합쳐 보여주는 조합이 취지·비용 균형이 가장 좋아요. 답변 예시: "둘 다 A로요" / "validation만요(2-a C), 화면 통합은 나중에(2-b B)".
