# TASK-QUALITY-OPERATING-MODEL-001 Change 005 — Deep Interview Round 1 (Fable 5)

- taskType: `NEW_FEATURE`
- interviewOwner: `FABLE_5`
- interviewRound: 1
- 질문 수: 5

## Round 1 기준선 확인

현재 Repository에서 확인한 사실은 다음과 같다.

- 구매품 구분 catalog(`material_categories`)는 `IQC 필요/없음`(`requires_iqc`) boolean만 가지며, 초기 구분은 외함(필요), 판금류·부스바·명판·기타(불필요)다. 구분 관리는 `양식 관리 > 구매품 구분·IQC 연결` 화면에 있다.
- 프로젝트는 migration `0067`의 불변 `iqc_routing_policy` snapshot(`AllReceipts`/`CategoryBased`)을 가진다. `CategoryBased` 프로젝트에서 IQC 필요 구분의 도착분은 항상 외함형 스캔 성적서(`ScanBased`)로 생성되고, `AllReceipts`(기존) 프로젝트는 전역 `MATERIAL_IQC` 현재 양식 하나로 상세(`Detailed`) 검사를 생성한다. 즉 지금은 "구분별로 다른 상세 체크리스트"를 선택할 수단이 없다.
- 구매품 저장 시 구분명과 `requires_iqc`는 구매품에 snapshot되고, 검사 방식은 도착 등록 시점에 프로젝트 routing policy로 결정된다. 상세 검사 양식 내용은 검사 회차 생성 시점의 활성 version으로 고정된다.
- Change 004는 Item별 LQC에서 `설정 테이블 + 운영 상태(시스템 관리자 전용) + Item별 현재 양식 + append-only audit + optimistic concurrency + 비소급 snapshot` 패턴을 확립했다. 이번 기능의 자연스러운 재사용 기반이다.

아래 5개 질문은 interview 문서 7장이 사용자 확정 대상으로 지정한 검사 mode 구성, 외함 스캔형 보존, 적용 시점, 기존 프로젝트 처리, 편집 권한에 해당하며 모두 구현 범위를 직접 바꾸는 blocking 결정이다.

### 질문 1 — 구매품 구분별 IQC 운영 방식의 구성

**필요한 이유**: 현재는 구분에 `IQC 필요/없음`만 있고, IQC 필요 구분은 신규 프로젝트에서 무조건 외함형 스캔 성적서로 검사된다. 구분마다 "어떤 종류의 검사를 하는가"를 저장하려면 운영 방식의 값 집합과 선택 자유도를 먼저 확정해야 한다.

**답변이 바꾸는 범위**: 구분 설정의 데이터 구조, 도착 등록 시 IQC 생성 분기, 양식 관리 화면의 구분별 설정 UI 전체.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A (권장) | 구분마다 `검사 대상 아님 / 스캔형 성적서 / 상세 체크리스트형` 중 하나를 단일 운영 방식으로 선택. 모든 구분이 세 방식 모두 선택 가능하며 초기값은 현재 동작 그대로(외함=스캔형, 나머지=검사 대상 아님) | 향후 어떤 구분이든 스캔형·상세형 자유 선택 가능, 현재 동작이 기본값으로 보존됨 | `IQC 필요/없음` boolean을 방식 enum으로 확장하는 migration·화면 변경 폭이 조금 큼 |
| B | `IQC 필요/없음`을 유지하고, 필요인 구분에만 검사 형태(스캔형/상세형) 하위 선택을 추가 | 기존 개념 유지로 변화가 작음 | 두 단계 설정이라 화면·검증 분기가 늘고, 결국 A와 같은 정보를 두 필드로 관리 |
| C | 스캔형은 외함 전용으로 고정하고 다른 구분은 `검사 대상 아님 / 상세형`만 선택 | 스캔형 계약 보호가 명확 | 외함 외 협력사 종이 성적서 스캔 운영이 생기면 다시 기능 변경 필요 |

권장안은 A다. 단일 방식 필드가 검증·감사·snapshot을 가장 단순하게 만들고 현재 외함 운영을 기본값으로 정확히 보존한다.

### 질문 2 — 외함 스캔형과 전역 MATERIAL_IQC 양식의 지위

**필요한 이유**: 외함 스캔형(회차별 스캔 첨부·시스템 PDF 미생성)은 Roadmap 확정 정책이고, 전역 `MATERIAL_IQC` 상세 양식은 기존(`AllReceipts`) 프로젝트가 계속 사용한다. 구분별 상세 양식이 생긴 뒤 이 전역 양식을 계속 편집 가능하게 둘지, 구분별 양식의 시작점을 무엇으로 할지 확정해야 한다.

**답변이 바꾸는 범위**: 양식 관리 catalog 구성(전역 IQC 편집기의 존치 여부), 구분별 양식의 초기 데이터 생성 규칙, 기존 프로젝트 검사에 대한 영향 경계.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A (권장) | 전역 양식은 기존 프로젝트 전용으로 계속 편집 가능하게 유지하고, 상세형을 선택한 구분의 초기 양식은 전역 현재 양식을 복제해 시작 (Change 004의 LQC 초기 복제와 동일) | 기존 프로젝트 검사 운영이 그대로 유지되고, 구분별 양식이 빈 화면이 아닌 실사용 항목에서 출발 | 전역 양식과 구분별 양식이 병존해 "어느 양식이 적용되는가" 안내가 필요 |
| B | 전역 양식 편집을 동결(조회만)하고, 상세형 구분 양식은 빈 양식에서 새로 작성 | 앞으로의 편집 진입점이 구분별 하나로 단순해짐 | 기존 프로젝트 검사 항목을 더 이상 보정할 수 없고, 구분마다 항목을 처음부터 다시 입력해야 함 |

권장안은 A다. 기존 프로젝트 비소급·보존 불변조건과 충돌하지 않으면서 입력 부담이 가장 작다.

### 질문 3 — 구분 설정과 검사 양식의 적용(고정) 시점

**필요한 이유**: "저장된 연결에 맞는 검사"가 되려면 운영 방식과 양식 version이 어느 시점의 값으로 고정되는지 확정해야 한다. 현재 계약은 구분명·IQC 필요 여부는 구매품 저장 시, 상세 양식 내용은 검사 회차 생성 시 고정이다.

**답변이 바꾸는 범위**: 구매품·도착분 snapshot 컬럼 설계, 도착 등록 transaction, "양식을 고쳤는데 언제부터 반영되는가"라는 운영 안내 전체.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A | 구매품 저장 시점에 운영 방식과 양식 version을 모두 구매품에 고정 | 발주 시점 기준이 명확하고 이후 설정 변경에 완전 비소급 | 발주~도착 사이에 발견된 양식 오류·개선이 해당 도착분에 반영되지 않음 |
| B (권장) | 운영 방식은 구매품 저장 시점 snapshot을 따르고, 검사 양식 version은 도착분 IQC 생성 시점의 현재 양식으로 고정. 이미 시작·확정된 회차는 불변 | 기존 구분 snapshot·회차 양식 snapshot 계약과 정확히 같은 구조라 변경이 최소이고, 잘못된 양식을 "이후 도착분부터 새 현재 양식으로 보정"하는 복구 원칙과 일치 | 같은 구매품의 도착분끼리 검사 항목이 다를 수 있어 회차별 양식 version 표시가 필요 |
| C | 프로젝트 생성 시점에 전 구분의 방식·양식을 프로젝트에 일괄 고정 (LQC Change 004 방식) | 프로젝트 단위 불변이 가장 단순 | 구매품은 프로젝트 생성 한참 뒤에 추가되고 구분 catalog도 늘어나므로, 생성 이후 신설 구분·양식 개선을 그 프로젝트에서 쓸 수 없음 |

권장안은 B다. LQC는 프로젝트 고정이 맞았지만, IQC는 구매·도착이 장기간 이어지는 흐름이라 기존 IQC 계약과 같은 "구매품 방식 + 회차 양식" 이중 고정이 실무에 맞다.

### 질문 4 — 기존 프로젝트에 대한 적용 범위

**필요한 이유**: 기존 프로젝트는 두 집단이다. `AllReceipts`(전 도착분 전역 상세 검사)와 `CategoryBased`(0067 이후, IQC 필요 구분 스캔형). 구분별 설정이 어느 집단의 이후 도착분부터 적용되는지 확정해야 migration과 도착 등록 분기를 설계할 수 있다.

**답변이 바꾸는 범위**: migration backfill 규칙, 도착 등록 시 routing 분기, 검증 시나리오(정책 혼재 프로젝트) 범위.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A | 완전 비소급: 기존 두 정책 프로젝트 모두 현행 동작 유지, 이번 기능은 migration 이후 생성 프로젝트에만 적용 | 경계가 가장 단순하고 안전 | 진행 중 `CategoryBased` 프로젝트는 새 구분을 만들어도 상세 검사를 쓸 수 없어 기능 효과가 늦게 나타남 |
| B (권장) | `CategoryBased` 프로젝트는 이후 새 도착분부터 구분별 설정을 적용하고, `AllReceipts` 기존 프로젝트는 현행 전역 상세 검사를 유지 | 초기값이 현재 동작과 동일해 migration 시 실동작 변화가 없고, 진행 중 프로젝트도 새 구분 설정의 효과를 받음. 확정·진행 중 회차는 불변 | 같은 프로젝트 안에서 시점에 따라 검사 방식이 달라질 수 있어 이력 표시가 필요 |
| C | 모든 기존 프로젝트의 새 도착분부터 적용 (`AllReceipts` 포함) | 적용 규칙이 하나로 통일 | 기존 프로젝트의 확립된 전역 상세 검사 운영이 바뀌어 비소급 불변조건과 충돌 소지 |

권장안은 B다. `CategoryBased`는 이미 구분 기반 routing이므로 초기값(외함=스캔형, 나머지=검사 대상 아님)이 현재 동작을 그대로 보존하면서 이후 설정 변경만 앞으로 반영된다.

### 질문 5 — 운영 방식 변경과 검사 항목 편집 권한

**필요한 이유**: Change 004의 LQC는 "운영 상태 변경은 시스템 관리자 전용, 품질 양식 관리자는 조회와 검사 항목 편집"으로 확정했다. IQC 구분별 설정에도 같은 분리를 적용할지 확정해야 API 권한과 화면 disabled 상태를 설계할 수 있다.

**답변이 바꾸는 범위**: Backend 권한 검사, 감사 기록 주체, 양식 관리 화면의 방식 선택 UI 활성 조건.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A (권장) | LQC와 동일: 운영 방식(검사 대상 아님/스캔형/상세형) 변경은 시스템 관리자 전용, 품질 양식 관리자는 방식 조회와 상세 검사 항목 편집만 가능 | 검사 생략·방식 전환이라는 고위험 결정과 일상적 항목 유지보수를 분리하고 LQC와 규칙이 일관됨 | 방식 변경마다 시스템 관리자 개입 필요 |
| B | 품질 양식 관리자가 운영 방식과 검사 항목을 모두 변경 가능 | 품질 부서가 자율적으로 운영 | "검사 대상 아님" 전환 같은 결정이 관리자 통제 없이 가능해져 LQC와 권한 기준이 어긋남 |

권장안은 A다. 두 화면이 같은 `양식 관리` 안에 있으므로 권한 규칙이 다르면 혼란이 커진다.
