## 1. 결론과 조사 범위

문서 감사에서 확인한 주요 비용 유발 후보는 **동일 사실의 중복 소유, 모든 작업에 큰 절차 적용, 고정 모델 분업, 읽기 작업까지 겹치는 실행 승인 조건**이다. 실제 비용 기여도는 측정하지 않았다. 개선안은 작은 실행 지침, Task 한 곳의 현재 계약, 위험에 맞는 모델/검증, 특수 환경에만 적용하는 SOP다.

두 읽기 전용 감사가 문서 규칙과 PMS 구현을 나누어 조사했고 parent가 재설계안을 작성했다. 아래 파일:줄은 별도 표시가 없으면 작성 시점 **현재 작업 폴더**의 내용이다. `origin/main` 표시가 있으면 원격 추적 ref의 source이며 같은 로컬 경로의 줄과 혼동하지 않는다.

| 범위 | 확인 수준 |
| --- | --- |
| Root·하위 AGENTS, README, START_HERE, 종료 정책, 검증표, 개인정보 증거, 모델 workflow, 현재 governance Task와 관련 템플릿 | 현재 규칙 본문·상호 참조 대조 |
| Roadmap·experiment 원장·Decision Log | 전체 구조/현재 큐·상태 대조. 역사와 활성 규칙 분리 |
| 다수 과거 Task Markdown | 목적·충돌·관련 승인/구현 기록 중심 검색 및 해당 본문 확인. 모든 과거 Task 전문을 읽었다고 주장하지 않음 |
| 제품 코드·DB·CI·runtime script | 원격 main의 사업부/승인/프로젝트 코드, 전용 검증과 최신 배포 문서 대조. 실행 테스트는 하지 않음 |

| 전역 설정·스킬/플러그인 | 모델/effort/승인/sandbox의 필요한 설정만 확인. 공용 플러그인 전문과 전역 rules 내용은 전체 감사하지 못함 |

## 2. 실용 영향순 지침 문제와 편집안

### 1) 실행 지침의 우선순위가 두 개다

- 인용: [README.md](../../README.md) 194~200줄의 “1. 승인된 ADR / 2. AGENTS.md”; [AGENTS.md](../../AGENTS.md) 11~20줄의 Source of truth.
- 영향: 과거 ADR과 현재 실행 지시 중 어느 것을 따라야 하는지 달라져 작업을 멈추거나 잘못된 정책을 선택할 수 있다.
- 편집: README의 독자 우선순위를 지우고 Root를 참조한다. 실행 지침, 승인 제품 계약, 실제 구현, 현재 작업 상태의 소유자를 분리한다.
- 권한 영향: 없음. 코드가 제품 정책을 자동 덮어쓰게 하는 변경도 아니다. 설계 §3·7·10에 반영.

### 2) 모든 코딩에 Sol xhigh, parent 직접 구현 금지

- 인용: [AGENTS.md](../../AGENTS.md) 94~105줄 “실제 구현과 테스트는 … xhigh”, “Parent는 … Sol을 대신해 구현하지 않고”; [모델 workflow](codex-model-workflow.md) §3의 “요청한 Sol 모델이나 위임 도구를 사용할 수 없으면 … blocked”.
- 영향: 작은 작업도 방향 문서·handoff·회신·parent review를 거친다. 특정 모델/도구 부재가 필요한 구현 전체의 blocker가 된다.
- 편집: GPT-6 직접 구현을 허용하고, 분리 이익이 있는 제한 작업만 Sol Medium/High에 위임한다. High/xhigh는 위험·난도에 맞춘다.
- 권한 영향: **모델 선택과 직접 구현 재량 확대.** 사용자 특정 모델 지시는 그대로 준수. 설계 §4·6.3에 명시.

### 3) 낡은 디자인 승격 SOP가 현재 규칙을 되돌린다

- 인용: [design-screen-promotion.md](design-screen-promotion.md) 13줄 “최신 main과 5174”, 42·68줄 commit 별도 승인, 51줄 실행 process가 있으면 branch 전환 금지.
- 영향: branch-following HTTPS 5174를 main 검수 환경으로 오인하거나, 이미 승인된 local commit에 다시 질문하고 불필요한 worktree를 만든다.
- 편집: 환경·branch·commit은 Root 참조. 이 SOP는 사용자가 선택한 격리 디자인 승격에만 적용하고 특정 과거 사례는 역사로 이동한다.
- 권한 영향: 현행 Root와 정렬은 없음. 일반 UI 작업의 승격 절차 의무 제거는 workflow 완화. 설계 §3·10에 반영.

### 4) Roadmap의 “현재 Next”가 여러 곳에서 다르다

- 인용: [Roadmap](../00-product-roadmap.md) 1087줄 “현재 Next Gate는 Task 3 구현…”; 1996·2363줄은 Task 3 완료와 Task 4 승인 대기. Change 020 보고 41줄에는 오래된 현재 포인터 보정 때문에 검증이 반복된 기록이 있다.
- 영향: 완료 작업 재선택, 다음 작업 차단, 현재 상태 포인터를 고치기 위한 반복 검토가 발생한다.
- 편집: Task의 현재 기록 한 곳이 상태를 소유한다. Roadmap은 우선순위·의존성·링크를 관리한다. 역사 Decision Log는 보존한다.
- 권한 영향: 없음. 설계 §2·7·10에 반영. 모든 반복 검토가 낭비라는 뜻은 아니다.

### 5) 모든 새 session이 전체 instruction chain을 반복 로드한다

- 인용: [AGENTS.md](../../AGENTS.md) 24~26줄 “모든 새 Task와 분리된 … session”, “최소 확인 범위는 … Product Roadmap … 해당 Task의 planning·review·change·implementation report”.
- 영향: 좁은 reviewer도 2,411줄 Roadmap과 누적 보고서까지 다시 읽게 된다. 압축 후 재개에서도 현재 경계 확인과 전체 역사 복원이 결합된다.
- 편집: 매 session은 현재 Root/관련 하위 지침·현재 Task·관련 큐를 확인한다. 상세 역사·다른 정책은 목적·영향이 있을 때 읽고 지침/base 변경 시 해당 부분을 갱신한다.
- 권한 영향: 실행 권한 확대 없음. 최소 읽기 의무 축소. 설계 §3·5·7에 반영.

### 6) 목적 확인과 Roadmap 순서가 단순 후속 수정까지 막는다

- 인용: [AGENTS.md](../../AGENTS.md) 36줄 tasks·Decision Log·local/remote branch·worktree·open/merged PR 검색, 46줄 “다른 Task를 요청해도 … 묵시적 순서 변경으로 해석하지 않는다”.
- 영향: 같은 Task 후속에도 역사 검색이 반복되고 사용자가 지정한 작업에 다시 순서 승인을 요구할 수 있다.
- 편집: 기존 Task/활성 branch/PR부터 확인하고 새 목적·모호성 때 검색을 확대한다. 실질 의존성이 유지되는 명시 작업 지시는 우선 진행으로 인정한다.
- 권한 영향: 검색 축소는 없음. **우선순위 결정 재량 확대**는 설계 §6.3에 별도 명시.

### 7) 작은 작성도 parent+fresh 검증과 넓은 기준선에 묶인다

- 인용: [AGENTS.md](../../AGENTS.md) 98줄 “계획이나 대상 artifact를 직접 작성·변경했다면 … fresh … verifier”; 246~250줄 실행 컨텍스트 분리와 고정 기준선. Change 020 보고 43줄의 범위 밖 untracked digest 기록.
- 영향: 작은 문서 보정에도 추가 agent와 넓은 파일 상태 기록 비용이 붙는다.
- 편집: 위험도별 독립 검토를 사용한다. 변경·의존 파일 기준선을 고정하고 외부 WIP 보존을 구분한다. 영향 없는 검증 증거는 재사용한다.
- 권한 영향: **독립 검증 의무 완화.** 제품·운영 권한은 늘지 않는다. Root가 이미 영향받은 검증만 재실행하도록 한 부분은 유지한다. 설계 §4·8에 반영.

### 8) 요구사항이 충분해도 여러 확인 상태가 필요하다

- 인용: [AGENTS.md](../../AGENTS.md) 150~161줄 interview 요약 확인, primary draft·review resolution·구현 승인; [planning template](../../tasks/_templates/new-feature-planning-template.md) 229~239줄 승인 checkbox.
- 영향: 하나의 명확한 요청을 여러 상태로 해체해 agent가 승인 누락을 오판할 수 있다.
- 편집: 목표·범위·불변조건·검증·변경 경계 한 계약에 합친다. 실제 미결정이 있을 때만 질문하고 한 메시지의 구체 승인을 재사용한다.
- 권한 영향: 현재도 한 메시지의 세 승인은 허용된다. **별도 인터뷰 확인을 필수로 하지 않는 변경**은 절차 확대 제안이며 설계 §6에 표시했다. 기획 요청을 구현 승인으로 바꾸지 않는다.

### 9) experiment 예외가 일반 절차보다 복잡해진다

- 인용: [AGENTS.md](../../AGENTS.md) 172~187줄 “1차 planning”, “별도 exact target … 최종 planning”, 다수 waiver/approval marker와 exclusive create.
- 영향: 빠른 실험에서도 같은 승인·모델·계약을 여러 파일에 적고 부분 보정이 target 충돌에 걸릴 수 있다.
- 편집: 하나의 현재 계약과 보존된 review/승인 이력을 사용한다. metadata는 한 곳에 기록하고 참조한다.
- 권한 영향: **승인 범위의 현재 기록 갱신 재량 확대.** 과거 원문 삭제·새 범위 redraft·실험 승인의 운영 이전은 허용하지 않는다. 설계 §6.3·7에 반영.

### 10) 산출물 상태와 최종 보고 형식이 작은 작업에 과하다

- 인용: [종료 정책](../12-task-completion-policy.md) 11~25·207줄 모든 쓰기의 5종 상태, 168~194줄 고정 10개 보고 항목.
- 영향: 결과와 무관한 SOP/manual/N/A·다음 Task 조사까지 생긴다.
- 편집: 기본 Task/change 한 곳에 목적·승인·변경·검증·남은 상태를 기록한다. 사용자 동작/운영/제품 순서가 바뀐 경우만 해당 문서를 갱신한다.
- 권한 영향: 실행 권한 확대 없음. 문서 의무 완화. **현행도 5개 독립 파일을 강제하지 않고**, 읽기 전용/docs 간단 보고 예외가 있다는 점을 유지해서 해석했다. 설계 §7·8.4에 반영.

### 11) Frontend 최소 검증이 모든 변경에서 전체 suite다

- 인용: [Validation Matrix](validation-matrix.md) 26줄 “lint + typecheck + test + build”, 58~67줄 공통 계약의 전체 pipeline.
- 영향: 좁은 UI 변경도 전체 테스트가 따라붙고 여러 역할이 동일 결과를 다시 만들기 쉽다.
- 편집: 개발 중 직접 반례·영향 검증, 사용자 검수 후 최종 병합 후보의 회귀 책임 실행으로 나눈다. 코드·설정·환경이 맞는 증거는 재사용한다.
- 권한 영향: **검증 선택 재량 확대.** 권한 거부·migration 새/기존 DB·동시성·provider 비호출 직접 검증을 유지한다. 실패나 새 변경의 재검증을 금지하지 않는다. 설계 §8에 반영.

### 12) PR 조사와 실화면 증거의 접근·출력 경계가 섞인다

- 인용: [Privacy-safe Evidence](privacy-safe-evidence.md) 49줄 PR body/comments/metadata의 필요성·사용자 승인 조건, 102줄 절차 보정 후 “처음부터 gate를 재실행”.
- 영향: 목적/승인 이력 조회를 요구하는 Task gate와 안전한 조회 경로가 충돌하고, 증거 collector 문제로 무관한 검증까지 초기화할 수 있다.
- 편집: 필요한 조회·내부 분석·보고서 보관·외부 공유를 구분한다. 최소 비식별 요약 경로를 명확히 하고 오염된 증거와 의존 결론만 다시 확인한다.
- 권한 영향: **최소 조회 재량은 넓어질 수 있음.** 원문 계정·실데이터·credential 저장/게시 권한은 유지해서 제한한다. 이미 허용된 합성 화면 증거를 새 허용처럼 설명하지 않는다. 설계 §5.3·6.3·8.3에 반영.

### 13) 과거 experiment runtime이 모든 Task의 실행 명령이 된다

- 인용: [scripts/AGENTS.md](../../scripts/AGENTS.md) 35~37줄 “현재 experiment” 주소와 Task 종료 때 최신 source 재검증/열어 두기; [원장](../27-experiment-task-ledger.md) 146줄 해당 주소는 당시 기록이라는 제한.
- 영향: 관련 없는 작업이 오래된 runtime을 갱신하려고 시도할 수 있다.
- 편집: 공통 지침은 ownership·strict port·DB guard만 소유하고 특정 환경의 현재 owner/source/승인은 SOP로 옮긴다.
- 권한 영향: 없음. 비승인 runtime 변경 유도를 제거한다. 살아 있는 process를 확인하지 않았으므로 정리/재시작 필요를 단정하지 않는다. 설계 §5·7·10에 반영.

### 14) 새 session 안내가 최초 bootstrap으로 돌아간다

- 인용: [START_HERE.md](../../START_HERE.md) 34~35줄 “AGENTS.md와 docs 전체” 후 bootstrap; [README](../../README.md) 39~41줄의 같은 진입.
- 영향: 성숙한 프로젝트에서도 초기 설치·게시와 전체 문서 읽기를 다시 시작할 수 있다.
- 편집: Root → 현재 Task/큐 → branch/WIP → 필요한 SOP로 대체한다. 최초 설치 절차는 역사/설치 요청 전용으로 둔다.

### 15) 실행 규칙이 안전 조회와 위험한 행동을 넓게 묶는다

## 8. 실행 제한과 최종 보고 원칙

| 프로젝트 범위의 기억·기존 Task로 재개 | 별도 원장·자동 교차 프로젝트 기억·동일 작업 재실행을 추가하지 않음 | §5.1·7.2 |

| 제한된 재시도·자원 ownership·강제 장치 구분 | 단순 횟수로 재질문하지 않고 공유 서버를 자동 정리하지 않음. 문서와 실제 차단을 구분 | §5.2·5.4 |

도입하지 않은 절차는 모든 작업의 P/A/B 승인, 고정 역할 모델, 새 goal·notepad·단계 상태 기계, 모든 완료 때 전체 suite 재실행, 다수 hook 일괄 설치와 일괄 자원 종료다. 기존 PMS 기록으로 충족되는 항목에 새 파일·스킬·검증 회차를 요구하지 않는다.
