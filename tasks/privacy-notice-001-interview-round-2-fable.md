### 질문 1 — "모바일 푸시 준비 중" 예고(4B)는 어디까지 표시할까요

- **필요한 이유**: 4번에서 권장안 A 대신 B(현재 채널 안내 + 푸시 준비 중 예고)를 선택하셨다. 예고를 설치 안내·공지 같은 마케팅성 안내에만 둘지, 법정 고지 문서인 개인정보 처리방침에도 병기할지에 따라 처리방침 문안 구성이 달라진다. 처리방침은 "현재 실제로 하는 처리"를 기술하는 문서라서 미구현 기능 예고가 섞이면 고지 정확성이 흐려질 수 있다.
- **답변이 바꾸는 범위**: 처리방침의 알림 채널 section 문안, 설치 안내 dialog·공지 문구 계획, Web Push 후속 Task 도입 시 갱신해야 할 문서 목록.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 안내·공지에만 예고 | 설치 안내 dialog와 공지에는 "모바일 푸시 알림 준비 중" 예고를 넣고, 처리방침·알림 설정 화면은 현재 제공 채널(인앱·Teams·메일)만 기술. 처리방침에는 "새 알림 채널 도입 시 방침을 갱신하고 필요하면 별도 동의를 받는다"는 원칙 문구만 명시 | 법정 고지의 사실 정확성 유지. 4B의 설치 유인 효과는 보존. 푸시 출시 시 처리방침은 정식 개정 절차로 갱신 | 안내 문구와 처리방침의 표현 범위가 달라 문서 간 표현 지침이 필요 |
| B. 처리방침에도 예고 병기 | 처리방침 알림 section에도 "준비 중" 문구를 함께 기재 | 모든 문서의 표현이 동일 | 법정 고지에 미구현 기능이 섞여 고지 정확성·개정 관리 부담 증가 |

- **권장안**: **A**. 예고는 일정·기기 범위를 약속하지 않는 "준비 중" 수준으로 제한하고, 처리방침은 실제 처리 사실과 도입 시 갱신·동의 원칙만 담는 것이 "제공하지 않는 Web Push를 제공한다고 표시하지 않는다"는 이 Task 불변조건과 4B를 동시에 지키는 구성이다.

### 질문 2 — 처리방침·권리 행사 안내·이용수칙을 한 페이지로 묶을까요, 문서별 페이지로 나눌까요

- **필요한 이유**: 조회 대상 문서가 개인정보 처리방침(권리 행사 안내 포함, 2A)과 사내 이용수칙 두 갈래다. 페이지 수가 route 수, 진입점 구성, 390px 검증 범위와 개정 시 시행일 표기 위치를 결정하므로 화면 기획 전에 확정이 필요하다.
- **답변이 바꾸는 범위**: route/component 수, 진입점 메뉴 항목 수, anchor 목차 설계, 문서별 시행일·변경 이력 표기 위치.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 단일 안내 페이지 | "개인정보·이용 안내" 한 페이지에 처리방침(권리 행사 section 포함)과 이용수칙을 구분된 section·anchor 목차로 배치. 문서별 시행일을 각 section 머리에 표기 | 진입점 1개로 단순. 390px·접근성 검증 1회. 정적 시작(1C)과 최소 구조 원칙에 부합 | 두 문서의 성격(법정 고지 vs 내부 수칙)이 한 화면에 섞임. 문서가 길어져 목차 설계 중요 |
| B. 문서별 페이지 분리 | 처리방침 페이지와 이용수칙 페이지를 분리하고 공통 진입 허브 또는 메뉴 2항목으로 연결 | 문서 성격·개정 주기 분리가 명확. 특정 문서만 링크하기 쉬움 | route·진입점·검증 범위 2배. 시범 운영 규모 대비 구조 과잉 가능 |

- **권장안**: **A**. 시범 운영 단계에서는 상시 진입점 하나에서 두 문서를 모두 찾는 동선이 가장 단순하고, 5A에서 확정한 진입점(계정 메뉴 + 기존 사이드바/모바일 메뉴 footer 재사용)과도 맞다. 문서가 실제로 길어지거나 개정 주기가 갈라지면 후속에서 B로 분리할 수 있다. 진입점의 정확한 배치(계정 popover 항목 + 메뉴 footer 링크)는 이 답변을 전제로 planning에서 확정한다.

### 질문 3 — 문안 개정 시 변경 이력 표시와 사용자 공지는 어떻게 할까요

- **필요한 이유**: 처리방침은 변경 이력 공개가 필요하고, interview 3절·5절의 "잘못 게시된 문안의 복구·정정 고지 방식"이 미확정으로 남아 있다. 1C(정적 문안)에서는 이전 전문 보존 위치와 개정 사실을 알리는 채널을 정해야 rollback·운영자 대응 절차를 기획할 수 있다.
- **답변이 바꾸는 범위**: 페이지의 변경 이력 section 구조, 이전 버전 보존 방식, 개정·정정 시 홈 공지 게시 절차, rollback 절차 문안.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 이력 목록 + 개정 공지 | 페이지 안에 시행일·변경 요약의 변경 이력 목록을 두고, 이전 전문은 Git 이력·사내 보관으로 유지. 개정·정정 시 홈 공지로 알리고 페이지 링크 제공 | 기존 NoticeBoard 재사용으로 신규 구조 없음. 정적 구조에서 관리 부담 최소. 정정 게시 절차가 공지 한 곳으로 일원화 | 사용자가 앱 안에서 이전 전문 원문을 직접 열람할 수 없음(요청 시 창구로 안내) |
| B. 이전 전문 열람 제공 | A에 더해 이전 버전 전문도 앱에서 열람 가능하게 유지 | 투명성 최대 | 정적 구조에서 버전 페이지가 누적돼 관리·검증 범위 증가. 시범 운영 대비 과잉 |
| C. 페이지 갱신만 | 공지 없이 문안·시행일만 갱신 | 절차 최소 | 사용자가 개정 사실을 인지하기 어려워 변경 고지 취지 약화 |

- **권장안**: **A**. 최소 구조로 변경 이력 공개와 개정 인지를 모두 충족하고, 잘못된 문안의 정정도 "이전 검증 revision으로 rollback + 정정 공지"라는 단일 절차로 정리된다.

### 질문 4 — 권리 행사 창구·보호책임자 연락처를 문안에 어떻게 표기할까요

- **필요한 이유**: 2A(안내만)에서 접수 창구 표기는 처리방침의 필수 내용인데, 이 Repository는 실제 담당자 이름·회사 이메일을 tracked 파일에 기록하지 않는 불변조건이 있고 1C에서는 문안이 곧 코드다. 표기 방식을 정하지 않으면 planning이 문안 골격의 해당 section을 확정할 수 없다.
- **답변이 바꾸는 범위**: 처리방침의 보호책임자·창구 section 구조, 운영 원문의 기록 위치와 승인 경계, 배포 전 회사 확인 checklist.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 부서·역할명 + 공용 창구 | 문안에는 개인 이름 대신 담당 부서·역할명과 개인 식별이 없는 공용 창구(공용 메일함 또는 Teams 채널)를 표기. 공용 창구의 실제 주소는 회사 확인 뒤 별도 승인된 change 범위에서 기록·게시 | 개인정보 보호법상 부서명·연락처 표기로 충족 가능. 담당자 교체에도 문안 개정 불필요. 개인 식별정보를 코드에 남기지 않음 | 공용 창구(메일함·채널)를 회사가 실제로 개설·운영해야 함 |
| B. 배포 시 주입 | 코드에는 placeholder를 두고 실제 연락처는 배포 설정으로 주입 | Repository에 운영 원문이 전혀 남지 않음 | 정적 문안의 장점(코드=문안 단일 source) 훼손. 설정 누락 시 빈 연락처 노출 위험과 검증 절차 추가 |

- **권장안**: **A**. 개인 담당자 실명·개인 연락처 표기는 Repository 불변조건과 충돌하므로 선택지로 두지 않았다. A는 법정 표기 요건과 privacy 불변조건을 동시에 만족하는 가장 단순한 구조이며, 문안이 없거나 창구가 비어 있으면 게시 완료로 표시하지 않는다는 기존 validation 원칙과도 이어진다.
