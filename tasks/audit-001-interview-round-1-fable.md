# TASK-AUDIT-001 — Deep Interview Round 1 (Fable 5)

## Repository 기준선 확인

interview 문서(`tasks/audit-001-interview.md`), Identity Gate, Roadmap과 현재 구현을 대조해 다음을 확인했다.

- 운영 인증은 MSAL React + Backend JWT Bearer이며 Microsoft Entra가 신원 확인을 전담한다. 앱은 발급된 token이 붙은 요청만 관찰하므로 **Entra 단계의 실패 로그인(비밀번호 오류·MFA 실패 등)은 현재 구조상 앱에 도달하지 않는다.** 앱 쪽에서 확정 가능한 사건은 인증된 `/api/me` 신원 확정(`backend/src/Emi.Qms.Api/Identity/IdentityEndpointExtensions.cs`), 앱 단계 거부(401·승인 대기), 명시적 로그아웃 행동뿐이며, 현재는 이들 중 어느 것도 로그인 사건으로 저장하지 않는다.
- 재사용 가능한 기존 감사 자산이 이미 4종 있다: 권한 거부 전용 `authorization_audit_events`(`backend/src/Emi.Qms.Api/Authorization/AuthorizationAuditLogger.cs`), 같은 transaction 안에서 before/after JSON을 남기는 `admin_master_change_logs`(`backend/src/Emi.Qms.Api/Admin/AdminMasterDataStore.cs`), Excel export 자체 감사 `data_export_events`(`backend/src/Emi.Qms.Api/DataExports/DataExportAuditStore.cs`), KST 기간 경계·필터·선택 Excel을 갖춘 알림 설정 감사 조회(TASK-NOTIFY-AUDIT-001, migration `0048`).
- 업무 mutation은 도메인별 store가 raw SQL로 직접 수행하며(프로젝트·패널·구매·자재·IQC·제조·품질·물류·영업·생산관리·관리자 등 약 30개 영역) 공통 ORM 가로채기 지점이 없다. 최신 migration은 `0082`이고 신규 원장은 additive `0083+`가 된다.
- 첨부는 DB 저장 binary이며, Roadmap·interview 확정 정책상 비밀번호·token·인증 헤더·cookie·첨부 내용은 절대 기록하지 않는다.

아래 5개 질문은 interview 7장의 blocking 결정 1~5번과 1:1로 대응하며 모두 v1 원장의 기록 경계를 확정하는 서로 연결된 결정이다.

### 질문 1 — 로그인 사건을 어디까지 기록하는가 (Entra 실패 포함 여부)

- 필요한 이유: "누가 언제 로그인했는지"의 경계가 원장의 첫 번째 축인데, 현재 구조에서 Entra 단계 실패는 앱이 볼 수 없어 포함하려면 신규 외부 연동(Entra sign-in log/Graph)이 필요하다. 승인 대기 사용자의 성공 인증을 기록할지도 미확정이다.
- 답변이 바꾸는 범위: 외부 연동 추가 여부(Graph 권한 승인·수집 지연·중복 제거·외부 데이터 반입), 로그인 사건 schema, Frontend의 로그인 완료 신호 API 추가 여부, 관리자 화면의 로그인 결과 필터 값.

| 선택지 | 설명 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A. 앱이 확정 가능한 경계만 기록 | 성공 로그인(인증 세션 시작 1회), 앱 단계 거부(비활성·승인 대기 포함), 명시적 로그아웃을 기록. Entra 단계 실패는 제외하고 Entra portal sign-in log로 위임 | 외부 연동 없이 전부 자체 transaction으로 확정 가능. 배포·검증 범위 최소 | 비밀번호 오류·MFA 실패는 앱 화면에서 조회 불가(Entra portal 별도 확인) |
| B. A + Entra sign-in log 연동으로 실패 로그인 수집 | Graph/진단 설정으로 Entra 실패 기록을 주기 수집해 원장에 병합 | 로그인 실패까지 한 화면에서 조회 | 신규 외부 연동·tenant 권한 승인 필요. 수집 지연·중복·보존 경계가 앱 transaction과 분리되어 "확정 원장" 성격이 약해짐 |
| C. 성공 로그인만 기록 | 실패·거부·로그아웃 제외 | 가장 단순 | 권한 문의·이상 접근 조사에서 거부 이력을 연결할 수 없어 목적 일부 미달 |

- 권장안: **A**. 이 Task의 목적이 "추정이 아닌 확정"이므로 앱 transaction으로 확정 가능한 사건만 v1 원장에 넣고, Entra 단계 실패 조회는 명시적 제외·후속 항목으로 기록한다. 승인 대기 사용자의 성공 인증도 정상 로그인 사건으로 포함하기를 권장한다(인증 자체는 성공했고 기존 접근 제한은 그대로 유지된다). MSAL silent 갱신은 로그인으로 세지 않고, Frontend 로그인 완료 시점의 명시 신호 1회를 1개 사건으로 본다.

### 질문 2 — IP·기기 정보를 어떤 형태로 저장하고 얼마나 보존하는가

- 필요한 이유: 장애·오입력·권한 문의 조사에는 접속 위치·기기 단서가 유용하지만, 이 Repository는 개인정보 최소화를 강한 불변조건으로 유지한다. 원문 저장 여부와 중복 저장 범위를 확정해야 schema가 고정된다.
- 답변이 바꾸는 범위: 로그인·변경 사건 schema, 관리자 화면·Excel 표시 열, 개인정보 검토 결과와 운영 SOP의 안내 문구.

| 선택지 | 설명 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A. 로그인 사건에만 원문 IP·브라우저 정보(User-Agent) 저장, 변경 사건은 correlation 값으로 연결 | 데이터 변경 사건은 IP를 중복 저장하지 않고 안전한 세션/요청 correlation 식별값으로 해당 로그인 사건에 연결 | 조사 가치 보존 + 개인정보 원문의 저장 지점 최소화. 저장량 절약 | 변경 사건 단독 조회 시 IP를 보려면 로그인 사건 join 필요 |
| B. 모든 감사 사건에 IP·User-Agent 원문 중복 저장 | 사건마다 완결된 기록 | 단건 조회가 자기완결적 | 개인정보 원문이 전 원장에 중복 확산. 최소화 원칙과 충돌 |
| C. IP·기기 정보 미저장 | 사용자·시각·행동·값만 기록 | 개인정보 부담 최소 | 계정 공유·이상 접속 의심 상황에서 조사 단서 상실 |

- 권장안: **A**. 보존기간은 별도 만료를 두지 않고 원장 본체와 동일하게 가져간다(질문 5와 연동). User-Agent는 원문 대신 브라우저·OS 계열 요약값으로 축약 저장해도 조사 목적에 충분하므로, 원문이 꼭 필요하지 않다면 축약을 함께 권장한다.

### 질문 3 — v1에서 field-level before/after를 기록할 업무 mutation 범위는 어디까지인가

- 필요한 이유: 공통 가로채기 지점이 없어 기록 범위가 곧 구현·검증 비용이다. 또한 worker가 수행하는 시스템 자동 변경(알림 발송 상태, purge 등)까지 포함할지에 따라 원장의 성격과 잡음 수준이 달라진다.
- 답변이 바꾸는 범위: 대상 도메인 수와 구현 방식, field allowlist 설계 범위, 감사 잡음·저장량, 자동 검증 범위, 후속 확장 Task의 존재 여부.

| 선택지 | 설명 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A. 인증된 사용자의 성공한 업무 mutation 전체 | 전 업무 도메인에 공통 기록 계약을 적용하되 field는 서버 allowlist projection으로 한정(파생값·대용량·첨부 binary 제외). 시스템 자동 변경(worker)은 제외 | "전체 이력을 확정할 수 없다"는 문제를 남김없이 해소. 사용자가 우선순위 재정렬로 승인한 추적 항목 48(전체 field-level audit)과 일치 | 전 도메인 store 계측으로 구현·검증 비용이 가장 큼. 도메인별 field allowlist 정의 필요 |
| B. 핵심 업무 원장 우선 | 프로젝트·패널·구매·자재·검사·제조·물류·영업 등 업무 원장 먼저 적용. 관리자·알림·개인설정은 기존 감사 재사용, 잔여 도메인은 후속 확장 | 비용을 단계화하면서 책임 추적이 가장 필요한 영역부터 확보 | 미적용 도메인에서는 지금과 같은 "복원 불가" 공백이 남아 조사 시 경계 혼동 위험 |
| C. 관리자·권한 변경 중심 최소 | 기존 `admin_master_change_logs` 계열 확장 수준 | 가장 작음 | 일반 업무 데이터 변경이 빠져 이 Task의 핵심 문제를 해결하지 못함 |

- 권장안: **A**. 사용자가 이미 전체 field-level audit를 현재 운영 관찰보다 우선하도록 명시 승인했고, 부분 적용은 "어느 화면은 추적되고 어느 화면은 안 되는" 새 혼선을 만든다. 다만 v1 대상은 **인증된 사용자 행위**로 한정하고, worker·스케줄러의 자동 변경은 기존 상태·이력 원장으로 추적(명시적 제외)하기를 권장한다. 비용이 부담이면 B를 선택하되 잔여 도메인의 확장 Task를 즉시 Roadmap에 고정해야 한다.

### 질문 4 — 실패한 업무 변경 시도와 첨부 metadata는 기록하는가

- 필요한 이유: interview 3장은 "저장되지 않은 변경은 성공으로 기록하지 않는다"까지만 확정했고, 실패 시도 자체를 남길지와 첨부 관련 사건의 허용 범위가 미확정이다.
- 답변이 바꾸는 범위: 원장 사건 종류(성공 전용 여부), 기존 권한 거부 감사와의 역할 분담, 첨부 upload/삭제 endpoint의 계측 여부, 저장량·잡음.

4-a. 실패한 업무 변경 시도:

| 선택지 | 설명 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A. v1 제외 | 신규 원장은 성공 변경만 기록. 권한 거부는 기존 `authorization_audit_events`가 계속 담당 | 원장이 "실제 일어난 변경"과 1:1로 일치해 해석이 명확. 기존 거부 감사와 중복 없음 | validation 실패의 반복 시도 패턴은 신규 화면에서 조회 불가 |
| B. 권한 거부·validation 실패 시도도 신규 원장에 기록 | 시도 사건을 별도 종류로 append | 이상 행동 탐지에 유리 | 저장량·잡음 급증. 실패 요청 본문을 다루며 개인정보·오입력 원문이 원장에 유입될 위험 |

4-b. 첨부 관련 사건:

| 선택지 | 설명 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A. metadata 변경 사건만 기록 | 첨부 upload·교체·삭제를 파일명·크기·행위자·시각 수준으로 기록. 내용(binary)은 절대 제외 | "누가 어떤 파일을 언제 올리고 지웠는지" 추적 가능. 내용 미기록 불변조건 유지 | 파일명에 업무 정보가 포함될 수 있음(원장 열람이 관리자 전용이므로 허용 범위) |
| B. 첨부 관련 사건 전체 제외 | 첨부는 원장 밖 | 가장 단순 | 첨부 삭제 책임 추적 불가 — 조사 목적의 실질 공백 |

- 권장안: **4-a는 A, 4-b는 A**. 성공 변경 전용 원장이 "확정 원장" 성격을 지키고, 첨부는 metadata 사건으로만 포함하면 기존 금지 불변조건과 충돌 없이 책임 추적이 성립한다.

### 질문 5 — 관리자 조회·Excel의 기본 기간과 장기 보존 정책은 무엇인가

- 필요한 이유: 전체 mutation을 기록하면 원장이 가장 빠르게 자라는 테이블이 된다. 기본 조회 기간과 보존 정책을 정해야 index·화면 성능 기준과 운영 SOP가 확정된다.
- 답변이 바꾸는 범위: 기본 필터·조회 성능 목표, Excel export 범위 제한, 보존·만료 운영 절차와 후속 Task 여부.

5-a. 관리자 화면 기본 조회 기간(기간 필터로 변경 가능, KST 날짜 경계는 기존 알림 설정 감사 조회와 동일 적용):

| 선택지 | 설명 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A. 최근 7일 | 최소 범위 기본값 | 가장 빠른 초기 로딩 | 일반 문의(“지난달 누가 바꿨나”)마다 기간 변경 필요 |
| B. 최근 30일 | 한 달 기본값 | 일반 조사 범위와 일치. 성능·편의 균형 | 대량 기간에는 필터 병행 필요 |
| C. 최근 90일 | 분기 기본값 | 기간 변경 빈도 최소 | 초기 조회·요약 부하 최대 |

5-b. 장기 보존:

| 선택지 | 설명 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| A. 무기한 append-only 보존 | v1은 만료·purge를 만들지 않음. 저장량 증가는 운영 관찰 후 별도 Task로 결정 | 원장 삭제 금지 불변조건과 완전 일치. v1 범위 최소 | 수년 후 저장량·조회 성능 관리 필요(후속 결정) |
| B. 보존기간 경과분 아카이브 후 삭제 | 예: 1~3년 경과 사건을 Excel/파일 아카이브로 내리고 원장에서 제거 | DB 크기 관리 | "감사 원장은 수정·삭제하지 않는다"는 확정 정책과 충돌. 아카이브 무결성·권한 관리가 새 위험 |

- 권장안: **5-a는 B(최근 30일), 5-b는 A(무기한 보존)**. Excel은 기존 선택 export 패턴을 재사용해 현재 필터·선택 범위만 내보내고, export 실행 자체는 기존 `data_export_events` 계약으로 자체 감사한다. 보존기간 만료 정책은 v1에서 만들지 않고 운영 저장량 관찰 후 별도 결정으로 남긴다.
