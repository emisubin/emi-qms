## 1. 문서 지위와 목표

[확인된 요구사항](osan-pilot-001-interview.md)을 구현 가능한 업무 계약으로 정리한다. 사용자 승인 범위는 대화에서 확인한 기획이며, 아래 “구현 권장안”은 조사에 근거한 설계 제안이다. 구현과 운영 적용의 실행 승인은 별도다. 독립 검토의 resolution은 [검토 문서](osan-pilot-001-review.md)에서 원문과 구분해 추적한다.

오산에서 8개 정보로 프로젝트를 만들고 개별 제품의 7단계 진행 여부를 기록하며 전체 프로젝트 현황을 확인한다. 청주의 데이터와 현행 업무 계약은 보존한다. 기존 제조 시스템의 화면·기록 메커니즘을 재사용하고 오산 전용 기능을 별도 코드베이스로 복제하지 않는다.

## 2. 확정 범위

- 같은 PMS 주소·Microsoft 365 조직으로 접속한다.
- PostgreSQL 서버 하나에 청주·오산 업무 DB를 각각 둔다. 업무 테이블·데이터·runtime DB 접속 권한을 분리하며 서버 처리 자원은 공유한다.
- 총괄 관리자는 소속을 지정하고 사업부 관리자는 자기 사업부 업무 권한을 부여한다. 사업부 전환은 지정된 총괄만 가능하다.
- 오산 업무 화면은 전체 현황판, 프로젝트 목록/생성/상세, 진행 관리다. 필요한 소속·권한 관리와 공통 진행 양식 관리는 관리자 기능으로 제공한다.
- 오산에는 중단·재개·펜딩, 별도 IQC/LQC/OQC/FAT 업무, 물류 인계, 정산, G2를 활성화하지 않는다. 명칭이 “검사”·“포장”이어도 별도 업무를 만들지 않는다.
- 오산은 PMS 내부 알림만 사용한다. 청주의 기존 provider 설정과 발송은 보존한다.
- 실제 Azure 자원 변경·DB 생성·Persistent UAT·외부 발송·Git 게시·merge는 문서화 범위 밖이다.

## 3. 프로젝트 생성 계약

| 순서 | 화면 항목 | 값과 규칙 |
| ---: | --- | --- |
| 1 | 프로젝트 Title | 필수 텍스트 |
| 2 | 프로젝트 코드 | 필수 텍스트; 오산 내 중복 차단 |
| 3 | 거래처 | 필수 텍스트 |
| 4 | PO No | 선택 텍스트; 중복 허용 |
| 5 | W/O No | 선택 텍스트; 중복 허용 |
| 6 | 납기일 | 필수 날짜; 서울 업무 날짜 기준, 과거일 입력 허용 |
| 7 | 제품명 | 필수 자유 텍스트; 사전 아이템 등록/선택 없음 |
| 8 | 수량 | 필수 양의 정수 |

필수 여부와 코드 중복 규칙은 승인된 대화 초안의 권장안을 따른다. 구현 권장안으로 문자열은 앞뒤 공백을 제거하고 공백뿐인 필수값은 거부한다. 코드 비교는 기존 프로젝트 코드 정규화 규칙을 재사용하고 PO/W/O의 기호·앞자리 0을 보존한다. 텍스트 길이·수량 상한은 기존 서버의 안전 한도를 구현 handoff에서 확인·고정하며 무제한 생성으로 넓히지 않는다.

생성은 프로젝트, 입력 수량만큼의 개별 대상, 공통 단계 snapshot과 진행 준비를 하나의 업무 transaction으로 저장한다. 일부만 만들어진 프로젝트를 성공으로 응답하지 않는다. 생성 실패는 입력을 보존하며 동일 요청 재시도는 중복 프로젝트를 만들지 않는다.

오산 생성 화면에는 담당자·포장방식·FAT·설계·영업 정산 입력을 추가하지 않는다. 제품명 텍스트를 기존 청주 Item 코드나 자동 생성 Item으로 바꾸지 않는다.

## 4. 진행 관리와 상태

공통 단계는 다음 순서다.

1. 입고검사
2. 배치검사
3. 배선검사
4. 8계통
5. 동작검사
6. 출하검사
7. 포장

수량이 N이면 대상 N개가 각자 7단계를 가진다. 대상 표시명은 제품명과 순번으로 구분하고 내부 식별자를 사용자에게 노출하지 않는다. 생성 직후 진행 관리에 표시하되 실제 작업 시작 시각을 생성 시각으로 가장하지 않는다.

기존 작업 시작·개별 단계 완료·선택 대상 일괄 단계 완료를 재사용한다. 단계마다 처리자와 서버 시각을 기록한다. 일괄 처리는 선택한 대상의 해당 단계에만 적용하며 다른 대상·단계를 완료시키지 않는다.

- 대상 상태: 시작 전 → 진행 중 → 완료.
- 프로젝트 상태: 모든 대상이 시작 전이면 시작 전, 하나라도 시작했고 전체 완료 전이면 진행 중, 모든 대상의 포장이 완료됐으면 완료.
- 앞 6단계가 완료되지 않은 대상은 포장을 완료할 수 없다. 개별·일괄·직접 API에 동일하게 적용한다.
- 포장 저장 시 해당 대상을 완료하고, 마지막 대상이라면 같은 transaction에서 프로젝트도 완료한다. 별도 제조 완료·프로젝트 완료 버튼은 없다.
- 마지막 대상의 완료 기준은 서버가 전체 대상을 확인해 판단한다. UI에 현재 표시된 행이나 페이지 수를 분모로 쓰지 않는다.
- 중단/펜딩 동작은 오산 UI뿐 아니라 API와 workflow dispatch에서도 거부하며 관련 work item·알림을 생성하지 않는다.
- 포장 후 OQC·물류·세금계산서로 인계하지 않는다.
- 동시 완료는 project lock/CAS·요청 중복 방지를 이용해 하나의 일관된 완료 결과·감사·알림 이벤트로 수렴해야 한다.

구현 권장안: 첫 시범에서는 단계 취소·프로젝트 재개·작업 시작 후 대상 수량 변경을 신규 UI로 추가하지 않는다. 기존 청주용 재개·수량 변경 API를 오산에 그대로 노출하지 않는다. 잘못된 진행 기록의 정정 절차는 검토에서 복구 가능성을 평가하고 별도 승인된 최소 보정 계약으로 다룬다. 자동으로 완료 이력을 삭제하지 않는다.

## 5. 양식 재사용

사용자는 제품명만 입력한다. 시스템은 오산의 공통 진행 양식과 연결하며 제품명마다 새 Item/양식을 만들지 않는다. 기존 Item별 제조 양식의 순서·항목 기록 메커니즘을 재사용하되 오산 공통 양식은 청주 Item·양식과 별개다.

구현 권장안: 오산 공통 양식을 사업부 설정에 연결하고 생성 시 7단계의 이름·순서를 프로젝트에 고정한다. 첫 시범의 적용 양식은 위 7단계다. 양식 설정을 바꾸더라도 이미 시작·완료한 오산 프로젝트를 소급 재작성하지 않는다. 청주의 현행 Item 양식 동기화 계약은 바꾸지 않는다. 별도 진척 양식 편집기나 범용 workflow builder를 새로 만들지 않는다.

## 6. 전체 현황판

오산 접속 후 기본 화면은 전체 프로젝트 진행현황이다. 상단에는 전체·시작 전·진행 중·완료 프로젝트 수를 표시한다. 중단·펜딩·불량·별도 지연 KPI를 추가하지 않는다.

| 영역 | 표시와 행동 |
| --- | --- |
| 프로젝트 행 | 코드·Title·거래처·제품명·수량·납기일·상태·진행률·7단계별 완료 수 |
| 단계별 셀 | “3/5 완료”처럼 완료 대상 수/전체 대상 수 표시 |
| 검색 | Title·코드·거래처·제품명·PO No·W/O No |
| 필터 | 전체·시작 전·진행 중·완료 |
| 정렬 | 미완료 우선, 납기일 오름차순, 동률 시 코드/식별자 안정 정렬 |
| 상세 이동 | 프로젝트 선택 → 해당 프로젝트 진행 관리 |
| 모바일 | 요약 카드와 펼침 상세; 넓은 표는 내부 탐색, 페이지 전체 가로 넘침 없음 |

검색 결과와 권한 scope에 동일한 기준을 적용한다. 구현 권장안: 상태 카드 수는 권한+검색 결과 전체(상태 필터 적용 전), 목록은 선택한 상태 필터까지 적용해 카드 클릭 시 의미를 유지한다. 페이지 단위 행 수로 전체 집계를 계산하지 않는다.

전체 진행률 = 완료한 단계 수 / (전체 대상 수 × 7) × 100. 표시 정수는 미완료일 때 최대 99이며 전체 포장 완료일 때만 100이다. 시작 버튼만 누른 프로젝트는 진행 중이면서 진행률 0%일 수 있다. 부적절한 수량 0 프로젝트는 생성 단계에서 거부한다.

저장 성공 후 관련 대상·프로젝트·현황 집계를 다시 읽는다. 조회 실패 시 이전 값을 최신값처럼 표시하지 않고 재시도를 제공한다. 대시보드에 별도 완료 mutation을 만들지 않는다.

## 7. 소속·권한과 화면 전환

| 역할 | 범위 |
| --- | --- |
| 미승인/미소속 사용자 | 승인 대기 안내만; 업무 DB 임의 선택 금지 |
| 사업부 일반 사용자 | 자기 사업부 및 기존 프로젝트 조회 scope 안의 데이터 |
| 프로젝트 생성/진행 권한 사용자 | 사업부 관리자가 부여한 업무 권한과 프로젝트 scope를 모두 충족한 행동 |
| 사업부 관리자 | 자기 사업부 사용자 업무 권한·프로젝트 접근 관리 |
| 지정 총괄 | 소속 지정과 사업부 전환; 선택 사업부의 업무 변경에는 해당 업무 권한도 적용 |

기존 System Administrator를 자동으로 총괄로 승격하지 않는다. 총괄 designation은 명시적으로 관리한다. 공통 소속 변경은 부서 변경과 별개이며 일반 사용자가 요청 header만 바꿔 다른 DB로 들어갈 수 없다.

구현 권장안: 프로젝트 생성자는 감사 actor로 기록하고 기존 scope 표현으로 해당 프로젝트 접근을 연결한다. 생성 권한이 진행 변경 권한을 자동 부여하지 않는다. 진행 권한이 있는 생성자는 별도 제조 담당자 지정 없이 시작할 수 있고, 추가 사용자는 관리자가 기존 접근/역할 관리로 연결한다. 담당자 미지정을 숨겨진 제조 투입 gate로 다시 만들지 않는다. 업무 권한 없는 계정을 서버에서 자동 승격하지 않는다.

총괄 전환 시 진행 중인 저장이 끝나기 전 전환을 막고, 이전 사업부 요청을 취소/무효화하며 화면·선택·검색 결과를 초기화한다. 사업부 선택은 탭별로 관리해 다른 탭의 선택을 바꾸지 않는다. 모든 요청과 deep link는 소속 확인을 거친 사업부 context에 묶는다. 로그아웃·소속/권한 회수 시 업무 접근을 다시 검증한다.

## 8. 데이터·서버 구조 — 구현 권장안

기존 Repository는 Container Apps + PostgreSQL Flexible Server 구조이며, DatabaseConnectionStringProvider가 하나의 DB를 선택하고 EntraClaimsTransformation이 그 DB의 사용자 profile을 읽는다. 단순 연결 문자열 두 개 추가로 사업부 격리가 완성되는 구조가 아니다.

같은 PostgreSQL 서버에 청주·오산 업무 DB를 분리하고, 소속 라우팅에 필요한 최소 공통 directory DB를 권장한다. 공통 DB는 인증 조직/사용자 연결키·사업부 membership·총괄 designation·변경 감사만 소유하며 프로젝트·단계·첨부·업무 역할의 원본을 모으지 않는다. 별도 서버 구매를 뜻하지 않는다. 이 공통 저장소의 세부 구조는 사용자 확정 업무 범위에 대한 기술 제안이다.

- 인증된 identity → 공통 directory의 허용 사업부 확인 → 선택 사업부 확정 → 그 사업부의 local 권한 profile → 업무 DB 접근 순서.
- 업무 DB별 접속 계정의 CONNECT·schema/table 권한을 분리한다. 서버 공통 role 이름 충돌과 public CONNECT 기본 권한까지 검증한다.
- runtime·migration·bootstrap 계정을 분리하고 기존 운영 credential을 코드나 문서에 기록하지 않는다.
- request context는 요청마다 고정한다. singleton store/provider에 변경 가능한 전역 “현재 사업부”를 보관하지 않는다.
- notification/에스컬레이션/삭제 worker는 명시적인 사업부 context로 실행하고 DB·lease·config·recipient·감사를 분리한다. 오산 외부 발송은 enqueue와 dispatch 양쪽에서 차단한다.
- 요청 밖 migration·health·bootstrap은 명시한 대상 DB에만 연결한다. 소속 없음·잘못된 DB·schema mismatch를 청주 fallback으로 숨기지 않는다.
- 기존 청주 DB·사용자 식별자·업무 이력은 유지하고 확인된 기존 사용자만 청주 membership으로 연결한다. 이후 신규 계정을 자동으로 청주 소속으로 만들지 않는다.
- PostgreSQL bytea로 저장하는 기존 첨부는 업무 DB 분리를 따르고 다운로드도 사업부/프로젝트 권한을 검증한다. 시범 기능을 위해 새 파일 저장 서비스를 도입하지 않는다.
- 공유 app/server 장애와 처리 자원은 공동 영향 범위다. 사업부 DB 분리가 물리 서버 장애 격리를 보장한다고 표현하지 않는다.

DB마다 migration ledger와 schema compatibility를 확인한다. 기존 main migration을 수정하지 않고 새 migration으로 기존 DB·fresh DB를 검증한다. 사업부 전용 업무 profile을 명시해 청주의 18단계가 오산의 7단계와 섞이지 않게 한다.

## 9. API·코드 영향

기존 프로젝트 생성 계약은 Item·패널·포장방식·FAT·영업 정보와 연결되므로 청주 계약을 완화해 오산 입력을 억지로 통과시키지 않는다. 오산 생성용 계약과 business-unit-aware 업무 profile을 두고 기존 엔진의 재사용 가능한 부분을 연결한다.

| 경계 | 필요한 기능 |
| --- | --- |
| 소속/접근 | 허용 사업부 조회·소속 관리·전환 context·사업부 local 권한 profile |
| 오산 프로젝트 | 8개 입력 생성·목록·상세와 개별 대상 조회 |
| 진행 | 시작·개별/일괄 단계 완료·자동 프로젝트 완료 |
| 현황 | 권한 scope 안의 검색·상태별 건수·프로젝트별 단계 aggregate |
| 관리 | 오산 공통 양식 연결·사업부 local 권한/접근 관리 |

오산 프로젝트에 청주 mutation API를 직접 호출하는 경우에도 서버가 profile을 확인해 거부하거나 오산의 동일 계약으로 처리해야 한다. UI menu 숨김을 보안 경계로 삼지 않는다.

핵심 조사 위치는 Backend의 Projects/Manufacturing/ProductionPlanning/Authorization/Identity/Workflow/Notifications, Frontend의 App.tsx/api.ts/ManufacturingPage.tsx/기존 현황 component, database/migrations와 Azure 배포 정의다. 정확한 파일 allowlist·migration 번호·endpoint shape는 각 Task 구현 승인 전에 최신 코드에서 고정한다. 광범위한 단순 rename이나 DB client 전면 교체를 섞지 않는다.

## 10. 알림·복구·운영

구현 권장안: 오산 인앱 알림은 프로젝트 생성과 프로젝트 최종 완료를 최소 이벤트로 삼고 기존 권한/프로젝트 접근을 충족하는 수신자에게만 전달한다. 매 단계·대상마다 broadcast하지 않는다. 청주 전체 직원 수신자를 재사용하지 않는다.

같은 PostgreSQL 서버의 기본 시점 복구는 서버 단위다. 한 사업부 복구는 임시 복구 서버에서 대상 DB만 추출·검증한 뒤 승인된 대상에 반영하는 절차를 rehearsal한다. 운영 전체 서버를 과거 시점으로 되돌려 다른 사업부를 덮어쓰지 않는다.

Azure 과금은 DB 개수 자체보다 확보한 처리·저장 자원과 백업 사용량에 따른다. 새 논리 DB가 별도 서버 기본요금을 만드는 것은 아니지만 용량·부하·백업 증가 비용은 실제 자원 확인 후 판단한다. 이번 조사에서 live Azure 용량·요금은 조회하지 않았다.

- [Microsoft: 데이터 분리 구조](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data)
- [Microsoft: PostgreSQL 백업·복구](https://learn.microsoft.com/en-us/azure/postgresql/backup-restore/concepts-backup-restore)
- [Microsoft: PostgreSQL 과금](https://azure.microsoft.com/en-us/pricing/details/postgresql/flexible-server/)

## 11. 구현 순서와 완료 기준

[상위 Task의 7개 개발 Task](osan-pilot-001.md)를 순차 실행한다. 제품 DB/권한 분리 기반을 먼저 검증하고 UI와 업무 기능을 연결한다. 청주용 기존 동작을 feature profile 뒤에서 유지하며 개발 중 오산 route를 공개 운영에 자동 활성화하지 않는다.

필수 시나리오:

- 같은 project/target ID를 두 시험 DB에 넣어도 list/detail/mutation/download/search가 교차하지 않는다.
- 미소속·일반·업무 권한자·사업부 관리자·총괄의 허용/거부, 권한 회수와 두 탭 전환을 검증한다.
- 기존 청주 데이터·사용자 ID·G2와 fresh 오산 schema/seed를 각각 검증한다.
- 수량 1/여러 개 생성, 잘못된 입력, 생성 중 실패, 중복 코드/요청을 검증한다.
- 마지막 포장 전/후, 일괄 조건 불충족, 동시 포장, stale version, 취소/재시도의 transaction 일관성을 검증한다.
- 오산 중단/펜딩·검사/물류 후속 업무·외부 provider 호출이 0인지 검증한다.
- 검색·권한·페이지 전환에 따라 집계 분모가 바뀌지 않고 100%가 조기 표시되지 않는지 검증한다.
- Backend/Frontend 전체 회귀와 격리 Full-Stack, desktop/390px, 읽기 전용 모드, backup/restore rehearsal을 완료한다.
- 실제 사용자 검수, Git 게시와 운영 적용 결과는 자동 테스트와 분리해 기록한다.

## 12. 승인·후속 사항

승인된 핵심 업무는 추가 인터뷰 없이 문서화한다. 이 문서의 구현 권장안과 독립 review에서 나온 추가 정책은 resolution으로 명시하며 기존 사용자 승인에 소급 포함하지 않는다.

공통 directory의 bootstrap 관리자 지정, 실제 사용자의 소속·권한, 운영 규모·개통 일정은 후속 운영 입력이다. 첫 제품 구현은 TASK-OSAN-ISOLATION-001의 exact 범위·검증 계획 승인 뒤 Sol xhigh에게 위임한다. 문서 작성만을 위해 구현 worker를 호출하지 않는다.

이번 기능에 대한 범용 검사 시스템, 개별 검사값/성적서/사진 의무, 불량·재작업, 펜딩, QR·Excel/PDF 신규 기능, cross-business 집계와 오산 외부 알림은 추가하지 않는다.
