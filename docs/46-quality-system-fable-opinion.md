# 품질 시스템 운영 모델에 대한 Fable 의견서 — IQC·LQC·OQC·전진검수·FAT·도면 대조

- primaryDraftStatus: `DRAFT_FOR_USER_REVIEW`
- sourceTask: `TASK-QUALITY-OPERATING-MODEL-001`
- authoringModel: `FABLE_5`

## 1. 문서 목적과 위상

이 문서는 사용자가 직접 조사한 실제 품질팀 운영 방식을 현재 EMI 프로젝트 통합관리시스템의 구현 기준선과 대조하고, 시스템을 어떻게 재구성할지에 대한 Fable의 독립 의견을 제시한다.

- 이 문서는 확인 완료된 interview(`tasks/quality-operating-model-001-interview.md`)와 현재 Repository 기준선만을 근거로 작성했다. 별도로 작성되는 Codex 의견서를 읽거나 참조하지 않았으며, 두 문서의 결론이 달라도 합치지 않는다.
- 이 문서는 사용자 비교 검토용 의견서다. 구현 계약, planning 승인, 구현 승인이 아니며 제품 구현 source of truth가 아니다.
- 본문 전체에서 `확인된 사실`(현장 조사와 Repository에서 확인), `문제 진단`(현재 시스템과 현장의 격차), `Fable 제안`(의견)을 구분해 표기한다.

## 2. 확인된 사실

### 2.1 현장 조사에서 확인된 운영 방식

IQC(수입검사):

- 모든 구매품을 검사하지 않는다. 실제 IQC 대상은 `외함`, `판금류`, `부스바`, `명판` 네 종류다.
- 네 종류 모두 육안 확인하지만, 공식 수입검사서를 작성·보관하는 대상은 현재 `외함`뿐이다.
- 외함 업체에는 EMI가 Excel 검사 양식을 미리 전달하고, 입고 시 업체가 종이에 체크한 검사서가 제품과 함께 도착한다. 그 검사서에는 EMI가 직접 확인할 항목도 포함되며, 품질팀이 추가 검사·서명 후 보관한다.
- 구매팀이 품목명을 자유 입력하므로 시스템이 검사 대상 여부를 안정적으로 구분하기 어렵다.
- 사용자는 판금류·부스바·명판의 육안 검사에도 기준을 만들고 기록 또는 성적서를 남기는 방안을 검토하고 싶다.

LQC(제조 중 검사):

- 품질 담당자가 제조 중 검사를 수행하고 있으나 공식 기준서와 성적서는 없다.

OQC(자체검수):

- 기준과 성적서가 비교적 명확하게 운영된다.
- 고객 요청·과거 문제·특이사항을 다음 프로젝트의 OQC 기준과 성적서에 계속 추가한다. 예: 이전 프로젝트의 문 경첩 파손 문제를 다음 OQC 항목으로 추가.
- 프로젝트에 해당 부품이 없는 경우 항목을 아예 제외할지, 전체 항목을 유지하고 `N/A`로 판정할지 품질팀도 고민 중이다.
- 프로젝트마다 적용할 OQC 기준과 성적서가 달라질 수 있다.

전진검수와 FAT:

- 고객이 방문해 실제 제품·도면·기존 검사성적서를 종합 확인한다. 세부 체크리스트를 다시 작성하는 검사라기보다, 기존 모든 품질 증빙을 제시하고 고객 확인을 받는 절차에 가깝다.
- OQC 성적서를 요약한 별도의 고객용 성적서에 고객 서명을 받아 보관한다.

도면 대조:

- 품질팀은 검사 중 도면과 실제 제품의 일치를 계속 확인하며, 현재는 검사성적서와 도면을 출력해 현장에 들고 다닌다.
- 종이 출력 의존을 줄이면서 정확한 도면 revision과 검사 기록을 연결할 방안이 필요하다.

### 2.2 현재 Repository 기준선

- 자재 도착 등록은 구매품 종류와 무관하게 같은 transaction에서 도착분별 IQC 검사 회차·품질 내 업무·담당자 알림을 자동 생성한다. 별도 IQC 요청 버튼은 없다.
- IQC는 도착분당 하나의 상세 성적서를 단일 `MATERIAL_IQC` 양식 version으로 작성하고, 확정 후 불변 snapshot·PDF·사진(외함 사진 필수)을 보존한다.
- 패널 품질은 LQC·OQC checklist stage와 전진검수·FAT의 패널 단위 통합 판정을 제공하며, 부적합/PUNCH는 조치 담당 부서가 지정된 Pending 재검사로 연결되고 재검사 attempt가 누적된다.
- 양식 관리는 고정 6종 catalog(IQC/LQC/OQC/전진검수/FAT/제조 단계)의 무코드 version 관리(Draft→Active→Archived)를 제공한다. 활성화는 새 실행에만 적용되고 기존 성적서·실행의 snapshot은 불변이다.
- 다음은 아직 제공하지 않는다: 품목별 IQC routing, 프로젝트별 OQC 적용 계획, 협력사 원본 검사서 수용, 도면 revision과 검사 기록 연결, 고객용 요약 성적서.
- 도면 업로드와 도면 Revision 관리는 기존 확정 요구사항 기준선에서 명시적으로 범위 밖이었다(`docs/05`, `docs/11`).
- Roadmap 추적 대상에는 IQC/LQC/OQC 상세 checklist content, 필수 사진 위치, PDF layout이 현업 회신 대기로 남아 있고, 관리 기능은 완료된 양식 관리 Task를 재구현하지 않는다는 경계가 기록되어 있다.

## 3. 문제 진단 — 현장과 시스템의 핵심 격차

1. **전수 자동 IQC 대 선택 IQC.** 시스템은 모든 도착분에 IQC 회차와 품질 업무를 만들지만 현장은 네 종류만 검사하고 공식 성적서는 외함뿐이다. 그대로 운영하면 품질팀 업무함이 실제로는 검사하지 않는 품목의 IQC 업무로 채워지고, 이를 형식적으로 `적합` 처리하면 검사하지 않은 것을 검사한 것처럼 기록하는 데이터 왜곡이 생긴다. 이것이 가장 시급한 격차다.
2. **자유 입력 품목명과 검사 대상 판별.** 검사 대상을 시스템이 구분하려면 분류 기준이 필요한데, 현재 구매품목은 자유 입력 텍스트다. 문자열 추론으로 외함 여부를 판별하는 방식은 오분류 위험이 커서 권장하지 않는다.
3. **협력사 원본 검사서의 부재.** 외함 IQC의 실제 증빙 절반은 협력사가 작성해 종이로 도착하는 검사서인데, 시스템의 IQC 성적서는 품질팀이 처음부터 끝까지 작성하는 구조만 있다.
4. **LQC의 실행-기록 불일치.** 검사는 수행되지만 기준서·성적서가 없어, 시스템의 LQC stage가 현장에서 근거 없는 체크로 채워질 수 있다.
5. **OQC의 프로젝트별 가변성 미지원.** 시스템 양식은 종류당 현재 Active version 하나이며, 프로젝트 특성에 따라 항목을 적용·제외하는 계획 개념이 없다.
6. **전진검수·FAT의 증빙 제시 성격 미반영.** 시스템은 통합 판정 입력 중심이고, 현장의 실체인 "기존 증빙 묶음 제시 + 고객용 요약 성적서 서명"을 지원하지 않는다.
7. **도면 대조의 종이 의존.** 검사 기록은 디지털화됐지만 대조 기준인 도면은 시스템 밖에 있어, 어떤 revision으로 검사했는지 기록이 남지 않는다.

## 4. 영역별 Fable 제안

### 4.1 IQC 대상 분류와 구매 자유 입력의 연결

**Fable 제안**: 문자열 추론이 아니라 사람이 지정하는 `검사 분류`를 구매품목의 명시 속성으로 도입한다.

- 관리자 기준정보에 `수입검사 분류` master를 둔다. 초기 값은 `외함(공식 성적서)`, `판금류(육안 기록)`, `부스바(육안 기록)`, `명판(육안 기록)`, `검사 없음`의 다섯이다. 분류가 검사 수준(공식 성적서 / 경량 기록 / 없음)을 결정한다.
- 구매정보 입력 시 구매 담당자가 품목별로 분류를 선택한다. 품목명은 지금처럼 자유 입력을 유지하되, 분류는 선택형이므로 시스템이 안정적으로 routing할 수 있다. 기본값은 `검사 없음`으로 두어 미선택이 과잉 검사를 만들지 않게 한다.
- 자재 도착 시 분류에 따라 분기한다: `공식 성적서` 분류만 현행처럼 상세 IQC 성적서 업무를 생성하고, `육안 기록` 분류는 경량 기록 업무(4.3)를, `검사 없음`은 IQC 없이 곧바로 입고 확정 가능 상태로 둔다.
- 분류 오지정의 복구 경로가 필요하다. 도착 이력이 생기기 전에는 구매 담당자가 분류를 수정할 수 있고, 도착 후 분류 변경은 이미 생성된 검사 회차를 소급 변경하지 않으며 다음 도착분부터 적용한다(양식 version과 같은 "새 실행에만 적용" 원칙의 재사용).
- 품질팀이 필요 시 특정 도착분에 수동으로 검사를 추가 요청할 수 있는 예외 경로를 남겨, 분류가 `검사 없음`이어도 의심 물품을 검사할 수 있게 한다.

이 설계의 핵심은 "누가 검사 대상을 결정하는가"를 시스템 추론이 아니라 명시적 분류 선택과 그 변경 이력으로 만드는 것이다. 분류 책임을 구매팀이 질지 품질팀이 질지는 사용자 결정 항목(8장)이다.

### 4.2 외함 협력사 원본 검사서

**Fable 제안**: 단기적으로는 "협력사 종이 검사서 사진·스캔 첨부 + 품질팀 확인 항목 + 품질 서명"의 2부 구성 성적서로 수용하고, 협력사 직접 입력은 별도 후속 결정으로 미룬다.

- 외함 IQC 성적서 양식을 두 부분으로 나눈다: (1) `협력사 검사서 수령 확인` — 종이 검사서의 사진 또는 스캔 첨부를 필수로 하고 수령 여부·이상 유무를 체크, (2) `EMI 직접 확인 항목` — 품질팀이 현물에서 직접 확인하는 항목의 체크·값 입력. 기존 무코드 양식 관리로 항목을 구성할 수 있으므로 관리 기능 재구현은 필요 없고, 필요한 것은 첨부 필수 속성 정도다.
- 확정 시 협력사 검사서 이미지가 성적서 snapshot·PDF에 포함되어, 현재의 "종이 보관"이 "불변 디지털 증빙"으로 대체된다.
- 협력사가 시스템에 직접 입력하는 방안(외부 사용자 계정 또는 제한 링크)은 인증·권한·데이터 품질 부담이 커서 1차 범위로 권장하지 않는다. 종이+사진 수용으로 먼저 증빙을 시스템 안으로 들여온 뒤, 실효가 확인되면 별도 신규 기능으로 검토할 것을 권장한다.

### 4.3 판금류·부스바·명판의 기록 수준

**Fable 제안**: 외함과 같은 상세 성적서가 아니라, 도착분 단위의 `경량 육안 검사 기록`을 별도 수준으로 도입한다.

- 구성은 최소로 한다: 육안 확인 항목 몇 개의 체크(예: 외관 손상, 수량, 규격 표시), 종합 적합/부적합, 선택 사진, 선택 메모. 모바일에서 수십 초 안에 끝나는 것을 목표로 한다.
- 부적합 시에는 현행 IQC와 동일하게 Pending 등록·재검사 흐름으로 연결한다. 기록이 가벼워도 부적합 처리는 같은 경로여야 이력이 갈라지지 않는다.
- 항목 기준은 품질팀이 양식 관리에서 세 품목 공통 또는 품목별로 관리한다. 상세 성적서로의 승격(예: 부스바를 공식 성적서 대상으로 격상)은 분류 master의 검사 수준 변경으로 처리한다.
- 이 수준을 아예 도입하지 않고 세 품목을 `검사 없음`으로 두는 선택지도 있으나, 사용자가 기준·기록을 남기는 방향을 검토하고 싶다고 확인했고, 기록이 없으면 부적합 발생 시 소급 근거가 없으므로 경량 기록 도입을 권장한다.

### 4.4 LQC 기준서와 성적서

**Fable 제안**: LQC 기준서·성적서를 만들되, 처음부터 상세하게 만들지 말고 "현재 실제로 보는 것"을 최소 항목으로 명문화하는 데서 시작한다.

- 근거: 시스템에는 이미 LQC stage·checklist·재검사·사진 구조가 있다. 없는 것은 content뿐이다. 기준 없는 검사는 담당자별 편차와 분쟁 시 근거 부재라는 실질 위험이 있고, 시스템에 기록이 남기 시작하면 그 기록 자체가 근거가 되므로 기준 명문화의 필요성이 커진다.
- 시작 항목은 품질팀이 현재 제조 중 실제로 확인하는 것(도면·작업기준 일치, 조립 상태, 배선·체결, 표시·마감 계열)을 5~10개 이내로 정리하고, 운영하며 양식 version으로 다듬는 것을 권장한다. 과도한 초기 항목은 형식적 체크를 유발한다.
- 제조 단계와의 연결은 1차로 "LQC 요청 시점 기준"을 정하는 수준(예: 특정 제조 단계 완료 시 LQC 업무 생성 — 현행 흐름 유지)을 권장한다. 제조 단계별로 다른 LQC 양식을 적용하는 세분화는 실측 수요가 확인되기 전에는 도입하지 않는 것이 좋다.
- LQC 성적서 발행 여부(내부 기록으로 충분한가, 고객 제출용 성적서까지 필요한가)는 사용자 결정 항목이다.

### 4.5 OQC — 프로젝트별 가변 항목과 `제외` 대 `N/A`

이 영역이 이번 조사에서 가장 구조적인 설계 결정을 요구한다.

**`제외` 대 `N/A`에 대한 Fable 의견**: 기본 정책으로 **`N/A`(항목 유지, 사유 포함 해당 없음 판정)**를 권장한다.

- `N/A`의 장점: 모든 프로젝트의 성적서가 같은 항목 목록을 가지므로 프로젝트 간 비교·집계가 가능하고, "이 항목을 검토했으나 해당 없음"이라는 판단 자체가 기록으로 남는다. 재발 방지 항목(경첩 파손 등)은 특히, 해당 부품이 없다고 항목을 지우면 "없어서 안 본 것"과 "실수로 빠뜨린 것"을 구분할 수 없게 된다.
- `제외`의 장점: 성적서가 짧아지고 현장 입력 부담이 준다. 항목 수가 수십 개를 넘고 해당 없음 비율이 높은 프로젝트에서는 `N/A` 방식이 클릭 낭비가 된다.
- 절충 권장안: 판정 값에 `N/A`를 정식으로 추가하되, 프로젝트별 적용 계획(아래)에서 명백히 무관한 항목군을 `적용 안 함`으로 지정하면 성적서 화면에서 접힌 상태로 표시하고 일괄 `N/A` 처리할 수 있게 한다. 데이터는 남고 입력 부담은 줄어든다. 단, 이 절충안 채택 여부와 `N/A` 사유 필수 여부는 사용자 결정 항목이다.

**프로젝트별 가변 OQC에 대한 Fable 제안**: `OQC 항목 library + 프로젝트별 적용 계획`의 2층 구조를 권장한다.

- 1층 — 항목 library: 회사 표준 OQC 항목의 단일 누적 목록. 재발 방지 항목은 여기에 추가되며, 각 항목에 출처(고객 요청/과거 문제/표준)와 적용 조건 tag(예: `문 있는 외함`)를 기록할 수 있다. 과거 문제에서 나온 항목은 원 Pending 이슈를 참조로 연결해 "왜 이 항목이 생겼는지"를 추적 가능하게 한다.
- 2층 — 프로젝트 적용 계획: 프로젝트의 OQC 시작 전에 library의 현재 version에서 해당 프로젝트에 적용할 항목 집합을 확정하고 snapshot한다. 이는 기존에 확정된 "프로젝트는 생성·검사 시작 당시 양식 snapshot을 유지한다" 원칙의 자연스러운 확장이며, 검사 시작 후 library가 바뀌어도 진행 중 성적서는 불변이다.
- 재발 방지 항목의 전파 규칙(새 항목이 이후 모든 프로젝트에 자동 포함되는가, 품질팀이 프로젝트별로 선택하는가)은 사용자 결정 항목이다. Fable은 "기본 자동 포함 + 적용 계획에서 명시적 `적용 안 함` 지정 가능"을 권장한다. 재발 방지 항목이 조용히 누락되는 것이 가장 피해야 할 실패이기 때문이다.

### 4.6 전진검수·FAT — 고객용 성적서와 증빙 묶음

**Fable 제안**: 전진검수·FAT를 "새 체크리스트 작성"이 아니라 "증빙 패키지 제시 + 고객 확인"으로 다시 정의하고, 두 가지를 추가한다.

- 증빙 패키지 조회: 검사 화면에서 해당 패널·프로젝트의 기존 확정 증빙(IQC·LQC·OQC 성적서 PDF, 사진, Pending 조치 이력)을 한 화면에서 모아 보여주는 읽기 전용 view. 새 데이터 개념이 아니라 기존 불변 snapshot의 집계 조회이므로 위험이 낮고, 고객 입회 시 종이 묶음을 대체하는 즉효가 있다. 현장(고객사 방문 포함)에서 쓰이므로 모바일 표시 품질이 중요하다.
- 고객용 요약 성적서: OQC 결과를 요약한 고객 제출용 문서를 시스템이 생성하고, 고객 서명을 받은 결과를 보존한다. 서명 방식은 1차로 "출력 또는 화면 제시 → 서명본 사진·스캔 첨부"를 권장한다. 화면 위 전자서명은 법적 효력·고객 수용성 검토가 필요한 별도 결정이므로 1차 범위로 권장하지 않는다. 서명본이 첨부된 시점에 해당 판정 증빙은 불변으로 고정한다.
- 현행 "패널당 통합 판정 1회 + PUNCH는 Pending 재검사" 구조는 현장 운영과 충돌하지 않으므로 유지한다. 요약 성적서와 증빙 패키지는 판정 구조를 바꾸는 것이 아니라 판정 앞뒤의 준비·증빙 절차를 시스템 안으로 들여오는 것이다.

### 4.7 도면 revision과 검사 기록의 연결

**Fable 제안**: 정식 도면 관리(CAD 보관, revision workflow, 설계 승인 절차)를 이번에 도입하지 말고, `검사 참조용 도면 파일`이라는 최소 개념부터 시작한다.

- 기존 기준선은 도면 revision 관리를 명시적으로 범위 밖으로 확정했었다. 이를 뒤집어 완전한 도면 관리 체계를 만드는 것은 설계 부서의 업무 방식 전체가 걸린 큰 결정이며, 품질팀의 당면 문제(종이 출력, revision 불명) 해결에 그 전부가 필요하지는 않다.
- 최소 개념: 프로젝트 또는 패널에 도면 파일(PDF)을 revision 표기·업로드 일시·업로드 담당자와 함께 첨부하고, 같은 대상에 새 파일이 오면 대체가 아니라 이력으로 누적한다. 검사 화면에서 현재 도면을 바로 열람할 수 있게 한다.
- 검사 기록 연결: 검사 확정 시점에 "당시 최신 도면 revision 표기"를 성적서 snapshot에 자동 기록한다. 이것만으로 "이 검사는 어느 도면 기준이었는가"라는 현장 질문에 답할 수 있다.
- 도면 업로드 책임 부서(설계로 추정되나 미확정), 도면 없이 검사 확정을 허용할지(1차는 허용 권장 — 차단하면 도입 초기 검사가 막힌다), 정식 도면 관리로의 확장 여부는 사용자 결정 항목이다.

| 개념 | 성격 | 연결 대상 |

| 수입검사 분류 master | 관리자 기준정보. 검사 수준(공식 성적서/육안 기록/없음) 결정 | 구매품목의 명시 속성 |

| 검사 참조용 도면 파일 | revision 표기가 있는 누적 첨부와 검사 시점 revision 기록 | 프로젝트/패널, 검사 성적서 snapshot |

## 6. 단계별 도입 순서 (Fable 권장)

1. **1단계 — IQC routing.** 수입검사 분류 master, 구매품목 분류 선택, 도착 시 분기, 경량 육안 기록. 가장 큰 데이터 왜곡(형식적 전수 IQC)을 먼저 제거한다. 기존 프로젝트·진행 중 도착분은 현행 흐름을 유지하고 새 등록부터 적용한다.
2. **2단계 — 외함 검사서 2부 구성.** 협력사 검사서 첨부 필수 구획과 EMI 확인 구획. 1단계로 외함이 유일한 공식 성적서 대상으로 정리된 뒤에 적용해야 효과가 명확하다.
3. **3단계 — OQC library와 프로젝트 적용 계획, `N/A` 판정.** `제외` 대 `N/A` 사용자 결정이 선행되어야 한다.
4. **4단계 — 전진검수·FAT 증빙 패키지와 고객용 요약 성적서.** 3단계의 OQC 구조가 요약의 원천이므로 그 뒤가 자연스럽다.
5. **5단계 — 도면 참조 최소 도입.** 독립성이 높아 순서 조정이 가능하나, 정식 도면 관리 확장 여부의 사용자 결정이 먼저 필요하다.
6. **병행 — LQC 기준 content 입력.** 시스템 변경이 거의 없는 content 작업이므로 품질팀 준비가 되는 대로 기존 양식 관리로 진행할 수 있다.

각 단계는 독립 검증·독립 되돌림이 가능한 크기로 유지하고, 단계마다 별도 Task 분류·기획·승인 절차를 거친다.

## 7. 위험과 완화

- **분류 오지정 위험**: `검사 없음` 기본값이 실제 검사 대상을 놓칠 수 있다. 완화 — 품질팀의 수동 검사 추가 경로, 분류 변경 이력 audit, 도입 초기 품질팀의 분류 현황 점검 화면.
- **입력 부담 증가 위험**: 경량 기록·`N/A` 판정·도면 확인이 현장 클릭을 늘린다. 완화 — 경량 기록의 항목 수 상한, 접힘·일괄 `N/A` 절충안, 모바일 우선 화면 검증.
- **기존 데이터와의 경계**: 새 분기·새 판정 값이 기존 확정 성적서를 소급 변경해서는 안 된다. 완화 — 모든 변경을 "새 실행부터 적용" 원칙으로 통일하고 legacy 표시를 명시한다.
- **범위 팽창 위험**: 협력사 직접 입력, 전자서명, 정식 도면 관리는 각각 독립된 큰 기능이다. 완화 — 본 의견서는 세 가지 모두 1차 범위에서 제외하는 것을 권장하며, 채택 시 별도 신규 기능으로 분리한다.
- **두 의견서 불일치 위험**: 독립 작성된 Codex 의견과 결론이 다를 수 있다. 이는 계약된 정상 상태이며, 채택·절충은 사용자 판단 사항이다.

## 9. 보존해야 할 불변조건

어떤 재구성안을 채택하더라도 다음은 보존한다.

- 확정된 검사 결과와 완료 증빙의 불변 snapshot·PDF·사진, append-only 원칙
- Pending 조치·재검사 이력의 연속성과 발생 단계로의 재검사 복귀
- 패널 단위·구매품목(도착분) 단위의 데이터 단위 원칙
- 검사 단계별 정·부 담당자 구조와 서버 authoritative 권한·프로젝트 접근 scope
- 기존 프로젝트의 생성·검사 시작 당시 양식 snapshot 유지, 새 version은 새 실행에만 적용
- 전진검수·FAT의 패널 단위 통합 판정 1회 구조
- 완료된 양식 관리·검사 기능의 재구현 금지 — 변경은 content 입력과 additive 확장으로만

## 10. 승인 경계

- 이 문서는 독립 의견서이며 planning 승인·구현 승인·게시 승인이 아니다.
- `implementationApproved: false`, `mainMergeApproved: false` 상태는 이 문서로 변하지 않는다.
- 여기 제시한 제안의 실행은 각각 Task Identity Gate, 기획·review·승인 절차를 별도로 거쳐야 하며, 8장의 사용자 결정이 확정되기 전에는 해당 영역을 구현하지 않는다.
